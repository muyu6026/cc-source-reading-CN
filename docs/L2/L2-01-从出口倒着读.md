## 1. 为什么倒着读

一个文件的代码不是平等重要的。`commandSemantics.ts` 里有一张 6 项的表、四个函数，但**只有一个是出口**：

```bash
grep -rn "interpretCommandResult" source/src --include="*.tsx"
```

实际输出：

```
source/src/tools/BashTool/BashTool.tsx:44:import { interpretCommandResult } from './commandSemantics.js';
source/src/tools/BashTool/BashTool.tsx:690:    interpretationResult = interpretCommandResult(input.command, result.code, result.stdout || '', '');
```

整个仓库只有 `BashTool.tsx` 第 690 行**调用**它（PowerShellTool 有自己的一份副本）。也就是说：这个 140 行的文件，最终只为回答 BashTool 的一个问题——「这条命令退出码是 N，算不算错？」。

**倒着读的顺序**就是顺着这唯一的调用反推：

1. 先读出口 `interpretCommandResult`（第 124–140 行）：它收什么、吐什么？
2. 它第 133 行调了 `getCommandSemantic`（第 94–99 行）：这是「选逻辑」的一步。
3. 选逻辑查的是 `COMMAND_SEMANTICS` 表（第 31–89 行）：这是「数据」。
4. 查不到时兜底的 `DEFAULT_SEMANTIC`（第 22–26 行）：最简单，最后看。

先看什么再看什么、为什么？——因为**出口决定了其他代码存在的意义**。不知道出口吐 `{ isError, message? }`，你就无法理解那张表里每个函数为什么都要返回这个形状。倒着读，每一层都有上一层的「问题」在手，读起来就不是背书，是找答案。

## 2. 精读正文（行号为 source 原文行号）

### 2.1 第一步：读出口（第 121–140 行）

```ts
/**
 * Interpret command result based on semantic rules
 */
export function interpretCommandResult(
  command: string,
  exitCode: number,
  stdout: string,
  stderr: string,
): {
  isError: boolean
  message?: string
} {
  const semantic = getCommandSemantic(command)
  const result = semantic(exitCode, stdout, stderr)

  return {
    isError: result.isError,
    message: result.message,
  }
}
```

**逐段念**：

| 片段 | 念法 |
| --- | --- |
| `export function` | 「我是出口」——全文件只有这一个 `export function` |
| `command, exitCode, stdout, stderr` | 收四样：命令字符串、退出码、两路输出 |
| `): { isError: boolean, message?: string }` | 吐一个对象：「算不算错」必填，「给人看的一句话」可选 |
| 第 133 行 `getCommandSemantic(command)` | 第一行：**选**一段逻辑（只看命令名） |
| 第 134 行 `semantic(exitCode, stdout, stderr)` | 第二行：**调**刚选中的那个函数 |
| 第 136–139 行 | 把结果原样转出去 |

函数体只有两行有效代码，却浓缩了本文件的全部架构：**选函数、调函数是两个时刻**。第 133 行拿到的是「一个函数值」（回忆 [L0-07](../L0/L0-07-函数也是值.md)：函数可以像数字一样被传来传去），第 134 行的圆括号才真正执行它。

读完出口你手里有了两个问题：「`getCommandSemantic` 怎么选的？」「选出来的函数长什么样？」——带着问题往上一层。

### 2.2 第二步：选逻辑的一层（第 91–99 行）

```ts
/**
 * Get the semantic interpretation for a command
 */
function getCommandSemantic(command: string): CommandSemantic {
  // Extract the base command (first word, handling pipes)
  const baseCommand = heuristicallyExtractBaseCommand(command)
  const semantic = COMMAND_SEMANTICS.get(baseCommand)
  return semantic !== undefined ? semantic : DEFAULT_SEMANTIC
}
```

三行三个动作：

1. 第 96 行：从完整命令里**提取基名**（比如 `cat x | grep y` 提取 `grep`，下一小节看怎么提的）。
2. 第 97 行：拿基名去 `COMMAND_SEMANTICS` 表里查。`Map.get` 查不到返回 `undefined`，所以 `semantic` 的类型是 `CommandSemantic | undefined`——又是 [L0-06](../L0/L0-06-联合类型三值状态机.md) 那个三值思路。
3. 第 98 行：查到就用查到的，查不到用默认。**兜底让「表没登记」永远不是崩溃，而是走默认路径。**

**基名怎么提**（第 108–119 行，先扫一眼注释就够了）：

```ts
/**
 * Extract the primary command from a complex command line;
 * May get it super wrong - don't depend on this for security
 */
function heuristicallyExtractBaseCommand(command: string): string {
  const segments = splitCommand_DEPRECATED(command)

  // Take the last command as that's what determines the exit code
  const lastCommand = segments[segments.length - 1] || command

  return extractBaseCommand(lastCommand)
}
```

第 115 行注释是本文件第二重要的信息：**取最后一段**。为什么？因为 shell 默认把管道最后一段的退出码当整条管道的退出码——代码在做和 shell 一致的事。第 110 行注释还自我警告 `May get it super wrong - don't depend on this for security`：这只是给展示层解释退出码用的，不能拿去做安全判断。

### 2.3 第三步：读那张表（第 28–89 行）

```ts
const COMMAND_SEMANTICS: Map<string, CommandSemantic> = new Map([
  // grep: 0=matches found, 1=no matches, 2+=error
  [
    'grep',
    (exitCode, _stdout, _stderr) => ({
      isError: exitCode >= 2,
      message: exitCode === 1 ? 'No matches found' : undefined,
    }),
  ],
```

表的形状：键是命令基名字符串，值是符合 `CommandSemantic` 形状的**匿名函数**（函数当值塞进字典，见 [L0-07](../L0/L0-07-函数也是值.md) §2.3）。表里登记了 6 个命令，可以用 grep 数出来：

```bash
grep -n "isError: exitCode >= 2" source/src/tools/BashTool/commandSemantics.ts
```

实际输出：

```
36:      isError: exitCode >= 2,
45:      isError: exitCode >= 2,
54:      isError: exitCode >= 2,
64:      isError: exitCode >= 2,
73:      isError: exitCode >= 2,
82:      isError: exitCode >= 2,
```

6 处、6 个命令（`grep`、`rg`、`find`、`diff`、`test`、`[`），而且**清一色 `exitCode >= 2` 才算错**。这不是巧合：这 6 个命令都是「退出码 1 携带正常信息」的命令——没匹配到、有差异、条件为假。它们共用同一个判式，只是 `message` 各说各话。

第 87–88 行注释交代了反面：`wc`、`head`、`tail`、`cat` 这类命令「只会在真错误时失败」，所以**不登记**，直接走默认。

### 2.4 第四步：最简单的兜底（第 19–26 行）

```ts
/**
 * Default semantic: treat only 0 as success, everything else as error
 */
const DEFAULT_SEMANTIC: CommandSemantic = (exitCode, _stdout, _stderr) => ({
  isError: exitCode !== 0,
  message:
    exitCode !== 0 ? `Command failed with exit code ${exitCode}` : undefined,
})
```

Unix 通用约定：退出码 0 = 成功，其余 = 失败。表里 6 个「退出码有特殊含义」的命令被单独关照，剩下的全部走这条最朴素的规则。到此，从出口出发的四层全部读完，每一层都回答了上一层留下的问题。

## 3. 核心问题（路线图 L2-1 卡片）

### 问题 1：`grep` 退出码 1 为什么不算错？

先想 `grep` 是怎么用的：`grep foo *.txt`——「这些文件里有没有 foo」本身就是个问题，**退出码就是答案**：0 = 找到了，1 = 没找到，2+ = 出事了（文件读不了等）。

「没找到」是 `grep` 对提问的正常回答，不是故障。所以表里 `grep` 的语义函数（第 35–38 行）判 `isError: exitCode >= 2`，并且专门在 `exitCode === 1` 时给人一句 `No matches found`——**既不当错处理，也不沉默**。

如果用默认语义（`exitCode !== 0` 算错）会怎样？你每次用 CC 跑一个没匹配到结果的搜索，界面就满屏假红、模型也以为任务失败了。第 4–5 行的文件头注释写的就是这个教训：`grep returns 1 when no matches are found, which is not an error condition`。

### 问题 2：第 98 行为什么写 `semantic !== undefined ? semantic : DEFAULT_SEMANTIC`，不写 `semantic || DEFAULT_SEMANTIC`？

在这个文件里，**两种写法行为完全一样**。因为 `semantic` 来自 `Map.get`，类型是 `CommandSemantic | undefined`：查到是函数（永远真值），查不到是 `undefined`（唯一可能的假值）。`||` 和 `!== undefined` 在这里分不出胜负。

但**表意**差别很大：

- `||` 的语义是「是假值就换」，假值包括 `0`、`''`、`false`、`null`、`undefined` 一大票。读者得自己推理「这里的值会不会恰好是 0 或空串」才能确认安全。
- `!== undefined` 的语义是「**查不到**才换」，精确对应 `Map.get` 的失败情形，读者不用做额外推理。

还有第三种写法 `??`（空值合并）：只在 `null`/`undefined` 时才换，语义和这里的需求严丝合缝，而且更短。PowerShell 那份同名文件就是这样写的（`?? DEFAULT_SEMANTIC`）。三个写法按精确度排序：`??` ≥ `!== undefined` > `||`。记住原则：**想排除什么，就明写什么**，别让读代码的人猜。

### 问题 3：命令带管道 `cat x | grep y`，退出码看谁？

看**最后一段**的。第 115–116 行注释直接给了答案：

```ts
// Take the last command as that's what determines the exit code
const lastCommand = segments[segments.length - 1] || command
```

shell 的规则就是如此：不带 `set -o pipefail` 时，管道的退出码 = 最后一段的退出码。所以提取基名时取最后一段，`cat x | grep y` 按 `grep` 的语义判——grep 返回 1（没匹配）照样不算错，哪怕前面的 `cat` 成功了。

## 4. 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 表是一串 `if (cmd === 'grep') ... else if ...` | 是一张 `Map`，**查表选函数**；加新命令是加一个表项，不是再加一个分支 |
| 表里没登记的命令会报错/崩溃 | 走 `DEFAULT_SEMANTIC` 兜底（第 98 行），「没登记」是正常路径 |
| `heuristicallyExtractBaseCommand` 是安全判断的一部分 | 注释原文警告 `don't depend on this for security`——它只是给展示层解释退出码用的启发式 |
| `exitCode === 1` 给了 `message`，说明 1 还是有点错 | `message` 是给人看的提示语（如 `No matches found`），和 `isError: false` 不矛盾 |
