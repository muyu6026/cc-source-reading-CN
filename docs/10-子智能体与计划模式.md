## 10.1 先正名：Agent、Task、subagent 是一件事

工具名是 `Agent`，`Task` 只是旧版线上名，保留给历史权限规则与会话恢复：`constants.ts:1` 是 `AGENT_TOOL_NAME = 'Agent'`，`:3` 是 `LEGACY_AGENT_TOOL_NAME = 'Task'`（注释原话：`Legacy wire name for backward compat`）。

老文档、权限规则 `Task(...)`、日志里的 `Task`，都指 [`Agent` 工具](../annotated/src/tools/AgentTool/AgentTool.tsx#L519)。本仓库**没有**第二个子代理运行时：除 `team_name + name` 走 `spawnTeammate` 外，所有子代理都从 `AgentTool.call` 进入 `runAgent`。

形态有三种：默认同步（结果直接变 `tool_result`）；`run_in_background` / 定义 `background` / 协调器 / fork 实验触发异步（先回 `agentId`，完成投递 `<task-notification>`）；不传 `subagent_type` 且 `FORK_SUBAGENT` 打开则走 fork（继承父对话）。

```bash
grep -n "const shouldRunAsync" source/src/tools/AgentTool/AgentTool.tsx
```

实际输出：`567:    const shouldRunAsync = (run_in_background === true || selectedAgent.background === true || ...`。

## 10.2 创建：`AgentTool.call` 的七步

`call()` 从 239 行开始，主干是直线，没有调度器：

| 步 | 行 | 做了什么 |
| --- | --- | --- |
| ① 解析参数 | [`239`](../annotated/src/tools/AgentTool/AgentTool.tsx#L519) | `prompt` / `subagent_type` / `model` / `run_in_background` / `name` / `team_name` / `isolation` |
| ② 选定义 | [`330-360`](../annotated/src/tools/AgentTool/AgentTool.tsx#L759) | 按 `subagent_type` 在 `activeAgents` 里找；找不到报「Available agents: …」 |
| ③ 拼提示词 | [`534`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1101) | 普通路径用 agent 自己的 `getSystemPrompt`；fork 继承父级已渲染字节 |
| ④ 算工具池 | [`573`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1222) | `assembleToolPool({...mode: agent.permissionMode ?? 'acceptEdits'})` |
| ⑤ 同步/异步 | [`567`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1193) | 看参数、定义的 `background`、协调器、fork 实验 |
| ⑥ 建 agentId | [`580`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1236) | 同步/异步共用，worktree 分支名也用它 |
| ⑦ 调 `runAgent` | [`846`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1790) | 同步拿 async 迭代器；异步包后台生命周期 |

两个容易漏的点：

- **默认不弹权限框。** `checkPermissions` 在非 auto 模式直接 `allow`，理由是子代理内部每个工具会再校验一遍；同文件 `isReadOnly()` 返回 `true`，注释是 `delegates permission checks to its underlying tools`（[`1265`](../annotated/src/tools/AgentTool/AgentTool.tsx#L2509)）。
- **父级工具限制不传下去。** `workerTools` 用 worker 自己的权限模式重装，注释写「so they aren't affected by the parent's tool restrictions」（[`568-575`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1217)）。

## 10.3 运行：`runAgent` 就是第二次 `query()`

`runAgent` 是 `AsyncGenerator<Message>`：不返回字符串，只把子代理的每条消息 `yield` 出去。核心只有一句——**同一个 `query()` 再跑一遍，换掉 messages / tools / systemPrompt**：

```ts
// source/src/tools/AgentTool/runAgent.ts:748-757
for await (const message of query({
  messages: initialMessages,
  systemPrompt: agentSystemPrompt,
  userContext: resolvedUserContext,
  systemContext: resolvedSystemContext,
  canUseTool,
  toolUseContext: agentToolUseContext,
  querySource,
  maxTurns: maxTurns ?? agentDefinition.maxTurns,
})) {
```

「递归」不是比喻：`query()` 里还是 [06 章](06-对话主循环与模型调用.md)那个 `while(true)`，只是 `maxTurns` 可能非空。到点后 `query` 产 `max_turns_reached` 附件并 `return`（[`query.ts:1705`](../annotated/src/query.ts#L3225)），`runAgent` 见附件即 `break`（[`772-784`](../annotated/src/tools/AgentTool/runAgent.ts#L819)）。

**初始消息只有两段**（[`370-373`](../annotated/src/tools/AgentTool/runAgent.ts#L390)）：普通子代理是 `[...prompt]` 一条 user 消息；fork 子代理把父对话整段带进来，但先过 `filterIncompleteToolCalls`，剔掉「有 `tool_use` 没 `tool_result`」的 assistant 消息，否则 API 400（[`866-904`](../annotated/src/tools/AgentTool/runAgent.ts#L919)）。

**system prompt 不是父级那份**：`agentDefinition.getSystemPrompt()` + `enhanceSystemPromptWithEnvDetails`（追加 cwd、平台、模型），失败退回 `DEFAULT_AGENT_PROMPT`（[`906-937`](../annotated/src/tools/AgentTool/runAgent.ts#L960)）。只读型还做两项减法：Explore/Plan 去掉 CLAUDE.md（约 5–15 Gtok/周，[`389-400`](../annotated/src/tools/AgentTool/runAgent.ts#L412)）和父会话 gitStatus（约 1–3 Gtok/周，[`404-410`](../annotated/src/tools/AgentTool/runAgent.ts#L428)）。

**工具集三道筛子**（[`agentToolUtils.ts:122-260`](../annotated/src/tools/AgentTool/agentToolUtils.ts#L129)）：

1. `filterToolsForAgent` 去掉 `ALL_AGENT_DISALLOWED_TOOLS`：`TaskOutput`、`EnterPlanMode`、`ExitPlanMode`、`AskUserQuestion`、`TaskStop`，以及**非 ant 构建**的 `Agent` 本身（[`constants/tools.ts:36-46`](../source/src/constants/tools.ts#L36)）。这就是「普通子代理不能再派子代理」的出处。
2. 去掉定义里的 `disallowedTools`。
3. `tools` 为 `['*']` 或未写则保留全部；否则只留列出的名字，未命中记进 `invalidTools`。

异步代理再叠一层白名单，只留读文件、搜索、Shell、Edit/Write、Skill、ToolSearch 等（[`constants/tools.ts:55-69`](../source/src/constants/tools.ts#L55)），所以后台代理拿不到 `Agent`、`TaskOutput`、`TaskStop`。同步子代理里 `Agent` 也禁；唯一例外是 in-process teammate，为了让它能派同步子代理单独放行（[`agentToolUtils.ts:98-116`](../annotated/src/tools/AgentTool/agentToolUtils.ts#L105)）。

```bash
grep -n "ALL_AGENT_DISALLOWED_TOOLS = " -A 8 source/src/constants/tools.ts
```

实际输出第一行是 `36:export const ALL_AGENT_DISALLOWED_TOOLS = new Set([`，其后依次是 `TASK_OUTPUT`、`EXIT_PLAN_MODE_V2`、`ENTER_PLAN_MODE`、非 ant 构建的 `AGENT`、`ASK_USER_QUESTION`、`TASK_STOP`。

**权限与模型可以被降级**：`permissionMode` 覆盖父级，但父级是 `bypassPermissions` / `acceptEdits` / `auto` 时不覆盖（[`415-433`](../annotated/src/tools/AgentTool/runAgent.ts#L440)）；异步代理默认 `shouldAvoidPermissionPrompts: true`，遇 ask 按拒绝处理（[`437-452`](../annotated/src/tools/AgentTool/runAgent.ts#L463)）；模型优先级是 `CLAUDE_CODE_SUBAGENT_MODEL` > 参数 `model` > 定义 `model` > `inherit`（[`model/agent.ts:25-70`](../source/src/utils/model/agent.ts#L25)）。所以「子代理一定更便宜」是错的——只有 Explore 在非 ant 构建固定 `haiku`（[`exploreAgent.ts:83`](../annotated/src/tools/AgentTool/built-in/exploreAgent.ts#L83)）。

**隔离与共享不同**：`createSubagentContext` 默认克隆 `readFileState`、新建子 controller；但同步代理显式共享父级 `abortController`，并 `shareSetAppState: !isAsync`（[`520`](../annotated/src/tools/AgentTool/runAgent.ts#L553)）。所以 ESC 能中断同步子代理；异步的不与父级相连，只能 `TaskStop` 显式杀（[`AgentTool.tsx:706`](../annotated/src/tools/AgentTool/AgentTool.tsx#L1460)）。

## 10.4 回传：父会话只看到两样东西

**同步只取最后一段文本。** 子代理跑完，`AgentTool` 手里是 `agentMessages`（完整历史），回给父级的只有 `finalizeAgentTool` 的产物：

```ts
// source/src/tools/AgentTool/agentToolUtils.ts:300-320（节选）
let content = lastAssistantMessage.message.content.filter(_ => _.type === 'text')
if (content.length === 0) {
  // 最后一条是纯 tool_use（循环在工具调用处结束），往回找最近一条有文本的
  for (let i = agentMessages.length - 1; i >= 0; i--) { ... }
}
return { agentId, agentType, content, totalDurationMs, totalTokens, totalToolUseCount, usage }
```

**子代理读过多少文件、跑过多少命令，父会话一个字看不到**，只有最后一条 assistant 的 `text` 块；中间过程只进子代理自己的 transcript（[`733-737`](../annotated/src/tools/AgentTool/runAgent.ts#L776)）。包装成 `tool_result` 时补两段元数据（[`1341-1372`](../annotated/src/tools/AgentTool/AgentTool.tsx#L2662)）：

```
agentId: agent-xxxx (use SendMessage with to: 'agent-xxxx' to continue this agent)
<usage>total_tokens: 12345
tool_uses: 7
duration_ms: 42000</usage>
```

`Explore` / `Plan` 是一次性 agent，不会被 `SendMessage` 续聊，所以这两类**不加**尾部（[`1355-1361`](../annotated/src/tools/AgentTool/AgentTool.tsx#L2724)；集合定义 [`constants.ts:9-12`](../source/src/tools/AgentTool/constants.ts#L9)）。子代理没产出文本时补一句 `(Subagent completed but returned no output.)`，避免父级把「只有元数据」误读成没事可做。

**异步先回执、后通知。** 分支立刻返回 `{status:'async_launched', agentId, outputFile, canReadOutputFile}`，`tool_result` 只写「后台在跑，完成会通知你」（[`1318-1340`](../annotated/src/tools/AgentTool/AgentTool.tsx#L2612)）。完成时 `enqueueAgentNotification` 生成 XML，以 **user 角色消息**入队：

```
<task-notification>
<task-id>agent-xxxx</task-id>
<output_file>…/tasks/agent-xxxx.output</output_file>
<status>completed</status>
<summary>Agent "调查登录 bug" completed</summary>
<result>……子代理最后一段文本……</result>
</task-notification>
```

标签常量在 [`xml.ts:28`](../source/src/constants/xml.ts#L28)，拼装在 [`LocalAgentTask.tsx:249-259`](../source/src/tasks/LocalAgentTask/LocalAgentTask.tsx#L249)。`<result>` 与 `<usage>` 都可选，父级不能假设一定有内容。

**为什么非要隔离**：读 30 个文件、跑 20 条命令的中间结果若全塞回主对话，会迅速填满上下文，触发 [11 章](11-上下文压缩.md)的压缩——压缩本身又要一次模型调用。隔离后父级只付「最后一段文本 + 一行 usage」的钱。代价：子代理看不到父对话（fork 除外），所以 `prompt` 必须自包含——这也是 [`AgentTool/prompt.ts`](../annotated/src/tools/AgentTool/prompt.ts#L260) 反复强调「brief the agent like a smart colleague who just walked into the room」的原因。

## 10.6 计划模式（一）：进入只是切一个枚举

`EnterPlanMode` 没有入参，`call()` 只做三件事：拒绝子代理、记录旧模式、把模式写成 `plan`。

关键三处（[`77-99`](../annotated/src/tools/EnterPlanModeTool/EnterPlanModeTool.ts#L83)）：`if (context.agentId) throw new Error('EnterPlanMode tool cannot be used in agent contexts')`；`handlePlanModeTransition(mode, 'plan')`；`applyPermissionUpdate(prepareContextForPlanMode(...), {type:'setMode', mode:'plan', destination:'session'})`。

`prepareContextForPlanMode` 的唯一职责是把当前模式存进 `prePlanMode`，供退出时恢复；若当前是 `auto` 且用户开了「计划期间也用 auto」，则保留 auto 语义（[`permissionSetup.ts:1462-1492`](../annotated/src/utils/permissions/permissionSetup.ts#L1528)）。

进入后的 `tool_result` 是一段固定指令：探索代码、识别既有模式、考虑多个方案、需要澄清用 `AskUserQuestion`、最后用 `ExitPlanMode` 提交，并强调「DO NOT write or edit any files yet」（[`103-124`](../annotated/src/tools/EnterPlanModeTool/EnterPlanModeTool.ts#L113)）。工具自身声明 `isReadOnly() { return true }`、`shouldDefer: true`，所以不会自我拦截；进入需要用户同意（没有自定义 `checkPermissions`，默认走 ask），提示词写明 `This tool REQUIRES user approval`（[`prompt.ts:97`](../annotated/src/tools/EnterPlanModeTool/prompt.ts#L97)）。

## 10.7 计划模式（二）：plan 文件在哪

方案不只存在消息里，还**落盘一个 Markdown**。规则由 `utils/plans.ts` 决定：

| 项 | 规则 |
| --- | --- |
| 目录 | 默认 `~/.claude/plans`（[`94`](../annotated/src/utils/plans.ts#L116)） |
| 覆盖 | `settings.plansDirectory`，必须在项目根内，否则回退并报错（[`85-99`](../annotated/src/utils/plans.ts#L105)） |
| 文件名 | 会话级随机词 slug：`<word-slug>.md`（[`32-53`](../annotated/src/utils/plans.ts#L39)） |
| 子代理 | `<word-slug>-agent-<agentId>.md`（[`119-129`](../annotated/src/utils/plans.ts#L143)） |
| 读回 | `getPlan()` 直接 `readFileSync`，不存在返回 `null`（[`135-145`](../annotated/src/utils/plans.ts#L163)） |

slug 最多重试 10 次避免撞名（[`25`](../annotated/src/utils/plans.ts#L30)）；`/clear` 会清缓存，下次换新文件（[`62-66`](../annotated/src/utils/plans.ts#L77)）。

落盘而不是留在对话里的三个理由：① 退出后模型还能回读；② 压缩时作为附件重注入（[`compact.ts:545-555`](../source/src/services/compact/compact.ts#L545)）；③ 用户能直接在编辑器改这个文件再批准。

## 10.8 计划模式（三）：退出时发生四件事

`ExitPlanMode` 的 `call()` 顺序固定（[`243-420`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L256)）：① 取方案，优先 `input.plan`（CCR 网页或 Ctrl+G 编辑后回传），否则读盘；② 若用户改过就写回磁盘，避免后续 `Read` 读到旧版（[`259-261`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L274)）；③ `mode` 改回 `prePlanMode`，清空 `prePlanMode`，置 `hasExitedPlanMode` / `needsPlanModeExitAttachment`（[`360`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L378)）；④ 批准的方案原文**再次塞进 `tool_result`**，附「已保存到某路径，实现时可回看」（[`475-490`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L496)）。

两道校验：不在 `plan` 模式调用会被 `validateInput` 拒绝，提示「You are not in plan mode」（[`205-217`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L216)）；非 teammate 必须用户确认，`checkPermissions` 返回 `ask`，`requiresUserInteraction()` 为 `true`（[`185-232`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L194)）。teammate 走另一条路：需要「先计划后执行」时不弹本地框，而把 `plan_approval_request` 写进 `team-lead` 邮箱，返回 `awaitingLeaderApproval: true`（[`264-310`](../annotated/src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts#L280)），由 `useInboxPoller` 收回批准并切模式。

## 10.9 谁在拦写操作：三层，不是权限引擎

很多教程说「进入 plan 模式后 `hasPermissionsToUseTool()` 会拒绝一切写操作」——**本快照里不成立**：

```bash
grep -c "plan" source/src/utils/permissions/permissions.ts
grep -n "mode === 'plan'" source/src/utils/permissions/permissions.ts
```

实际输出：

```
2
523:        (appState.toolPermissionContext.mode === 'plan' &&
1270:    (appState.toolPermissionContext.mode === 'plan' &&
```

1,300 多行的权限判定文件只有两处提 `plan`，且都不是拒绝：523 行是「计划模式下 auto 分类器仍生效」，1270 行是「从 bypass 进入计划模式时继续 bypass」。`checkWritePermissionForTool` 也没有 `mode === 'plan' → deny` 分支，只认 deny/ask 规则、`acceptEdits` 和工作目录（[`filesystem.ts:1205-1419`](../annotated/src/utils/permissions/filesystem.ts#L1250)）。

真正起作用的是三层：

| 层 | 机制 | 证据 |
| --- | --- | --- |
| ① 指令 | 每回合注入 `plan_mode` 提醒「MUST NOT make any edits … This supercedes any other instructions」，并给 5 阶段工作流 | [`messages.ts:3227`](../annotated/src/utils/messages.ts#L3290) |
| ② 白名单 | plan 文件是唯一免询问可写路径；`checkWritePermissionForTool` 在 deny 规则后立刻放行 | [`filesystem.ts:1488-1498`](../annotated/src/utils/permissions/filesystem.ts#L1541) |
| ③ 弹窗 | 越界写不自动 deny，而走正常 `ask`，由用户决定；此时模型已违反指令 | [`filesystem.ts:1410-1419`](../annotated/src/utils/permissions/filesystem.ts#L1446) |

第 ① 层还有节流：`plan_mode` 附件隔若干回合才重发一次，首次全量、之后稀疏（`reminderType`），避免每轮灌长文（[`messages.ts:3136-3170`](../annotated/src/utils/messages.ts#L3198)）。子代理收到的是精简版：没有 5 阶段工作流，只重申只读、只能写 plan 文件、可用 `AskUserQuestion`（[`3399-3412`](../annotated/src/utils/messages.ts#L3464)）。

**结论**：计划模式是「强约定 + 单文件豁免 + 用户兜底」，不是沙箱。这也解释了为什么 Explore/Plan 还要在系统提示里再写一遍 `CRITICAL: READ-ONLY MODE`（[`exploreAgent.ts:29`](../annotated/src/tools/AgentTool/built-in/exploreAgent.ts#L29)）——约束靠提示词冗余，不靠权限位。想看权限引擎真正的三态与 1a–1g，去 [08 章](08-权限与安全.md) 与 [L4-C2](L4/L4-C2-判定流水线1a到1g.md)。

**计划模式本身就是子代理的大客户**：它的 5 阶段是写死的：① 只用 Explore 子代理探索（最多 3 个并行）；② 派 1–3 个 Plan 子代理设计；③ 自己读关键文件、用 `AskUserQuestion` 澄清；④ 写 plan 文件；⑤ 调 `ExitPlanMode`（[`messages.ts:3235-3286`](../annotated/src/utils/messages.ts#L3298)）。

数量不是拍脑袋（`source/src/utils/planModeV2.ts:5-35`）：Plan agent 默认 1 个，Max 20x / 企业 / 团队为 3 个；Explore agent 默认 3 个；两者都可被环境变量覆盖，上限 10。

提示词还要求：一轮回复只能以 `AskUserQuestion` 或 `ExitPlanMode` 结束，不允许用普通文本问「这个方案行吗」（[`messages.ts:3280-3286`](../annotated/src/utils/messages.ts#L3351)）。这把「审批」变成结构化工具调用，而不是自由对话。

## 10.11 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 子代理是「另一个模型实例」，有独立框架 | 同一个 `query()` 再跑一次，只换 messages / tools / systemPrompt（`runAgent.ts:748`） |
| 子代理干的所有事都会回到父对话 | 只回最后一条 assistant 的 `text` 块 + 一行 `<usage>`（`agentToolUtils.ts:300-320`） |
| 子代理默认用更便宜的模型 | 默认 `inherit`；只有 Explore 在非 ant 构建固定 `haiku`（`model/agent.ts:25`、`exploreAgent.ts:83`） |
| 派子代理会弹权限确认 | `checkPermissions` 默认直接 `allow`，靠子代理内部工具再校验（`AgentTool.tsx:1281-1297`） |
| plan 模式会硬拦截写入 | 权限引擎没有 plan 分支；靠提醒 + plan 文件白名单 + ask 弹窗兜底（`permissions.ts` 仅 2 处 `plan`） |
| `Task` 是另一套工具 | `Task` 只是 `Agent` 的旧 wire name（`constants.ts:3`） |
| 协调器是能自己干活的超级 agent | 它只有 4 个工具，读文件都不行；干活的是 worker（`constants/tools.ts:107`） |

## 10.12 本篇小结

- `Agent`（旧名 `Task`）是唯一派生子代理的入口；同步走 `runAgent` 迭代器，异步包 `LocalAgentTask`。
- 子代理 = 第二次 `query()`：独立 messages、独立工具池、可覆盖权限模式与模型，`maxTurns` 到点由 `query` 产出 `max_turns_reached`。
- 回传只有两样：同步是「最后一段文本 + agentId/usage」的 `tool_result`；异步是 `async_launched` 回执 + 完成后的 `<task-notification>`。
- 定义来源：内置 6 个、三层 `.claude/agents/*.md`、插件；frontmatter 控制工具、模型、轮次、权限、技能、MCP、记忆、隔离。
- 计划模式只做三件事：切 `mode='plan'`、把方案落到 `~/.claude/plans/<slug>.md`、退出时恢复 `prePlanMode` 并把方案原文塞回 `tool_result`。
- 它**不是沙箱**：写入靠指令约束 + 单文件白名单 + 用户审批三层兜底。
- 多智能体只有协调器与 swarm 两层皮，worker 运行时被构建开关裁掉，别把「缺失文件」当成读错了。

6. 计划模式第一阶段为什么用 `Explore` 子代理而不是主线程自己搜？默认并行几个？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. 同步：父回合内跑完，`finalizeAgentTool` 只留最后一条 assistant 的 `text` 块，再由 `mapToolResultToToolResultBlockParam` 包成 `tool_result`，尾部带 `agentId` 与 `<usage>`（Explore/Plan 例外，不带）。异步：立刻返回 `{status:'async_launched', agentId, outputFile}` 的 `tool_result`；完成后 `enqueueAgentNotification` 生成 `<task-notification>`，以 user 消息入队。出处：`AgentTool.tsx:1341-1372`、`LocalAgentTask.tsx:249-259`。
2. ① `filterToolsForAgent` 去掉 `ALL_AGENT_DISALLOWED_TOOLS`（含非 ant 的 `Agent`）；② 去掉定义里的 `disallowedTools`；③ 按 `tools` 白名单收窄，未命中的进 `invalidTools`。普通子代理因此不能嵌套；in-process teammate 例外放行 `Agent`，但 `call()` 又禁止它派后台代理或再建团队。出处：`agentToolUtils.ts:70-160`、`AgentTool.tsx:264-280`。
3. 子代理的循环可能在「纯 tool_use」处结束（轮次用尽或被中断），最后一条 assistant 没有任何 `text` 块；直接取会让 `content` 为空。回退到最近一条有文本的 assistant；若全都没有，`tool_result` 补 `(Subagent completed but returned no output.)`。出处：`agentToolUtils.ts:300-312`、`AgentTool.tsx:1349-1353`。
4. 目录默认 `~/.claude/plans`，可用 `settings.plansDirectory` 覆盖（必须在项目根内）；文件名是会话级随机词 slug `<word-slug>.md`，子代理是 `<word-slug>-agent-<agentId>.md`。`/clear` 清 slug 缓存，换新文件。出处：`plans.ts:76-129`。
5. 权限引擎不会因为 `mode==='plan'` 自动 deny（`permissions.ts` 只有 2 处 plan，均非拒绝）；`checkWritePermissionForTool` 只对 plan 文件白名单放行，普通文件落到默认 `ask`；于是弹出普通文件写权限框，由用户拒绝或批准。拦住的不是策略，而是「模型守规矩 + 用户不点同意」。出处：`filesystem.ts:1205-1419`、`1488-1498`、`permissions.ts:523/1270`。
6. Explore 是只读、可并行、上下文隔离的搜索代理：读文件的中间过程不污染主线程，主线程只拿结论；且非 ant 构建跑 `haiku`，成本低。默认并行 3 个，Plan agent 默认 1 个（Max 20x/企业/团队 3 个），都可用环境变量覆盖，上限 10。出处：`messages.ts:3235-3250`、`planModeV2.ts:5-35`。
