## 9.1 先分清三个「配置」

新手最容易犯的错，是把「主题」「模型」「CLAUDE.md」都当成同一种配置。实际上它们走三条不同的管线：

| 你嘴里的「配置」 | 真实文件 | 代码里的类型 | 管什么 | 谁写 |
|------------------|----------|--------------|--------|------|
| 全局状态 | `~/.claude.json` | `GlobalConfig` | 主题、安装方式、项目信任、启动次数、各种缓存 | CLI（`/config` 代写） |
| 设置 | `~/.claude/settings.json` 等 5 层 | `SettingsJson` | 模型、权限、hooks、环境变量、插件 | 用户 / 团队 / 管理员 |
| 记忆 | 四类 `CLAUDE.md` | `MemoryType` | 给模型的自然语言指令 | 用户 / 团队 |

三个类型分别定义在 [`config.ts`](../annotated/src/utils/config.ts)（`GlobalConfig` 第 188 行起）、[`settings/types.ts`](../annotated/src/utils/settings/types.ts)（`SettingsJson` 第 1,153 行）、[`claudemd.ts`](../annotated/src/utils/claudemd.ts) 头部注释。

先记一句反直觉的话：**`theme` 不在 `settings.json` 里，`model` 也不在 `~/.claude.json` 里**。主题是 `GlobalConfig.theme`（[`config.ts`](../annotated/src/utils/config.ts#L202)），默认模型读的是 `settings.model`（[`utils/model/model.ts`](../source/src/utils/model/model.ts#L68-L70)）。

## 9.2 `~/.claude.json`：全局状态文件，不是「设置文件」

### 路径是怎么算出来的

[`utils/env.ts`](../annotated/src/utils/env.ts#L14-L26) 的 `getGlobalClaudeFile()` 只有两条分支：

```ts
if (existsSync(join(getClaudeConfigHomeDir(), '.config.json'))) {
  return join(getClaudeConfigHomeDir(), '.config.json')   // 旧版路径
}
const filename = `.claude${fileSuffixForOauthConfig()}.json`
return join(process.env.CLAUDE_CONFIG_DIR || homedir(), filename)
```

三个结论：

1. 默认就是 `~/.claude.json`（注意：在 home 下，**不在** `~/.claude/` 目录里）。
2. 如果存在旧版的 `~/.claude/.config.json`，优先用它——兼容老用户。
3. 环境变量 `CLAUDE_CONFIG_DIR` 可以把配置目录整体搬走；OAuth 环境不同还会加 `-staging-oauth` 之类的后缀（[`constants/oauth.ts`](../source/src/constants/oauth.ts#L18-L31)）。

### 里面装了什么

`GlobalConfig` 是个扁平大对象，至少混了四类东西（[`config.ts`](../annotated/src/utils/config.ts#L188-L583)）：用户偏好（`theme`、`verbose`、`diffTool`）；按目录存的状态 `projects`，键是项目路径；「这个提示看过没有」的计数器（`numStartups`、`tipsHistory`）；服务端下发数据的缓存（`cachedGrowthBookFeatures`、`cachedStatsigGates`）。

所以它更像「CLI 的持久化状态层」，而不是一份给人手写的配置文件。真正给人写的是下一节的 `settings.json`。

### 它要解决的四个工程问题

写加文件锁（`lockSync`，[`config.ts`](../annotated/src/utils/config.ts#L1178-L1215)）；读走内存缓存 + `mtime` 监视（[#L1065-L1108](../annotated/src/utils/config.ts#L1065-L1108)）；解析失败抛 `ConfigParseError` 并提示最近备份（[#L1453-L1495](../annotated/src/utils/config.ts#L1453-L1495)）；旧字段由 `migrateConfigFields` 幂等迁移（[#L929-L978](../annotated/src/utils/config.ts#L929-L978)）。

还有一个专门防「掉登录」的守卫 `wouldLoseAuthState`（[`config.ts`](../annotated/src/utils/config.ts#L796-L809)）：如果另一个进程刚好把文件写截断，本进程读到默认值，此时**绝不能**把默认值写回去，否则 `oauthAccount` 和 `hasCompletedOnboarding` 就永久丢了。

### 重入保护：为什么需要 `insideGetConfig`

[`config.ts`](../annotated/src/utils/config.ts#L49-L52) 顶部有一个布尔开关：

```ts
// Re-entrancy guard: prevents getConfig → logEvent → getGlobalConfig → getConfig
// infinite recursion when the config file is corrupted.
let insideGetConfig = false
```

它防的是一条真实环路：`getConfig()` 读文件失败 → 想记 analytics 调 `logEvent()` → 判断采样率要读 GrowthBook 特性 → 特性缓存在全局配置里 → `getGlobalConfig()` → 又调 `getConfig()` → 又失败，直到栈溢出。

第二次进入时直接返回兜底默认值，环路被切断。这个模式值得背下来：`if (inside) return default; inside = true; try { ... } finally { inside = false }`。

### `enableConfigs()` 不是「加载 settings.json」

[`config.ts`](../annotated/src/utils/config.ts#L1363-L1386) 的 `enableConfigs()` 只做两件事：

1. 把 `configReadingAllowed` 置为 `true`；
2. 用 `throwOnInvalid = true` 对 `~/.claude.json` 做一次启动自检。

在此之前，任何 `getConfig` 都会抛 `Config accessed before allowed.`（测试环境除外，[`config.ts`](../annotated/src/utils/config.ts#L1458-L1461)）。这是故意的：模块初始化阶段目录探测、环境变量都还没就绪，此时读配置可能读到错的位置。

调用点在入口和初始化链上：[`entrypoints/cli.tsx`](../source/src/entrypoints/cli.tsx#L58) 的各条快速路径、[`entrypoints/init.ts`](../source/src/entrypoints/init.ts#L65)。也就是说，`enableConfigs()` 管的是**全局状态文件的读取闸门**，不是 `settings.json` 的合并。

## 9.3 `settings.json` 的五层来源

设置系统的来源是一个固定数组，顺序就是优先级：**后面的来源压在前面的来源之上**（数组字段例外，见 9.4；出处 [`constants.ts`](../source/src/utils/settings/constants.ts#L7-L22)）。

| 顺序 | `SettingSource` | 路径 | 可写 | 典型内容 |
|:--:|-----------------|------|:--:|----------|
| 1 | `userSettings` | `~/.claude/settings.json`（受 `CLAUDE_CONFIG_DIR` 影响） | 是 | 个人全局偏好 |
| 2 | `projectSettings` | `<cwd>/.claude/settings.json` | 是 | 团队共享的权限、hooks |
| 3 | `localSettings` | `<cwd>/.claude/settings.local.json` | 是 | 个人项目覆盖，通常进 `.gitignore` |
| 4 | `flagSettings` | `--settings <文件>` 或 SDK 内联设置 | 否 | 本次进程的临时覆盖 |
| 5 | `policySettings` | 企业托管（下面单独讲） | 否 | 管理员强制策略 |

另外还有一层不在数组里：**`pluginSettings` 是所有来源的底座**，优先级最低（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L675-L686)）。

两个容易忽略的细节：`--setting-sources` 只接受 `user,project,local` 三个名字（[`constants.ts`](../source/src/utils/settings/constants.ts#L128-L152)），`policySettings` 和 `flagSettings` 永远会被加回来（[`getEnabledSettingSources`](../source/src/utils/settings/constants.ts#L159-L167)）；项目设置的根目录取的是**启动时的原始 cwd**（`getOriginalCwd()`），不是 git 仓库根（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L246-L260)）。

> **验证命令**
> ```
> grep -n "SETTING_SOURCES" -A 18 source/src/utils/settings/constants.ts
> grep -n "parseSettingSourcesFlag" -A 25 source/src/utils/settings/constants.ts
> ```

## 9.4 合并算法：对象深合并，数组「拼接去重」

合并用 lodash 的 `mergeWith`，自定义规则只有一个（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L540-L563)）：

```ts
function mergeArrays(targetArray, sourceArray) {
  return uniq([...targetArray, ...sourceArray])
}
```

翻译成人话：

| 值的类型 | 合并行为 | 后果 |
|----------|----------|------|
| 对象 | lodash 默认深合并 | 两边不同的键都保留 |
| 数组 | 拼接后去重 | **高优先级不能删除低优先级里的条目** |
| 标量（字符串/布尔/数字） | 后者覆盖前者 | 常规「谁后谁赢」 |

这一点非常关键。`permissions.allow` / `deny` 是数组：用户级写了一条 `allow`，项目级再写一条 `allow`，合并结果里两条都在；项目级想「撤销」用户级那条是做不到的。要收紧策略，得加一条 `deny` 规则或靠企业策略，而不是「在后一个文件里删掉它」。数组的拼接语义在 [`settings.ts`](../annotated/src/utils/settings/settings.ts#L553-L563) 的注释里写得很明确。

注意「读」和「写」的规则不同。写回某个来源时（`updateSettingsForSource`），数组是**整体替换**，`undefined` 表示删键（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L423-L429)）。因为写回时调用方已经算好了数组终态，再拼接就会重复。

读设置有四个常用出口（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L320-L328)）：

- `getSettingsForSource(source)`：单个来源的原文，用来查「这一层到底写了什么」（[#L320](../annotated/src/utils/settings/settings.ts#L320)）；
- `getInitialSettings()`：五层合并后的快照，绝大多数业务代码用它（[#L831](../annotated/src/utils/settings/settings.ts#L831)）；
- `getSettingsWithSources()`：合并值 + 各层原文，按优先级排好，给 `/status` 用（[#L858](../annotated/src/utils/settings/settings.ts#L858)）；
- `getSettingsWithErrors()`：合并值 + 校验错误，用来告诉用户「哪一行写错了」（[#L879](../annotated/src/utils/settings/settings.ts#L879)）。

> 验证：`grep -n "function mergeArrays" -A 4 source/src/utils/settings/settings.ts`

## 9.5 企业策略：`policySettings` 是「首个源胜出」

普通来源是**逐层合并**，企业策略不是。它先在四类候选源里挑出**第一个有内容的**，只把这一份接进合并链（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L692-L757)）：

| 优先级 | 来源 | 位置 | 谁能写 |
|:--:|------|------|--------|
| 1 | 远程托管 | [`services/remoteManagedSettings/`](../source/src/services/remoteManagedSettings/) 的缓存 | 服务端下发 |
| 2 | MDM（macOS plist / Windows HKLM） | `/Library/Managed Preferences/…`、`HKLM\SOFTWARE\Policies\ClaudeCode` | 管理员 / root |
| 3 | 受管文件 | `managed-settings.json` + `managed-settings.d/*.json` | 管理员 |
| 4 | HKCU | `HKCU\SOFTWARE\Policies\ClaudeCode` | 当前用户 |

「首个源胜出」的含义是：只要远程有内容，MDM 和受管文件里的策略**整份都不参与**；不是四份取并集。`mdm/settings.ts` 的头部注释和第 237 行的 [`consumeRawReadResult`](../annotated/src/utils/settings/mdm/settings.ts#L237) 把这个短路顺序写死了。

### 三个平台的落点

`getManagedFilePath()` 按平台返回受管目录（[`managedPath.ts`](../source/src/utils/settings/managedPath.ts#L9-L28)）：

| 平台 | 受管目录 | MDM 通道 |
|------|----------|----------|
| macOS | `/Library/Application Support/ClaudeCode` | `com.anthropic.claudecode` 的 plist，读 `/Library/Managed Preferences/` 下的设备级与用户级文件 |
| Windows | `C:\Program Files\ClaudeCode` | 注册表 `HKLM` / `HKCU` 下的 `SOFTWARE\Policies\ClaudeCode` |
| Linux | `/etc/claude-code` | 无 MDM，只能读受管文件 |

macOS 的 plist 路径与 Windows 的注册表键定义在 [`mdm/constants.ts`](../source/src/utils/settings/mdm/constants.ts#L9-L31)。

### 受管文件内部还有一层「基文件 + drop-in」

`managed-settings.json` 先作为底座，然后 `managed-settings.d/` 下的 `.json` 按**文件名字典序**依次覆盖，后到者胜（[`settings.ts`](../annotated/src/utils/settings/settings.ts#L63-L122)）。这套约定照搬 systemd / sudoers，让不同团队各发 `10-otel.json`、`20-security.json` 而不抢同一个文件。

### 为什么 MDM 要单独一个模块

读 plist 和注册表要起子进程（`plutil`、`reg query`），不能像读 JSON 那样同步完成。所以启动时先在 [`main.tsx`](../source/src/main.tsx#L16) 模块求值阶段 `startMdmRawRead()`，让子进程与模块加载并行；第一次读设置前再 `ensureMdmSettingsLoaded()` 等结果（[`main.tsx`](../source/src/main.tsx#L914)）。运行中没法用文件事件监听注册表，于是 `changeDetector` 每 30 分钟轮询一次（[`changeDetector.ts`](../annotated/src/utils/settings/changeDetector.ts#L47-L53)）。

远程托管设置还多一道人工闸：如果新下发的设置里出现「危险项」且与上次不同，会弹阻塞对话框让用户确认；拒绝就退出（[`securityCheck.tsx`](../source/src/services/remoteManagedSettings/securityCheck.tsx#L17-L71)）。从代码看，它防的是「管理员配置静默扩大权限」，不是防中间人。

## 9.6 一个设置从改完到生效

流程是：① 编辑 `settings.json` → ② `changeDetector` 发现变化（等写入稳定 1 秒）→ ③ `resetSettingsCache()` 清掉三层缓存 → ④ `applySettingsChange()` 重读设置 → ⑤ 重载权限规则与 hooks 快照，推进 `AppState`。

关键参数都在 [`changeDetector.ts`](../annotated/src/utils/settings/changeDetector.ts)：

| 常量 | 值 | 作用 |
|------|----|------|
| `FILE_STABILITY_THRESHOLD_MS` | 1,000 | 等文件写完再处理，避免读到半截 JSON |
| `INTERNAL_WRITE_WINDOW_MS` | 5,000 | 自己刚写完的 5 秒内不弹「设置被外部修改」通知 |
| `MDM_POLL_INTERVAL_MS` | 30 分钟 | 注册表/plist 无法监听，只能轮询 |

第 ⑤ 步落在 [`applySettingsChange.ts`](../source/src/utils/settings/applySettingsChange.ts#L33-L62)：它重新读 `getInitialSettings()`，再 `loadAllPermissionRulesFromDisk()`、`updateHooksConfigSnapshot()`，最后把新设置和新的权限上下文一起推进 `AppState`。

`--settings <文件>` 走的是另一条路：启动时把路径记进 `flagSettingsPath`，然后 `resetSettingsCache()`（[`main.tsx`](../source/src/main.tsx#L475-L479)）。这条来源只读，且优先级高于项目与本地设置。

## 9.7 `settings.json` 里到底能写什么

顶层 schema 在 [`SettingsSchema`](../annotated/src/utils/settings/types.ts#L272)，字段全部可选；顶层用了 `.passthrough()`，所以 schema 不认识的键不会被丢掉（[`types.ts`](../annotated/src/utils/settings/types.ts#L1117-L1118)）。下面是已核实的常用字段：

| 字段 | 类型 | 作用 | 出处 |
|------|------|------|------|
| `$schema` | 字符串字面量 | 编辑器补全用的 JSON Schema 地址 | [`types.ts`](../annotated/src/utils/settings/types.ts#L274-L278) |
| `apiKeyHelper` | 字符串 | 输出认证信息的脚本路径 | [#L280](../annotated/src/utils/settings/types.ts#L280) |
| `cleanupPeriodDays` | 非负整数 | 对话记录保留天数，`0` 关闭持久化 | [#L344](../annotated/src/utils/settings/types.ts#L344) |
| `env` | 字符串键值对 | 注入会话的环境变量，值会被强制转字符串 | [#L352](../annotated/src/utils/settings/types.ts#L352) |
| `permissions` | 对象 | `allow` / `deny` / `ask` / `defaultMode` | [#L394](../annotated/src/utils/settings/types.ts#L394) |
| `model` | 字符串 | 覆盖默认模型 | [#L397](../annotated/src/utils/settings/types.ts#L397) |
| `availableModels` | 字符串数组 | 企业允许的模型白名单 | [#L401](../annotated/src/utils/settings/types.ts#L401) |
| `hooks` | 对象 | 工具执行前后运行的自定义命令 | [#L460](../annotated/src/utils/settings/types.ts#L460) |
| `disableAllHooks` | 布尔 | 关闭所有 hook 与状态栏 | [#L485](../annotated/src/utils/settings/types.ts#L485) |
| `allowManagedHooksOnly` | 布尔 | 只允许受管设置里的 hook | [#L500](../annotated/src/utils/settings/types.ts#L500) |
| `enabledPlugins` | 对象 | `插件名@市场名` → 是否启用 | [#L590](../annotated/src/utils/settings/types.ts#L590) |
| `language` | 字符串 | 回复语言 | [#L678](../annotated/src/utils/settings/types.ts#L678) |

一个能直接放进 `.claude/settings.json` 的例子（字段均来自上面这张表）：

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "opus",
  "env": { "DEBUG": "true" },
  "permissions": {
    "allow": ["Bash(npm:*)", "Read"],
    "deny": ["Bash(rm -rf:*)"]
  },
  "enabledPlugins": { "formatter@anthropic-tools": true }
}
```

权限规则的写法在源码里有现成示例：`Bash(npm:*)`、`Edit(.claude)`、`Read`（[`skills/bundled/updateConfig.ts`](../source/src/skills/bundled/updateConfig.ts#L30-L40)）。

还有两条校验细节：

- 解析时**先过滤非法权限规则，再跑 schema**，避免一条坏规则让整份文件作废（文件解析在 [`settings.ts`](../annotated/src/utils/settings/settings.ts#L223-L240)，MDM 解析在 [`mdm/settings.ts`](../annotated/src/utils/settings/mdm/settings.ts#L190-L211)）。
- 非法字段「不生效但留在文件里」，让用户自己修（[`types.ts`](../annotated/src/utils/settings/types.ts#L225-L255) 的向后兼容声明）。

## 9.8 另一条线：`CLAUDE.md` 的四类记忆

`CLAUDE.md` 不是设置来源，不会被合进 `SettingsJson`；它是**拼进提示词的自然语言文本**。四条装载线按「从外到内」排列，后加载的优先级更高（模型对靠后的内容注意力更强）：

| 顺序 | 类型 | 路径 | 受哪个设置源控制 |
|:--:|------|------|------------------|
| 1 | `Managed` | `<受管目录>/CLAUDE.md` | 始终加载 |
| 2 | `User` | 默认 `~/.claude/CLAUDE.md`（受 `CLAUDE_CONFIG_DIR` 影响） | `userSettings` 开启时 |
| 3 | `Project` | `<cwd>/CLAUDE.md`、`<cwd>/.claude/CLAUDE.md`、`.claude/rules/*.md` | `projectSettings` 开启时 |
| 4 | `Local` | `<cwd>/CLAUDE.local.md` | `localSettings` 开启时 |

路径由 `getMemoryPath()` 决定（[`config.ts`](../annotated/src/utils/config.ts#L1825-L1846)），装载入口是 [`getMemoryFiles()`](../annotated/src/utils/claudemd.ts#L813-L880)。文件头注释把规则写全了（[`claudemd.ts`](../annotated/src/utils/claudemd.ts#L1-L27)）：

- `Project` 与 `Local` 从 cwd 逐级向上走到根，**越靠近 cwd 越晚加载**；
- `@include` 只在叶子文本节点生效，代码块里不算；
- `Managed` 与自动记忆**永不可被 `claudeMdExcludes` 排除**，排除项只对 `User` / `Project` / `Local` 生效（[`isClaudeMdExcluded`](../annotated/src/utils/claudemd.ts#L564-L591)）。

一句话边界：**`settings.json` 决定「程序怎么运行」，`CLAUDE.md` 决定「模型被告知什么」**。前者是结构化配置，后者是文本，不要把权限规则写进 `CLAUDE.md` 就以为能生效。

> 验证路径分派：`grep -n "case 'Managed'\|case 'User'\|case 'Project'\|case 'Local'" -A 1 annotated/src/utils/config.ts`

## 9.9 一张「谁赢」的决策表

| 场景 | 结果 | 依据 |
|------|------|------|
| 用户级和项目级都写了 `model` | 项目级赢（后合并） | `SETTING_SOURCES` 顺序 |
| 项目级和 `--settings` 都写了 `model` | `--settings` 赢 | `flagSettings` 在 `projectSettings` 之后 |
| 前四层任意一层和企业策略都写了 `model` | 企业策略赢 | `policySettings` 最后合并 |
| 远程托管和本地受管文件都有策略 | 远程赢，且本地整份不参与 | 「首个源胜出」 |
| 用户级和项目级都写了 `permissions.allow` | 两条都在，不是后者替换前者 | 数组拼接去重 |
| 用户级 `CLAUDE.md` 和项目级 `CLAUDE.md` 内容冲突 | 项目级更靠后，模型更可能听它 | 记忆装载顺序 |

最后一行要谨慎：`CLAUDE.md` 的「优先级」是**提示词顺序**，不是程序层面的硬覆盖。两条相反的指令同时存在时，模型仍可能摇摆；真正需要强制执行的规则，应该写成 `settings.json` 的权限规则或 hook。

## 9.11 合书自测（不翻书写出答案才算过）

1. `~/.claude.json` 和 `~/.claude/settings.json` 各管什么？`theme` 和 `model` 分别存在哪？
2. 用户级、项目级、本地级、`--settings`、企业策略，五层的合并顺序是什么？`--setting-sources` 能关掉企业策略吗？
3. 两个来源都写了 `permissions.allow`，合并结果是「后者替换前者」还是「两条都在」？为什么？
4. 企业策略的四类来源为什么叫「首个源胜出」？远程有内容时，本地 `managed-settings.json` 还会生效吗？
5. `enableConfigs()` 到底加载了什么？在它被调用之前读配置会发生什么？
6. `CLAUDE.md` 的四类记忆按什么顺序装载？`claudeMdExcludes` 能排除企业级的 `Managed` 吗？

<details><summary>参考答案（点开）</summary>

1. `~/.claude.json` 是 `GlobalConfig`，存主题、安装方式、项目信任、计数器、服务端缓存；`~/.claude/settings.json` 是 `SettingsJson`，存模型、权限、hooks、env、插件。`theme` 在 `GlobalConfig.theme`，`model` 在 `settings.model`。
2. `userSettings → projectSettings → localSettings → flagSettings → policySettings`，后者覆盖前者。不能：`--setting-sources` 只接受 `user,project,local`，`getEnabledSettingSources()` 会把 `policySettings` 和 `flagSettings` 永远加回来。
3. 两条都在。`settingsMergeCustomizer` 对数组走 `uniq([...target, ...source])`，是拼接去重；所以高优先级文件不能靠「不写」来删除低优先级数组里的条目。
4. 因为它在远程、MDM、受管文件、HKCU 里只挑第一个非空的来源，整份接入，不做四份合并。远程有内容时，本地 `managed-settings.json` 整份都不参与。
5. 只做两件事：打开 `configReadingAllowed` 开关，并对 `~/.claude.json` 做一次 `throwOnInvalid = true` 的启动自检。它不加载 `settings.json`。在它之前读配置会抛 `Config accessed before allowed.`。
6. `Managed → User → Project → Local`，后加载的优先级更高（提示词里更靠后）。不能：`isClaudeMdExcluded` 只对 `User` / `Project` / `Local` 生效，`Managed` 永不可排除。

</details>
