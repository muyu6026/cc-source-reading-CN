### ⚠️ 一个必须先知道的事实：8 个纯类型模块不存在

这份源码是**打包产物**的回推，`src/types/` 下有 8 个被大量引用的文件**并没有出现在仓库里**（本地克隆与 GitHub 远端一致，不是克隆遗漏）：

| 缺失文件 | 被引用次数 | 备注 |
|----------|-----------|------|
| `src/types/message.ts` | 75 | 全项目缺失最多的一个（`Message` / `UserMessage` / `AssistantMessage`…） |
| `src/types/tools.ts` | 3 | `ToolProgressData`、各 `*Progress` |
| `src/types/utils.ts` | 2 | `DeepImmutable` |
| `src/types/connectorText.ts` | 2 | |
| `src/types/fileSuggestion.ts` | 2 | |
| `src/types/messageQueueTypes.ts` | 2 | |
| `src/types/statusLine.ts` | 2 | |
| `src/types/notebook.ts` | 1 | |

**为什么不影响阅读**：这些 import 全是 `import type`，编译期被整段擦除，运行时不需要这些文件。所以打包能过、程序能跑。

**根因（已用 `source/cli.js.map` 验证）**：这份 `src/` 不是从代码仓库导出的，而是从 `cli.js.map` 的 `sourcesContent` 字段**反向提取**出来的。sourcemap 只记录**真正被打进 bundle 的模块**，而 `import type` 在编译期被整段擦除、不产生任何运行时代码，因此这些文件从未进入 `cli.js`，自然也不会出现在 `sources` 数组里。

| 验证项 | 结果 |
|--------|------|
| `cli.js.map` 的 `sources` 中 `../src/*` 条目数 | **1902**，与 `source/src` 的文件数完全一致 |
| 上表 8 个文件在 `sources` 中的命中数 | 6 个为 **0**；`fileSuggestion` / `notebook` 命中的是 `src/hooks/fileSuggestions.ts`、`src/utils/notebook.ts`，并非缺失的那两个 |
| 取 `src/Tool.ts` 全文与 `sourcesContent` 比对 | **逐字命中**（29,456 字符完整存在） |

结论：这些文件不是"被谁删了"，而是**打包时它们根本没产生代码**。

**会有什么影响**：

- 直接 `tsc` 会报一堆 `Cannot find module`
- 阅读时"跳转到定义"会失败（例如 `Tool.ts` 里的 `DeepImmutable<T>` 展不开，只能按用法推断为"递归 readonly"）
- 想知道某个类型长什么样，只能**从调用处的字面量结构反推** —— 这也是本手册里很多类型说明写成"结构看起来是…"的原因

> 这块对理解架构帮助最小，**除非你要做终端 UI，否则可以先跳**。

## 2.5 怎么用这张表
- **想找某个功能**：按中文含义反查英文目录。比如"埋点在哪"→ `analytics/`。
- **想评估工作量**：文件数越多越复杂。`utils/`（564）和 `components/`（389）是最难啃的，初学先别碰。
- **想找入口**：`entrypoints/`、`main.tsx`、`setup.ts`、`tools.ts`、`commands.ts` 这几个是"总闸"。
