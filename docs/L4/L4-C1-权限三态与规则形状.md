## 2. 精读正文（一）：三态——allow / deny / ask

```ts
40 │ // ============================================================================
41 │ // Permission Behaviors
42 │ // ============================================================================
43 │
44 │ export type PermissionBehavior = 'allow' | 'deny' | 'ask'
```

这就是 [L0-06](../L0/L0-06-联合类型三值状态机.md) 引用过的那一行（原文第 44 行）。441 行的文件，主角只有这一行——其余 436 行都是它的「周边配套」。

三个值的语义，不看文档、看**结果类型的字段差异**最准：

| 行为 | 结果类型（行号） | 必填字段 | 说明 |
| --- | --- | --- | --- |
| `allow` | `PermissionAllowDecision`（174–184） | `behavior: 'allow'` | 连 `message` 都不要——放行不需要理由文案 |
| `ask` | `PermissionAskDecision`（199–226） | `behavior: 'ask'`、`message` | 弹框必须告诉用户「在问什么」，还能带 `suggestions`（「允许并记住」的候选规则） |
| `deny` | `PermissionDenyDecision`（231–236） | `behavior: 'deny'`、`message`、**`decisionReason`（必填）** | 拒绝必须给得出原因 |

注意 `deny` 的 `decisionReason` **没有问号**，而 allow/ask 的都有：

```ts
174 │ export type PermissionAllowDecision<
175 │   Input extends { [key: string]: unknown } = { [key: string]: unknown },
176 │ > = {
177 │   behavior: 'allow'
178 │   updatedInput?: Input
179 │   userModified?: boolean
180 │   decisionReason?: PermissionDecisionReason
181 │   toolUseID?: string
182 │   acceptFeedback?: string
183 │   contentBlocks?: ContentBlockParam[]
184 │ }
```

对比 deny（231–236 行）：`decisionReason: PermissionDecisionReason`——**必填**。类型系统在替产品说话：放行可以无声，拒绝必须可解释。

三个类型再用一个联合装起来（241–246 行）：

```ts
241 │ export type PermissionDecision<
242 │   Input extends { [key: string]: unknown } = { [key: string]: unknown },
243 │ > =
244 │   | PermissionAllowDecision<Input>
245 │   | PermissionAskDecision<Input>
246 │   | PermissionDenyDecision
```

这就是 L0-6 讲的「判别联合」实战：下游 `switch (result.behavior)` 时，每个分支自动收窄到对应类型，deny 分支里 `decisionReason` 保证不是 undefined。

还有第四个值吗？有，但它是**变体**不是行为——`passthrough`（251–266 行）：「工具自己没意见，交给上层定」。它不在 `PermissionBehavior` 三态里，因为三态是**最终裁决**，passthrough 只是中间态，最后会被转成 ask（下一课 C-2 的步骤 3 就干这件事）。

## 3. 精读正文（二）：规则的形状

一条规则长什么样？分三层：

**第一层，规则从哪来**（54–62 行）：

```ts
54 │ export type PermissionRuleSource =
55 │   | 'userSettings'
56 │   | 'projectSettings'
57 │   | 'localSettings'
58 │   | 'flagSettings'
59 │   | 'policySettings'
60 │   | 'cliArg'
61 │   | 'command'
62 │   | 'session'
```

8 种来源。前五种对应设置文件体系，后三种是临时的（命令行参数、命令注入、会话内存）。记住一个区别：**policySettings 是企业策略，只读**——下一课会看到删除这类来源的规则会直接抛错。

**第二层，规则管谁**（67–70 行）：

```ts
67 │ export type PermissionRuleValue = {
68 │   toolName: string
69 │   ruleContent?: string
70 │ }
```

`ruleContent` 是可选的。这一行可选，就是「整工具规则」与「内容级规则」的分水岭：

- `Bash`（无内容）→ 管住整个 Bash 工具；
- `Bash(npm install)` → 只管 `npm install` 这一条命令。

用户写的是**字符串**，代码里是**对象**。字符串怎么变成对象？看解析器（permissionRuleParser.ts 第 93–101 行，此文件也无批注版）：

```ts
 93 │ export function permissionRuleValueFromString(
 94 │   ruleString: string,
 95 │ ): PermissionRuleValue {
 96 │   // Find the first unescaped opening parenthesis
 97 │   const openParenIndex = findFirstUnescapedChar(ruleString, '(')
 98 │   if (openParenIndex === -1) {
 99 │     // No parenthesis found - this is just a tool name
100 │     return { toolName: normalizeLegacyToolName(ruleString) }
101 │   }
```

找到第一个未转义的 `(`，拆出工具名与括号内容。几个边界情况都在同一个函数里兜底：`Bash()` 空括号、`Bash(*)` 星号，都视作整工具规则（131–135 行注释写明）。括号本身可以被 `\(` `\)` 转义（55–60 行的 `escapeRuleContent`），所以命令里含括号也不会拆错。

**第三层，三件套合体**（75–79 行）：

```ts
75 │ export type PermissionRule = {
76 │   source: PermissionRuleSource
77 │   ruleBehavior: PermissionBehavior
78 │   ruleValue: PermissionRuleValue
79 │ }
```

来源 + 行为 + 值，一条规则就是这三个字段的组合。`ruleBehavior` 正是第一节的 `PermissionBehavior`——**三态是规则的属性之一**。

## 4. 精读正文（三）：规则怎么被解析、匹配、装进判定

### 4.1 从 context 到规则数组

规则在 context 里按「来源」分组存成字符串数组（types/permissions.ts 第 427–441 行的 `ToolPermissionContext`，其中三张表最关键）：

```ts
433 │   readonly alwaysAllowRules: ToolPermissionRulesBySource
434 │   readonly alwaysDenyRules: ToolPermissionRulesBySource
435 │   readonly alwaysAskRules: ToolPermissionRulesBySource
```

`ToolPermissionRulesBySource`（419–421 行）是 `{ [T in PermissionRuleSource]?: string[] }`——按 8 种来源分组的字符串数组。**allow、deny、ask 分三张表存，而不是一张表里每条规则带 behavior 字段**。permissions.ts 第 227 行批注一针见血：这样「判定顺序完全由代码结构决定，不依赖数据里的字段」——deny 的优先级是写在代码里的，规则数据再乱也改变不了。

读取侧是三个同构函数（annotated/src/utils/permissions/permissions.ts 第 219–227 行）：

```ts
219 │ export function getDenyRules(context: ToolPermissionContext): PermissionRule[] {
220 │   return PERMISSION_RULE_SOURCES.flatMap(source =>
221 │     (context.alwaysDenyRules[source] || []).map(ruleString => ({
222 │       source,
223 │       ruleBehavior: 'deny',
224 │       ruleValue: permissionRuleValueFromString(ruleString),
225 │     })),
226 │   )
227 │ }
```

每次调用都把字符串**重新解析**成 `PermissionRule` 对象（第 137 行批注：调用方多、规则少，不做缓存）。`ruleBehavior: 'deny'` 在这里写死——从哪张表读出来，行为就是什么。

### 4.2 规则怎么匹配工具

```ts
246 │ function toolMatchesRule(
247 │   tool: Pick<Tool, 'name' | 'mcpInfo'>,
248 │   rule: PermissionRule,
249 │ ): boolean {
250 │   // Rule must not have content to match the entire tool
251 │   if (rule.ruleValue.ruleContent !== undefined) {
252 │     return false
253 │   }
```

`toolMatchesRule` 只管**整工具级**匹配：规则带内容（`Bash(npm install)`）就直接返回 false——内容级匹配是工具自己的 `checkPermissions` 的事（下一课的步骤 1c）。剩下的是名字比对 + MCP 服务器级通配（`mcp__server1` 管整个服务器，`mcp__server1__*` 管其下全部工具，264–276 行）。

### 4.3 装进一次判定

最后是三个查询器（297–313 行），它们是「规则」与「判定」之间的桥：

```ts
297 │ export function getDenyRuleForTool(
298 │   context: ToolPermissionContext,
299 │   tool: Pick<Tool, 'name' | 'mcpInfo'>,
300 │ ): PermissionRule | null {
301 │   return getDenyRules(context).find(rule => toolMatchesRule(tool, rule)) || null
302 │ }
```

返回**命中的规则本身**而不是布尔值（第 289 行批注：上层要把规则写进 `decisionReason`，UI 才能告诉用户「是哪一条规则放行/拦截的」）。它们正是下一课流水线的步骤 1a / 1b / 2b 调用的函数。

于是「装进判定」的完整链条是：

```
设置文件里的字符串 "Bash(npm install)"
  → 按来源分组存进 ToolPermissionContext 的三张表（types 427–441）
  → getDenyRules / getAskRules / getAllowRules 解析成 PermissionRule（219–235）
  → toolMatchesRule 判「整工具」命中（246–277）
  → getDenyRuleForTool 等查询器返回命中的规则（297–313）
  → 流水线把它包进 { behavior, decisionReason: { type: 'rule', rule } }（下一课）
```

## 5. 核心问题（路线图 C-1 卡片）

**卡片原文**：「三态 + 规则的形状（L0-6 那一行的完整上下文）」。

完整解答：

1. **三态是什么**：`PermissionBehavior = 'allow' | 'deny' | 'ask'`（types 第 44 行）。allow 放行（可不解释）、ask 弹框（必须带 message 与候选规则）、deny 拒绝（必须带 decisionReason）。另有 passthrough 中间态（251–266 行），不属于三态，最终转 ask。
2. **规则长什么样**：`PermissionRule = { source, ruleBehavior, ruleValue }`（75–79 行）；ruleValue 是 `{ toolName, ruleContent? }`（67–70 行），无内容管整工具、有内容管具体操作（Bash 前缀命令就是内容级规则）；来源有 8 种（54–62 行）。
3. **怎么解析**：字符串 `Bash(npm install)` 经 `permissionRuleValueFromString` 按第一个未转义 `(` 拆开，`Bash()` / `Bash(*)` 兜底为整工具。
4. **怎么匹配**：整工具级由 `toolMatchesRule` 判（带内容的规则直接 false）；内容级由各工具自己的 `checkPermissions` 判。
5. **怎么装进判定**：三张按来源分组的表存进 `ToolPermissionContext`，读取时展开成规则数组、查命中、连同规则本身写进判定结果的 `decisionReason`。
6. **三态与模式的区别**：第 16–29 行的 `PermissionMode`（default / acceptEdits / plan / bypassPermissions / dontAsk…）是「怎么审」的宏观档位，`PermissionBehavior` 是「单次审出什么」的微观结果。[L0-06](../L0/L0-06-联合类型三值状态机.md) 末尾那条对照（`type PermissionMode` 在第 29 行）说的就是别把两者混为一谈。

## 6. 常见误读

**误读一：「Bash(npm install) 这条规则在 types/permissions.ts 里定义了 Bash 前缀匹配」。**
这个文件只定义了规则的**形状**（`ruleContent?: string`），完全不知道「Bash 前缀匹配」是什么。前缀匹配的逻辑在 BashTool 自己的 `checkPermissions` 里（`annotated/src/tools/BashTool/bashPermissions.ts`），通用类型文件对具体工具一无所知——这正是它敢自称「Pure type definitions」的原因（头注第 2 行）。

**误读二：「PermissionDecision 就是三态，所以共三个分支」。**
漏了 passthrough（251–266 行）。`PermissionResult`（254 行）= 三态联合 + passthrough 变体，是**四种**。初学最疼的一次是发现某个函数返回 `PermissionResult`，写 switch 只处理三个 case，passthrough 悄悄漏过去。

**误读三：「规则带 behavior 字段，所以一条 deny 规则可能被数据改成 allow」。**
反了。规则在存储层就分三张表（`alwaysAllowRules` / `alwaysDenyRules` / `alwaysAskRules`），`ruleBehavior` 是**读出来时按表写死**的（224 行 `'deny'` 字面量），不是从数据里读的。deny 优先于 allow 是代码结构保证的，不是数据保证的。

## 8. 合书自测

1. `PermissionBehavior` 定义在原文第几行？三个值各自的「必填字段」差异是什么？
2. 为什么 `PermissionDenyDecision` 的 `decisionReason` 没有问号而 allow 的有？
3. `PermissionRule` 的三个字段分别是什么？`ruleContent?: string` 的可选性对应了哪两类规则？
4. 规则在 context 里是怎么存储的？为什么分三张表而不是一张表带 behavior 字段？
5. `toolMatchesRule` 遇到 `Bash(npm install)` 这样的规则时返回什么？为什么？内容级规则由谁负责匹配？
6. `passthrough` 为什么不放进 `PermissionBehavior` 三态里？它的最终归宿是什么？

<details><summary>1. 三态定义与必填字段差异</summary>

第 44 行。allow 只必填 `behavior`（放行无需解释，连 message 都不要）；ask 必填 `behavior` + `message`（弹框要说清在问什么，还可带 suggestions）；deny 必填 `behavior` + `message` + `decisionReason`（拒绝必须给得出原因，且类型上保证非空）。</details>

<details><summary>2. decisionReason 的问号差异</summary>

类型系统替产品立规矩：放行可以无声无息，拒绝必须可解释——UI 会把 `decisionReason` 展示给用户。ask 保留可选是因为有些 ask 来自默认兜底而非具体规则。</details>

<details><summary>3. PermissionRule 三字段与两类规则</summary>

`source`（8 种来源之一）、`ruleBehavior`（三态之一）、`ruleValue`（toolName + 可选 ruleContent）。ruleContent 缺省 = 整工具规则（如 `Bash`）；ruleContent 存在 = 内容级规则（如 `Bash(npm install)` 这类前缀/路径规则）。</details>

<details><summary>4. 存储结构与为什么分三张表</summary>

按 `PermissionRuleSource` 分组的字符串数组：`alwaysAllowRules` / `alwaysDenyRules` / `alwaysAskRules`（types 第 433–435 行），类型为 `ToolPermissionRulesBySource`（419–421 行）。分三张表后，`ruleBehavior` 在读取时按表写死，deny 与 allow 的判定优先级由**代码结构**（先查哪张表）决定，不依赖任何数据字段——数据再乱也翻不了优先级。</details>

<details><summary>5. toolMatchesRule 对内容级规则的态度</summary>

返回 false（第 251–253 行：`ruleContent !== undefined` 直接 false）。它只负责「整工具」级匹配；内容级（前缀、路径）由各工具自己的 `checkPermissions` 在流水线步骤 1c 里判定，通用类型层不掺和具体工具的匹配语义。</details>

<details><summary>6. passthrough 的身份与归宿</summary>

它不是最终裁决而是**中间态**——「工具自己没意见，交给上层定」，所以不配进三态联合。归宿：流水线末尾（下一课步骤 3）被转换成 ask，并用工具给出的 decisionReason 重新生成提示文案。</details>
