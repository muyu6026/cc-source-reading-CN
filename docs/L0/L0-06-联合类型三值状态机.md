## 1. 先看这一行

```ts
export type PermissionBehavior = 'allow' | 'deny' | 'ask'
```

出处：`source/src/types/permissions.ts` 第 44 行。上面第 40–42 行是一段注释分隔条：

```ts
// ============================================================================
// Permission Behaviors
// ============================================================================
```

**这行定义的是「一次权限判定的结局」**。整个项目里，任何工具调用要问「这个操作能不能做」，最终只能落到三种答案之一：允许、拒绝、询问用户。它不是一句口号——`allow` / `deny` / `ask` 这三个词会在权限规则、SDK 协议、界面文案里反复出现。

**规模感**：这行只有 5 个词，却是全仓 29 处引用的源头；而**定义点只有这一个**（第 5 节验证）。改这一行，等于改整个权限系统的对外契约。

## 2. 精读正文（逐行）

### 2.1 第 44 行：拆成六段念

```ts
export type PermissionBehavior = 'allow' | 'deny' | 'ask'
```

| 片段 | 念法 |
| --- | --- |
| `export` | 「这个类型给别的文件用」 |
| `type` | 「我要**发明一个新类型**，不是定义一个变量」 |
| `PermissionBehavior` | 新类型的名字（首字母大写是约定，表示「这是类型」） |
| `=` | 「它等于右边这个东西」——注意这里是**类型层面**的等于，不是赋值 |
| `'allow' \| 'deny' \| 'ask'` | 三个**字符串字面量类型**，用 `\|` 连起来 |
| `\|` | 读作「**或**」 |

**整句念法**：「导出一个叫 `PermissionBehavior` 的类型，它只能是 `allow`、`deny` 或 `ask` 三者之一。」

### 2.2 三个关键区别

**① `type` 不是 `const`**

`export const X = 'allow'` 是在内存里造一个值；`export type X = ...` 只在编译期存在，**编译成 JS 后整行消失**。所以这行不是「定义了一个字符串变量」，是「给编译器立了一条规矩」。

**② `'allow'` 是「字面量类型」，不是变量名**

带引号的 `'allow'` 在类型位置出现时，意思是「**只能是这个确切的字符串**」。所以下面两种写法完全不同（教学示例，不在仓库里）：

```ts
let a: string = 'allow'      // 类型是 string，将来可以改成任何字符串
let b: PermissionBehavior = 'allow'   // 类型只允许三个值
```

**③ `|` 是「并集」，不是「或者随便挑」**

它的意思是「取值范围 = 左边集合 ∪ 右边集合」。三个字符串拼起来，取值范围就是三个元素——多一个不行，少一个也不行。

### 2.3 它怎么当「参数类型」用（原文第 349–353 行）

```ts
export function getRuleByContentsForTool(
  context: ToolPermissionContext,
  tool: Tool,
  behavior: PermissionBehavior,
): Map<string, PermissionRule> {
```

第 352 行 `behavior: PermissionBehavior` —— 这里就把新类型当普通类型用了。**念法**：「`behavior` 这个参数只接受三种值之一」。

好处立刻显现：函数体里对 `behavior` 做分支时，编译器知道只有三种可能，不会漏、也写不出第四种。

### 2.4 三种结局怎么被「用尽」（原文第 369–379 行）

```ts
  switch (behavior) {
    case 'allow':
      rules = getAllowRules(context)
      break
    case 'deny':
      rules = getDenyRules(context)
      break
    case 'ask':
      rules = getAskRules(context)
      break
  }
```

这是联合类型最典型的消费方式：**一个 `case` 对一个值，正好三个**。

**注意这里没有 `default`**。这不是疏忽——类型只有三个成员，三个 `case` 就穷尽了所有可能，`default` 是死代码。反过来说，**哪天有人往第 44 行加了第四个值**：这个 `switch` 会静默地什么都不做（`rules` 保持上面的空数组），而展示层的 `getRuleBehaviorLabel`（`PermissionRuleList.tsx` 第 63–72 行）因为**没有兜底 `return`** 会直接编译报错——**类型改动的第一道警报，往往就来自这类穷尽性 `switch`**。

### 2.5 它怎么当「数组元素类型」用（第 1434、1459 行）

```ts
    const behaviors: PermissionBehavior[] = ['allow', 'deny', 'ask']
```

`PermissionBehavior[]` 读作「装 `PermissionBehavior` 的数组」。这里作者把三个值**枚举了一遍**，用来做「对每种行为都执行一次」的批量清理。

```ts
    for (const behavior of ['allow', 'deny', 'ask'] as PermissionBehavior[]) {
```

第 1459 行换了写法：数组字面量后面跟 `as PermissionBehavior[]`，意思是「我断言这个数组的元素就是这三种」。`as` 是**断言**，不是检查——写错了编译器不会拦（这一点在 L0-09 之外的课时再展开，这里只需认得）。

两种写法的差别：前者靠**注解**让编译器校验每个元素；后者靠**断言**让编译器闭嘴。前者更安全。

### 2.6 类型消失了，运行时靠什么（第 252–254 行）

```ts
export const PermissionBehaviorSchema = lazySchema(() =>
  z.enum(['allow', 'deny', 'ask']),
)
```

这是同一个三值集合的**第二份定义**，用 zod 写的。为什么需要两份：

- TypeScript 的类型**编译后不存在**，外部传进来的 JSON（SDK 调用、配置文件的 `permissions` 字段）在运行时是裸数据；
- `z.enum([...])` 是**运行时**真的会执行的校验，值不在里面就报错；
- 于是形成双保险：**静态**靠 `PermissionBehavior`，**动态**靠 `PermissionBehaviorSchema`。

**代价**：加第四个值时，两处都要改。这不是冗余设计，是「编译期」和「运行期」本来就活在两个世界。

## 3. 三个问题（路线图 L0-6 卡片）

### 问题 1：为什么不用 `string`，而要写死三个值？

因为 `string` 允许的值是**无穷多个**，而权限判定的结局**只有三个**。用 `string` 会丢掉四样东西：

| 丢掉的东西 | 具体后果 |
| --- | --- |
| 拼写检查 | 写成 `'alow'` 编译期不报错，运行到某个分支才「什么都没发生」 |
| 穷尽性 | `switch` 少写一个 `case`，编译器不会提醒你 |
| 文档性 | 看到 `behavior: string`，读者得翻遍全仓才知道有哪几种 |
| 重构安全 | 想把 `ask` 改名成 `prompt`，全局搜索靠字符串，容易漏 |

写死三个值之后，**非法状态在编译期就不可表达**。这是本项目权限系统最基础的一道防线：能写出来的 `PermissionBehavior`，一定是三种之一。

反过来说，代价也要认：**新增一种结局要改多处**（定义 + zod + 每个 `switch`）。这个代价是故意的——权限变更本来就该被强制过一遍所有分支。

### 问题 2：`|` 这个符号读什么？

读「**或**」，准确说是「**或（取其一）**」。

```ts
'allow' | 'deny' | 'ask'
```

> 「`allow` **或** `deny` **或** `ask`，三选一。」

两个容易混的地方：

- 它**不是**位运算的「按位或」。在**类型位置**（`type` 右边、参数冒号右边）出现时，它是联合类型；在**值位置**（`a | b` 两个数字之间）才是位运算。判断方法：看它左右两边是类型还是值。
- 它**不是**「可以同时是三个」。联合类型的值是「其中一个」，不是「全部」。

顺带记住它的两个亲戚（讲义 [§2.3、§2.5](../00a-TypeScript地基.md)）：`?` 是「可以没有」，`&` 是「必须同时满足」。

### 问题 3：全仓库有多少地方在用这个类型？

实际跑 `grep -rn "PermissionBehavior" source/src | wc -l`：**29 处，分布在 8 个文件**。

按文件分布（真实统计）：

| 文件 | 处数 | 在干什么 |
| --- | --- | --- |
| `utils/permissions/permissions.ts` | 6 | 核心逻辑：参数、`switch`、批量遍历 |
| `types/permissions.ts` | 5 | 定义本身 + 同文件内其他类型引用 |
| `entrypoints/sdk/coreSchemas.ts` | 5 | SDK 协议的 zod 校验 |
| `utils/permissions/permissionsLoader.ts` | 3 | 从配置加载规则 |
| `utils/permissions/PermissionRule.ts` | 3 | 规则对象的字段类型 |
| `components/permissions/rules/PermissionRuleInput.tsx` | 3 | 输入组件（用户选 allow/deny/ask） |
| `components/permissions/rules/PermissionRuleList.tsx` | 2 | 列表展示（把值翻成英文标签） |
| `components/permissions/rules/AddPermissionRules.tsx` | 2 | 添加规则的弹层 |

**这 29 处说明一件事**：一行类型定义的影响面，可以从内核（`utils/permissions/`）一路穿到 SDK 协议、再到终端界面。**L0 阶段不必读这 8 个文件**，只要知道「定义一次、处处受约束」这件事在这个仓库是常态。

## 4. 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 这行会在运行时检查值合不合法 | 编译后整行消失。真正的运行时校验在 `coreSchemas.ts` 的 `z.enum` |
| `'allow'` 是一个叫 allow 的变量 | 是**字符串字面量类型**，代表「这个确切的字符串」 |
| `PermissionBehavior` 和 `PermissionMode` 是一回事 | 不是。`PermissionMode`（第 29 行）是另一组值，管「整体模式」；`PermissionBehavior` 管「单条规则的判定」 |

1. 用一句中文念出第 44 行。

4. 为什么同一个三值集合要用 zod 再写一遍？

6. `let x: PermissionBehavior = 'allow'; x = 'deny'` 合法吗？`x = 'maybe'` 呢？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. 「`PermissionBehavior` 只能是 `allow`、`deny` 或 `ask` 三者之一。」
2. 三个：`allow`（允许）、`deny`（拒绝）、`ask`（询问用户）。
3. 因为联合类型只有三个成员，三个 `case` 已经穷尽；多写 `default` 反而是永远走不到的死代码。收益是：将来加第四个值时，这个函数会因为「缺少返回路径」被编译器点名。
4. TypeScript 类型编译后不存在，运行时无法校验外部传入的 JSON；`z.enum([...])` 是运行时真正执行的检查。两份定义分别守编译期和运行期。
5. ① 第 44 行的类型定义；② `coreSchemas.ts` 第 253 行的 `z.enum`；③ 所有 `switch` 的 `case`（`permissions.ts`、`PermissionRuleList.tsx`、`hooks.ts`、`utils/hooks.ts` 等）；④ 展示层把值翻成文案的地方；⑤ 规则数组字面量（`['allow','deny','ask']`）。
6. 合法；不合法——`'maybe'` 不在联合类型里，编译期报错。
