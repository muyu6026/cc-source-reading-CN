## 4.1 工具注册中心：[`src/tools.ts`](../source/src/tools.ts)

> 📁 本节源码：[`src/tools.ts`](../source/src/tools.ts)

这是**所有 AI 工具的"户口本"**。模型能调用哪些工具，完全由这里决定。

```ts
/**
 * Get the complete exhaustive list of all tools that could be available
 * in the current environment (respecting process.env flags).
 * 获取当前环境下所有"可能可用"的工具的完整列表（受环境变量开关影响）。
 * This is the source of truth for ALL tools.
 * 这是【所有工具的唯一真相来源】。
 */
export function getAllBaseTools(): Tools {
  return [
    AgentTool,          // 派发子智能体
    TaskOutputTool,     // 读取后台任务输出
    BashTool,           // 执行 shell 命令
    ...(hasEmbeddedSearchTools() ? [] : [GlobTool, GrepTool]), // 内嵌搜索工具时就不单独给 Glob/Grep
    ExitPlanModeV2Tool, // 退出计划模式
    FileReadTool,       // 读文件
    FileEditTool,       // 改文件
    FileWriteTool,      // 写文件
    NotebookEditTool,   // 改 Jupyter notebook
    WebFetchTool,       // 抓网页
    TodoWriteTool,      // 写待办
    WebSearchTool,      // 联网搜索
    // …下面大量 feature('XXX') 条件工具（cron/Sleep/Monitor/Workflow 等）
    BriefTool,
    ListMcpResourcesTool,  // MCP 资源列表
    ReadMcpResourceTool,   // 读 MCP 资源
    ...(isToolSearchEnabledOptimistic() ? [ToolSearchTool] : []), // 工具搜索
  ]
}
```

### 关键点
- 注释里那句 **"This is the source of truth for ALL tools"（所有工具的唯一真相来源）** 是读这份源码的第一把钥匙：想知道 AI 有什么能力，只看这一个函数。
- 数组里用 `...(条件 ? [工具] : [])` 这种**展开语法做条件包含**——这是"按环境变量动态裁剪工具集"的写法。

### 工具还分"模式"
`getTools()` 里能看到 `CLAUDE_CODE_SIMPLE` 模式只给三个工具：

```ts
export const getTools = (permissionContext): Tools => {
  // Simple mode: only Bash, Read, and Edit tools
  // 极简模式：只给 Bash、Read、Edit 三个工具
  if (isEnvTruthy(process.env.CLAUDE_CODE_SIMPLE)) {
    const simpleTools: Tool[] = [BashTool, FileReadTool, FileEditTool]
    return filterToolsByDenyRules(simpleTools, permissionContext)
  }
  // …正常模式：拿 getAllBaseTools() 再按权限过滤
}
```

> 注意最后那步 `filterToolsByDenyRules(...)`：**工具列表还要过一遍权限过滤**（用户 deny 掉的工具不给模型看）。权限细节见 [08 权限与安全](08-权限与安全.md)。

## 4.2 单个工具长什么样：以 `BashTool` 为例

> 📁 本节源码：[`src/tools/BashTool/BashTool.tsx`](../source/src/tools/BashTool/BashTool.tsx)

`src/tools/BashTool/` 目录：

| 文件 | 大小 | 作用 |
|------|------|------|
| `BashTool.tsx` | 161 KB | 工具主逻辑 |
| `bashSecurity.ts` | 103 KB | **安全沙箱 / 危险命令检测**，非常值得读 |
| `bashPermissions.ts` | 101 KB | 权限判定（要不要问用户） |
| `commandSemantics.ts` | 3.8 KB | 命令"退出码语义"，**小而易懂，强烈推荐先读这个** |

### 最佳入门文件：`commandSemantics.ts`

> 📁 本节源码：[`src/tools/BashTool/commandSemantics.ts:31-45`](../source/src/tools/BashTool/commandSemantics.ts#L31-L45)

这是整个项目里**最适合初学者**的文件之一：小、注释全、逻辑独立。

```ts
/**
 * Command semantics configuration for interpreting exit codes in different contexts.
 * 命令语义配置：在不同场景下解释"退出码"的含义。
 * Many commands use exit codes to convey information other than just success/failure.
 * 很多命令用退出码表达"成功/失败"以外的信息。
 * For example, grep returns 1 when no matches are found, which is not an error condition.
 * 例如 grep 在"没匹配到"时返回 1，但这不算错误。
 */

// grep: 0=有匹配, 1=无匹配, 2+=错误
['grep', (exitCode) => ({
  isError: exitCode >= 2,
  message: exitCode === 1 ? 'No matches found' : undefined,
})],
// find: 0=成功, 1=部分成功(有些目录无权限), 2+=错误
// diff: 0=无差异, 1=有差异, 2+=错误
// test/[ : 0=条件真, 1=条件假, 2+=错误
```

**为什么这个文件重要**：多数程序把"非 0 退出码"当失败，但 `grep` 没匹配到返回 1、`diff` 有差异返回 1——这些**都不是错误**。如果 AI 把 `grep` 的 1 当成错误，它就会误判"命令失败了"从而做错决策。这个文件就是修正这种误判的"翻译表"。

> **学习要点**：`BashTool` 是整个项目里**安全代码最密集**的地方。想学"AI 怎么安全地执行命令"，路径是：`commandSemantics.ts`（先读，建立信心）→ `bashSecurity.ts`（危险命令识别）→ `bashPermissions.ts`（权限判定）。

## 4.3 工具执行流水线：`src/services/tools/`
⚠️ 注意区分两个目录：

| 目录 | 管什么 |
|------|--------|
| `src/tools/` | 工具的**定义**（有哪些工具、每个工具怎么实现） |
| `src/services/tools/` | 工具**被 AI 叫起来之后**，怎么并发跑、怎么套 hook、怎么编排 |

### ① 流式并发执行器：`StreamingToolExecutor.ts`

> 📁 本节源码：[`src/services/tools/StreamingToolExecutor.ts:19-39`](../source/src/services/tools/StreamingToolExecutor.ts#L19-L39)

AI 一边吐工具调用，这边一边跑（不用等模型把话说完）。

```ts
// src/services/tools/StreamingToolExecutor.ts:19-39
type ToolStatus = 'queued' | 'executing' | 'completed' | 'yielded'
// 核心设计（类注释翻译）：
// - 标注了"并发安全"的工具，可以和其他并发安全工具并行跑
// - 没标注的工具必须独占运行（不能同时跑别的）
// - 结果先缓冲，再按"工具被收到的顺序"吐出去（不乱序）
export class StreamingToolExecutor {
  private tools: TrackedTool[] = []
```

**为什么这么设计**：

- `isConcurrencySafe`（并发安全）：只读工具（读文件、搜索）可以并行，快；
- 有副作用的工具（写文件、跑 shell）必须**独占**，否则会互相踩。
- `siblingAbortController`：某个 Bash 工具报错时，**同批的其他子进程立刻被杀掉**，而不是等它们自己跑完——避免浪费。

### ② 更高层编排：`toolOrchestration.ts`

> 📁 本节源码：[`src/services/tools/toolOrchestration.ts:8-12`](../source/src/services/tools/toolOrchestration.ts#L8-L12)

把工具调用按"能否并发"分区（`partitionToolCalls`），再决定并行还是串行。

```ts
// 并发数上限由环境变量控制，默认 10
function getMaxToolUseConcurrency(): number {
  return parseInt(process.env.CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY || '', 10) || 10
}
```

### ③ 钩子：`toolHooks.ts`

> 📁 本节源码：[`src/services/tools/toolHooks.ts`](../source/src/services/tools/toolHooks.ts)

在工具调用**前后**插钩子：

- `executePreToolHooks` —— 工具执行**前**（可以拦截、阻止）
- `runPostToolUseHooks` —— 工具执行**后**（可以加工结果）
- `executePostToolUseFailureHooks` —— 工具**失败**时（可以补救）

> 这就是"你能写脚本在 AI 动手前后自动执行"的机制来源。

### ④ 单工具执行：`toolExecution.ts`

> 📁 本节源码：[`src/services/tools/toolExecution.ts`](../source/src/services/tools/toolExecution.ts)

`runToolUse()` 是真正执行单个工具的地方，上面三者都最终调它。

## 4.4 执行流水线全景
```
模型返回 tool_use（可能有多个，一次一批）
        │
        ▼
┌──────────────────────────────────────────────┐
│ toolOrchestration.ts  partitionToolCalls()   │
│  按"是否并发安全"分区                          │
└───────────────┬──────────────────────────────┘
                │
     ┌──────────┴──────────┐
     ▼                     ▼
并发安全组              独占工具
（并行跑，上限10）        （串行，一个一个来）
     │                     │
     └──────────┬──────────┘
                ▼
        executePreToolHooks()    ← 工具执行前的钩子（可拦截）
                ▼
        hasPermissionsToUseTool() ← 权限判定 allow/ask/deny（见第08篇）
                ▼
        runToolUse()              ← 真正执行（toolExecution.ts）
                ▼
        runPostToolUseHooks()     ← 执行后的钩子（可加工结果）
                ▼
        结果按"收到的顺序"回灌给模型（不乱序）
```

## 4.5 工具的"类型契约"：[`src/Tool.ts`](../source/src/Tool.ts)

> 📁 本节源码：[`src/Tool.ts:362-416`](../source/src/Tool.ts#L362-L416)

前面一直说"工具是什么"，这里给定义。[`src/Tool.ts`](../source/src/Tool.ts)（29.6 KB）里的 `Tool` 类型，是**所有工具必须满足的契约**——想加一个新工具，就是实现这个类型。

```ts
// src/Tool.ts:362-416（节选 + 中文注释）
export type Tool<
  Input extends AnyObject = AnyObject,   // 输入用 Zod schema 描述
  Output = unknown,
  P extends ToolProgressData = ToolProgressData,
> = {
  aliases?: string[]                     // 工具改过名时，保留旧名字做兼容
  searchHint?: string                    // 一句话能力描述，供 ToolSearch 关键词匹配（3~10 词）

  call(                                  // ← 核心：真正干活的方法
    args: z.infer<Input>,                //   参数已被 Zod 校验，类型自动推导
    context: ToolUseContext,
    canUseTool: CanUseToolFn,            //   权限判定函数（见第08篇）
    parentMessage: AssistantMessage,
    onProgress?: ToolCallProgress<P>,    //   进度回调（流式输出）
  ): Promise<ToolResult<Output>>

  description(input, options): Promise<string>  // 给模型看的"这个工具干什么"

  readonly inputSchema: Input            // Zod schema：运行时校验 + 编译期类型
  outputSchema?: z.ZodType<unknown>

  isConcurrencySafe(input): boolean      // 能否和其他工具并行
  isEnabled(): boolean                   // 当前环境是否启用
  isReadOnly(input): boolean             // 是否只读
  isDestructive?(input): boolean         // 是否不可逆（删除/覆盖/发送）
  interruptBehavior?(): 'cancel' | 'block'  // 执行中用户发新消息怎么办
}
```

### 七个设计要点（每个都值得抄）
| 字段 | 设计意图 | 为什么重要 |
|------|----------|------------|
| `inputSchema`（Zod） | 一份 schema 同时做**运行时校验 + 编译期类型** | `z.infer<Input>` 让 `args` 自动有类型，不用手写两遍 |
| `call(...)` 返回 `Promise<ToolResult<Output>>` | 统一返回结构 | 上层不需要为每个工具写特殊处理 |
| `isConcurrencySafe` | **能否并行** | 只读工具可并行，写操作必须独占（见 4.3） |
| `isReadOnly` | **是否只读** | 和"并发安全"是**两个独立概念**：只读通常并发安全，但并发安全不一定只读 |
| `isDestructive` | **是否不可逆** | 注释写明："只在做**不可逆操作**（删除、覆盖、发送）时才设置" |
| `interruptBehavior` | `'cancel'` 丢弃结果 / `'block'` 让新消息等待 | 用户在工具跑一半时插话，行为要可预期 |
| `description(input, options)` | 描述**是函数不是字符串** | 因为描述可能随参数、权限、是否交互而变化 |

### 为什么 `description` 是函数
```ts
description(
  input,
  options: { isNonInteractiveSession: boolean; toolPermissionContext: ...; tools: Tools },
): Promise<string>
```

它拿到了参数、是否非交互、权限上下文、全部工具列表——这意味着**同一个工具可以针对不同场景给模型不同的说明**。比如"在非交互模式下，不要建议用户手动操作"。

### `isReadOnly` vs `isConcurrencySafe` 的区别
很多人会混淆这两个。举例：

| 工具 | `isReadOnly` | `isConcurrencySafe` | 说明 |
|------|--------------|---------------------|------|
| 读文件 | ✅ | ✅ | 只读且可并行 |
| 写文件 | ❌ | ❌ | 有副作用，必须独占 |
| 搜索 | ✅ | ✅ | 只读可并行 |
| 跑 shell | ❌ | ❌ | 可能改任何东西，必须独占 |
| 写待办（内存） | ❌（会改状态） | 可能 ✅ | 改了状态但不会影响文件系统，可以并行 |

> **一句话**：`isReadOnly` 描述"**会不会改东西**"，`isConcurrencySafe` 描述"**能不能同时跑**"。前者偏语义，后者偏安全。

## 4.6 本篇小结
- `getAllBaseTools()` 是**所有工具的唯一真相来源**；`getTools()` 还要按权限过滤。
- 单工具结构：`XXXTool.tsx`（逻辑）+ `bashSecurity.ts`（安全）+ `bashPermissions.ts`（权限）+ `prompt.ts`（给模型的指令）。
- 初学者从 `commandSemantics.ts` 入手——它讲"退出码语义"，小且注释全。
- 执行流水线四件套：`StreamingToolExecutor`（并发）、`toolOrchestration`（分区）、`toolHooks`（钩子）、`toolExecution`（执行）。
