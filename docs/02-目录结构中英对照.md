# 02 · 目录结构：中英对照与按目录深挖（精读版）

> **本篇目标**：把 `src/` 从「35 个看不懂的英文目录名」变成一张**能按问题查、能按顺序读**的地图。每个目录回答三件事：它解决什么问题、先读哪三个文件、批注覆盖到哪。
> **和 [01 篇](01-项目总览与架构.md) 的分工**：01 给全仓体量与启动链路；本篇不重复总账，只做「按目录深挖」。
> **统计口径**：`source/src` 下**全部文件**（含 18 个 `.js` 命令桩），行数 = 逐文件换行数加总；「批注」= `annotated/src` 下存在**同相对路径**文件的个数。不做 `.ts/.tsx` 过滤，所以 `commands/` 比 01 篇表里的 189 多 18。

## 2.1 先验数：这条命令跑出 2.2 的表

```bash
python -c "
import os
root='source/src'; a='annotated/src'
rows=[]
for d in os.listdir(root):
    p=os.path.join(root,d)
    if not os.path.isdir(p): continue
    fs=[os.path.join(dp,f) for dp,_,g in os.walk(p) for f in g]
    n=len(fs); l=sum(sum(1 for _ in open(f,errors='ignore')) for f in fs)
    c=sum(os.path.exists(os.path.join(a,os.path.relpath(f,root))) for f in fs)
    rows.append((l,n,c,d))
rows.sort(reverse=True)
for l,n,c,d in rows: print(f'{d:12}{n:6}{l:9}{c:6}')
print('TOTAL',len(rows),sum(r[1] for r in rows),sum(r[0] for r in rows),sum(r[2] for r in rows))
"
```

实际输出（前 6 行 + 合计；中间 29 行就是 2.2 表的数值）：

```
utils          564   180487   230
components     389    81892    66
services       130    53683   130
tools          184    50863   184
commands       207    26528     4
ink             96    19859    96
TOTAL 35 1884 501265 817
```

`src/` 根目录还有 18 个文件，单独一条命令：

```bash
python -c "
import os
p='source/src'
fs=[f for f in os.listdir(p) if os.path.isfile(os.path.join(p,f))]
print(len(fs), sum(sum(1 for _ in open(os.path.join(p,f),errors='ignore')) for f in fs))
print(sum(os.path.exists('annotated/src/'+f) for f in fs))
"
```

实际输出：`18 11972` / `5`。合起来 **1,902 文件 / 513,237 行 / 822 份批注**；这 822 份批注覆盖的源文件共 **314,898 行，占全仓 61.4%**（同一脚本按文件累加，与 README 一致）。

## 2.3 `utils/`：决策逻辑的蓄水池（564 文件 / 180,487 行 / 批注 230，40.8%）

**它在解决什么问题。** 名字最像杂物间，实际是 31 个子目录 + 298 个散文件。大件全是有状态的子系统：`plugins/` 44 文件 20,522 行（插件市场 + 安装器 + 版本仲裁）、`bash/` 23 文件 12,306 行（shell 解析与 AST）、`permissions/` 24 文件 9,409 行（权限引擎）、`swarm/` 22 文件 7,549 行（多智能体）、`settings/` 19 文件 4,562 行（配置分层）。判断一个东西该不该在 `utils/`，标准不是「小」，而是「能脱离界面单独测试」。

| 代表文件 | 行数（批注） | 为什么是代表 |
|---|---:|---|
| [`utils/permissions/permissions.ts`](../annotated/src/utils/permissions/permissions.ts) | 1,486（1,531） | 权限三态判定的总入口 `hasPermissionsToUseTool`，被 [`hooks/useCanUseTool.tsx:37`](../source/src/hooks/useCanUseTool.tsx#L37) 直接调用 |

## 2.9 目录与分层的关系：职责分层，不是依赖分层

```
入口层    entrypoints/  cli/  screens/  bootstrap/  main.tsx  setup.ts
             │  动态 import（先分流，再加载大块头）
编排层    query.ts  QueryEngine.ts  query/  state/  tasks/  coordinator/
             │  调用（决定这一轮怎么走）
领域层    tools/（模型调）  commands/（人敲）  services/（程序调）  skills/  memdir/
             │  依赖（提供能做的事）
基础层    utils/  constants/  types/  native-ts/  schemas/  migrations/
             （提供做事的零件）

横切（各层都能 import）  components/  ink/  hooks/  context/  outputStyles/
边界（进程外）          bridge/  remote/  server/  upstreamproxy/
```

四层的判据只有一句话：**入口层决定「跑哪种形态」，编排层决定「这一轮怎么走」，领域层提供「能做的事」，基础设施层提供「做事的零件」。**

但**别把这张图当依赖图**。实算三条反向边（`grep -rlE "from '(\.\./)+tools/"` 这类命令）：

```bash
grep -rlE "from '(\.\./)+tools/" source/src/utils | wc -l      # 49
grep -rlE "from '(\.\./)+utils/" source/src/tools | wc -l      # 119
grep -rlE "from '(\.\./)+tools/" source/src/services | wc -l   # 16
```

`utils/` 有 49 个文件 import `tools/`（权限判定要认识 `BashTool` 的沙箱与规则），`tools/` 有 119 个文件 import `utils/`，`services/` 也有 16 个（`toolExecution.ts`、`compact.ts` 这些编排型服务）。所以这套目录是**按职责切的**，不是按依赖切的；`utils` 与 `tools` 之间是双向网，读代码时不要假设「下层不会反过来依赖上层」。

## 2.12 本篇小结

- 全仓 **1,902 文件 / 513,237 行 / 822 份批注**（文件覆盖 43.2%，行覆盖 61.4%）；`utils` 35.2%、`components` 15.9%、`services` 10.5%、`tools` 9.9%。
- 四个巨型目录各有性格：`utils` 是决策蓄水池，`services` 是协议客户端（100% 批注），`tools` 是模型的手（100% 批注），`components` 是界面（批注只覆盖消息与输入框）。
- 剩下的 31 个目录按「入口 / 交互 / 状态 / 边界」四组记，比按字母背有效。
- 找功能的顺序：先查 2.8 的问题表，再 `grep -rn`，最后才按目录名猜。
- 目录是职责划分，不是依赖方向；`utils↔tools` 双向依赖是最容易被分层图骗的地方。
