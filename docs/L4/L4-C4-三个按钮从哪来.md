## 3. 精读正文

### 3.1 三态的形状：三个 type，不是一个 enum

```ts
// source/src/types/permissions.ts:174-184
export type PermissionAllowDecision<
  Input extends { [key: string]: unknown } = { [key: string]: unknown },
> = {
  behavior: 'allow'
  updatedInput?: Input
  userModified?: boolean
  decisionReason?: PermissionDecisionReason
  toolUseID?: string
  acceptFeedback?: string
  contentBlocks?: ContentBlockParam[]
}
```

三态不是一个数字枚举，而是**三个带不同必填字段的对象**（`ask` 在 199 行、`deny` 在 231 行各是一个 `export type` 的开头）。`allow` 可以带 `updatedInput`（用户在弹窗里改过内容）；`ask` **必须**带 `message`（要显示给人看）；`deny` **必须**带 `decisionReason`（谁拒的、凭什么）。类型层面就规定了：想说「不」就得交出理由。

### 3.2 谁发起：只有 `ask` 会走到弹窗

`useCanUseTool`（203 行）拿到 `hasPermissionsToUseTool` 的结果后先分流：`allow` 立刻 `resolve(ctx.buildAllow(...))` 返回（39-54），`deny` 走 65-91 直接返回。只有 `ask` 才继续往下，经过三道「自动检查」的门（协调者 hook/分类器 96-108、swarm 113-125、投机分类器 126-159），最后落到：

```ts
// source/src/hooks/useCanUseTool.tsx:160-168
              handleInteractivePermission({
                ctx,
                description,
                result,
                awaitAutomatedChecksBeforeDialog: appState.toolPermissionContext.awaitAutomatedChecksBeforeDialog,
                bridgeCallbacks: feature("BRIDGE_MODE") ? appState.replBridgePermissionCallbacks : undefined,
                channelCallbacks: feature("KAIROS") || feature("KAIROS_CHANNELS") ? appState.channelPermissionCallbacks : undefined
              }, resolve);
              return;
```

**注意最后一个参数 `resolve`**：整个函数体包在 `new Promise(resolve => …)` 里（32 行）。`handleInteractivePermission` 自己不返回 Promise（文件头 53-55 行的注释明说 `This function does NOT return a Promise`），它把 `resolve` 存起来，等人点了再调用。**这是全链最关键的一手**——UI 与调用方之间唯一的连接就是这根 `resolve` 线。

### 3.3 谁展示：往队列里 push 一个「带回调的对象」

```ts
// source/src/hooks/toolPermission/handlers/interactiveHandler.ts:92-100
  ctx.pushToQueue({
    assistantMessage: ctx.assistantMessage,
    tool: ctx.tool,
    description,
    input: displayInput,
    toolUseContext: ctx.toolUseContext,
    toolUseID: ctx.toolUseID,
    permissionResult: result,
    permissionPromptStartTimeMs,
```

（101-107 行还跟着分类器状态字段：`...(feature('BASH_CLASSIFIER') ? { classifierCheckInProgress: … } : {})`。）

推入的不是「一段文字」，而是一个 `ToolUseConfirm` 对象：既有要显示的数据（`tool`、`description`、`input`），也有四个回调（`onAbort` 137、`onAllow` 154、`onReject` 183、`recheckPermission` 204）。UI 拿到它，等于拿到了「怎么回答」的四个入口。

`PermissionContext` 里这三个队列操作只有 9 行，全是 React setState：

```ts
// source/src/hooks/toolPermission/PermissionContext.ts:337-345
    pushToQueue(item: ToolUseConfirm) {
      queueOps?.push(item)
    },
    removeFromQueue() {
      queueOps?.remove(toolUseID)
    },
    updateQueueItem(patch: Partial<ToolUseConfirm>) {
      queueOps?.update(toolUseID, patch)
    },
```

`queueOps` 是可选的（注意 `?.`）：**这个 hook 不依赖 React**，测试或非交互环境可以不传队列。这是「把 React 挡在业务逻辑外面」的典型做法。

界面那头就一行：

```tsx
// source/src/screens/REPL.tsx:4519（节选）
const toolPermissionOverlay = focusedInputDialog === 'tool-permission' ? <PermissionRequest key={toolUseConfirmQueue[0]?.toolUseID} onDone={() => setToolUseConfirmQueue(([_, ...tail]) => tail)} … toolUseConfirm={toolUseConfirmQueue[0]!} … /> : null;
```

**队列一次只显示队首**（`[0]`），`onDone` 就是「弹掉队首」。`key` 用 `toolUseID`，保证换一条权限请求时组件彻底重建，不会把上一条的输入状态带过来。

### 3.4 按钮的文案：三个 value，不是一个 Yes/No

`PermissionRequest.tsx` 只做分发（47-82）：`BashTool` → `BashPermissionRequest`，`FileEditTool` → `FileEditPermissionRequest`，其余落到 `FallbackPermissionRequest`。**通用路径的按钮就在这里**——三个 value 定义在 15 行（`type FallbackOptionValue = 'yes' | 'yes-dont-ask-again' | 'no';`），选项在 157-214 行构造：

```tsx
// source/src/components/permissions/FallbackPermissionRequest.tsx:159-165
    t7 = {
      label: "Yes",
      value: "yes",
      feedbackConfig: {
        type: "accept"
      }
    };
```

```tsx
// source/src/components/permissions/FallbackPermissionRequest.tsx:197-203
      t8 = {
        label: "No",
        value: "no",
        feedbackConfig: {
          type: "reject"
        }
      };
```

中间的第二个选项是条件的（173 行 `if (showAlwaysAllowOptions)`），文案是 `Yes, and don't ask again for {工具名} commands in {目录}`（185 行）。**「三个按钮」其实常常是两个**——`Yes, and don't ask again` 只在允许持久化的场景出现。

`feedbackConfig` 是这两个选项与普通选择器的差别：选中后按 Tab 可以补一句「告诉 Claude 该怎么做」，这段文字会作为 `feedback` 一路带回去。

### 3.5 点完之后：三个 value 分头走

```tsx
// source/src/components/permissions/FallbackPermissionRequest.tsx:66-68（case "yes" 分支的尾部）
            toolUseConfirm.onAllow(toolUseConfirm.input, [], feedback);
            onDone();
            break bb8;
```

三条分支的差别只有第二个参数 `permissionUpdates`：

| 用户点了 | 调用 | 第二个参数 | 结果 |
| --- | --- | --- | --- |
| `yes` | `onAllow(input, [], feedback)` | 空数组 | 只这一次 |
| `yes-dont-ask-again` | `onAllow(input, [{ type: "addRules", rules: [{ toolName }], behavior: "allow", destination: "localSettings" }])`（81-88 行） | 一条规则 | 写进本地配置，以后不再问 |
| `no` | `onReject(feedback)` | — | 走拒绝路径 |

**这就是「三态」在 UI 上的真身**：不是三个并列的按钮对应三个状态，而是「allow（本次）」「allow（永久）」「deny」——前两个都是 `allow`，差别在**要不要顺手改规则**。

### 3.6 回到哪：`claim()` 之后 `resolveOnce`

`onAllow` 收到点击后做的第一件事不是干活，而是**抢锁**：

```ts
// source/src/hooks/toolPermission/handlers/interactiveHandler.ts:154-160
    async onAllow(
      updatedInput,
      permissionUpdates: PermissionUpdate[],
      feedback?: string,
      contentBlocks?: ContentBlockParam[],
    ) {
      if (!claim()) return // atomic check-and-mark before await
```

`claim()` 是原子「检查并占领」（[`PermissionContext.ts:75-94`](../../source/src/hooks/toolPermission/PermissionContext.ts)）：谁先 return true 谁说了算，后来者直接退出。因为同一个请求可能同时被**用户点击、hook、分类器、远程桥、IM 频道**回答——五个来源抢一个 `resolve`。

`handleUserAllow`（291-318）负责正事：先把 `permissionUpdates` 落盘并写进 appState（`persistPermissions`，139-147），再记一条决策日志，最后 `buildAllow` 出一个 `allow` 对象。这个对象经 `resolveOnce` 交给 3.2 存下的 `resolve`，`useCanUseTool` 那个 `Promise` 就此兑现，上层 `toolExecution` 拿到 `behavior: 'allow'`，工具开始执行。

**一条命令的完整回答路径**：`toolExecution` 调 `canUseTool` → `useCanUseTool` 判 `ask` → `handleInteractivePermission` 推队列 → REPL 渲染 → `FallbackPermissionRequest` 出按钮 → `onAllow` → `claim()` → `handleUserAllow` → `resolveOnce` → 回到 `toolExecution`。

## 4. 核心问题完整解答

对应 [学习路线](../00-零基础学习路线.md) L4-C 组卡片 C-4：「用户看到的那三个按钮从哪来？」

**按钮的出处**：`components/permissions/FallbackPermissionRequest.tsx` 的 15 行（三个 value）与 157-214 行（两个/三个选项的构造）。**不在** `hooks/toolPermission/` 里——那个目录只产出回调，一个 JSX 都没有。

**数据流**：流水线判 `ask`（C-2）→ `useCanUseTool` 把 `resolve` 连同上下文打包（160-168）→ `handleInteractivePermission` 推入队列（92-107）→ REPL 渲染队首（4519）→ `PermissionRequest` 按工具分发（47-82）→ `PermissionPrompt` 渲染选项（296）→ 用户点击 → `onAllow`/`onReject`（154/183）→ `claim()` 抢锁 → `handleUserAllow` 写规则并造 allow（291-318）→ `resolveOnce` 兑现 Promise。

**C 组过关题：为什么 deny 规则必须比 allow 先判？**

看流水线的第一行代码就知道顺序是硬编码的：

```ts
// source/src/utils/permissions/permissions.ts:1169-1175（节选）
  // 1. Check if the tool is denied
  // 1a. Entire tool is denied
  const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
  if (denyRule) {
    return {
      behavior: 'deny',
      decisionReason: {
```

两个理由：

1. **规则的「宽窄」不对等**。allow 规则通常写得很宽（「这个工具都能用」），deny 规则通常写得很窄（「这个工具的这个用法不行」）。宽规则先匹配，窄规则就永远轮不到——`rm -rf` 会被一条覆盖所有 Bash 的 allow 直接放走，用户特意写的 deny 变成摆设。
2. **deny 是唯一能穿过 bypass 模式的判断**。`checkRuleBasedPermissions` 的注释（1060-1066）写明它只算「bypassPermissions 模式也尊重的子集」，也就是 step 2a 之前的一切——而 1a 是第一顺位。**顺序反了，等于给了所有人一把总钥匙。**

顺带一个同构的例子：C-3 里 `validateNewlines` 的 `ask` 会被故意延迟，好让后面「误解析类」的强结论先落地——**弱结论不能盖住强结论，先到的不能压后到的**。权限规则只是把这件事做到了极致：deny 不是「先到」，而是「永远第一」。

**从这一课去 L5**：到这里你已经能回答「一次工具调用怎么被放行或拒绝」。L5 的任务 B 就是把这条链再往外扩一圈——从模型吐出 `tool_use` 一直走到 `tool_result` 回到消息历史，中间会再次经过今天这两个目录。

## 5. 常见误读

1. **「按钮在 `hooks/toolPermission/` 里」**。该目录 5 个文件、1,386 行，**没有一行 JSX**；它提供的 `ToolUseConfirm` 只有数据 + 四个回调（类型定义在 `PermissionRequest.tsx:103-127`）。找文案必须去 `components/permissions/`。
2. **「点 Yes 就是永久允许」**。`yes` 传的是空数组 `[]`（66 行），只有 `yes-dont-ask-again` 才带 `addRules`（81-88）。「永久」不是把本次结果记下来，而是**改规则**，下一条命令重新走完整流水线时才生效。
3. **「点 No 会得到一个 deny 决策」**。`onReject` 最后调的是 `ctx.cancelAndAbort(...)`，而它返回的是 `{ behavior: 'ask', message, contentBlocks }`（`PermissionContext.ts:172`）。工具执行器只判「是不是 allow」（`toolExecution.ts:995`：`if (permissionDecision.behavior !== 'allow')`），其余一律按拒绝处理，`message` 就是回给模型的那句 `tool_result` 错误文案。

## 7. 合书自测

1. 用一句话说清 `hooks/toolPermission/` 与 `components/permissions/` 的分工。
2. `ToolUseConfirm` 里为什么必须有 `toolUseID`？REPL 那句 `key={toolUseConfirmQueue[0]?.toolUseID}` 在防什么？
3. `yes` 和 `yes-dont-ask-again` 的差别落在哪个参数上？那个参数最终被谁消费？
4. C 组过关题：为什么 deny 必须比 allow 先判？举一个「顺序反了会出事」的例子。
5. 用户点 No 之后，`toolUse` 拿到的是什么 `behavior`？为什么不是 `deny`？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. `hooks/toolPermission/` 管**流程**（推队列、抢锁、写规则、记日志、与 hook/分类器/远程竞速），不产出任何 UI；`components/permissions/` 管**呈现**（文案、选项、Tab 补反馈），只调回调。
2. 它是这条权限请求的唯一标识：队列按它删除/更新（`PermissionContext.ts:340-345`），React 用它当 `key` 强制重建组件——否则上一条请求的输入框内容、Tab 反馈状态会带到下一条上。
3. 差别在 `onAllow` 的第二个参数 `permissionUpdates`：`yes` 传 `[]`，`yes-dont-ask-again` 传一条 `addRules`（destination 是 `localSettings`）。它被 `ctx.persistPermissions`（`PermissionContext.ts:139-147`）消费：落盘 + 合并进内存里的 `toolPermissionContext`。
4. 因为规则宽窄不对等：宽 allow 会吞掉窄 deny，用户写的 deny 永远轮不到；且 deny 是唯一能穿过 bypass 模式的判断（`checkRuleBasedPermissions` 只复刻 step 2a 之前的一切，1a 排第一）。反例：用户配了「Bash 全允许」外加「`rm` 必须拒」，若 allow 先判，`rm -rf ~` 命中宽规则直接放行，那条 deny 等于没写。详见 [`permissions.ts:1168-1181`](../../source/src/utils/permissions/permissions.ts)。
5. 拿到的是 `behavior: 'ask'`，`message` 是拒绝理由（`PermissionContext.ts:172`）。因为「人拒绝了」在语义上不是「规则禁止」，而是「这次没批准」；工具执行器只看 `!== 'allow'`（`toolExecution.ts:995`），把 `message` 写成 `tool_result` 的错误内容，模型据此换一种做法。
