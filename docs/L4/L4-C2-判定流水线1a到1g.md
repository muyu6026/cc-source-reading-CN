## 1. 方法课：怎么在几千行里只读主函数

大文件精读的标准动作，本课全程示范一遍：

**第一步，grep 步骤注释定位骨架**。这个文件的作者把流水线写成了带编号的注释（`// 1a.`、`// 2a.`），这就是现成的路标：

```bash

```

（实际输出见第 7 节「动手验证」。）一次 grep 拿到全部 16 个步骤的行号，两个函数的骨架立刻浮现：1112–1179 是一组（规则子集函数），1206–1338 是另一组（主函数）。

**第二步，按行号区间读主函数**。第 57 行的文件总览批注已点名主函数名：`hasPermissionsToUseToolInner`。grep 一下定义行（1194），于是只读 1194–1358 这 165 行。

**第三步，跳过各步骤调用的辅助函数**。主函数里出现的 `getDenyRuleForTool`、`toolMatchesRule`、`createPermissionRequestMessage`、`shouldUseSandbox`……全部**不展开**。判断标准：主函数关心的是「这一步问什么问题、返回什么就走哪条路」，辅助函数是「这个问题具体怎么算」——C-1 已经把规则匹配讲过，剩下的（如沙箱判定）属于别的课时。

## 4. 精读正文（一）：规则层 1a→1c

函数开头先挡掉已中止的请求（1199–1201 行），然后立刻进入 1a：

```ts
1205 │   // 1. Check if the tool is denied
1206 │   // 1a. Entire tool is denied
1207 │   const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
1208 │   if (denyRule) {
1209 │     return {
1210 │       behavior: 'deny',
1211 │       decisionReason: {
1212 │         type: 'rule',
1213 │         rule: denyRule,
1214 │       },
1215 │       message: `Permission to use ${tool.name} has been denied.`,
1216 │     }
1217 │   }
```

**deny 必须排最前的代码证据就在这**：这是全函数第一个可以返回判定的分支，而且返回的是 `deny`。它是无条件的第一问——后面任何逻辑（包括 2a 的 bypassPermissions 放行）都没有机会在它之前放行任何东西。第 303 行批注说得更直白：「它是流水线第一步（1a），优先级最高，**连 bypassPermissions 都不看它后面**」。

接着 1b（1219–1244 行）：查 ask 规则，命中就 return ask——但留了一个沙箱例外：

```ts
1225 │     const canSandboxAutoAllow =
1226 │       tool.name === BASH_TOOL_NAME &&
1227 │       SandboxManager.isSandboxingEnabled() &&
1228 │       SandboxManager.isAutoAllowBashIfSandboxedEnabled() &&
1229 │       shouldUseSandbox(input)
```

四个条件同时成立（是 Bash、沙箱开着、autoAllow 开着、这条命令确实会进沙箱），就不返回 ask，落到底下让 Bash 的 `checkPermissions` 做命令级判定。第 1230 行批注点出反向约束：「被排除的命令与 dangerouslyDisableSandbox 的命令不进沙箱，仍须遵守 ask 规则」——例外有边界，不是后门。

1c（1245–1261 行）把问题交给工具自己：

```ts
1247 │   let toolPermissionResult: PermissionResult = {
1248 │     behavior: 'passthrough',
1249 │     message: createPermissionRequestMessage(tool.name),
1250 │   }
1251 │   try {
1252 │     const parsedInput = tool.inputSchema.parse(input)
1253 │     toolPermissionResult = await tool.checkPermissions(parsedInput, context)
1254 │   } catch (e) {
```

默认值是 `passthrough`（工具没意见），工具的 `checkPermissions`（前缀规则、路径规则都在这判）覆盖它。注意：`tool.inputSchema.parse` 校验失败**不会**中断判定，只记日志（1259 行 `logError(e)`），`toolPermissionResult` 保持 passthrough——校验坏了不能顺便把权限审没了，但也不能放行，于是落到「没意见，问用户」。

## 5. 精读正文（二）：免疫层 1d→1g

1c 的结果 `toolPermissionResult` 现在带着三种可能：deny / ask / passthrough。1d–1g 是四道「先拦截」：

```ts
1262 │   // 1d. Tool implementation denied permission
1263 │   if (toolPermissionResult?.behavior === 'deny') {
1264 │     return toolPermissionResult
1265 │   }
1267 │   // 1e. Tool requires user interaction even in bypass mode
1268 │   if (
1269 │     tool.requiresUserInteraction?.() &&
1270 │     toolPermissionResult?.behavior === 'ask'
1271 │   ) {
1272 │     return toolPermissionResult
1273 │   }
```

1d：工具自己说 deny，直接采纳。1e：标注了「需要用户亲手交互」的工具（如某些会动真实世界的操作），即使 bypass 模式也要弹框——注释原文就是「even in bypass mode」。

1f 是本段最有讲头的一步（1275–1288 行）：

```ts
1275 │   // 1f. Content-specific ask rules from tool.checkPermissions take precedence
1276 │   // over bypassPermissions mode. When a user explicitly configures a
1277 │   // content-specific ask rule (e.g. Bash(npm publish:*)), the tool's
1278 │   // checkPermissions returns {behavior:'ask', decisionReason:{type:'rule',
1279 │   // rule:{ruleBehavior:'ask'}}}. This must be respected even in bypass mode,
1280 │   // just as deny rules are respected at step 1d.
1281 │   if (
1282 │     toolPermissionResult?.behavior === 'ask' &&
1283 │     toolPermissionResult.decisionReason?.type === 'rule' &&
1284 │     toolPermissionResult.decisionReason.rule.ruleBehavior === 'ask'
1285 │   ) {
1286 │     return toolPermissionResult
1287 │   }
```

三重条件精确圈出「用户**亲手写了**内容级 ask 规则」（如 `Bash(npm publish:*)`）产生的 ask。这类 ask 排在 2a 之前——**bypass 模式压不住它**。用户写「npm publish 必须问我」，开了 bypass 也不许悄悄放行。

1g 同理（1289–1298 行）：`decisionReason.type === 'safetyCheck'` 的 ask（`.git/`、`.claude/`、shell 配置等敏感路径检查）也是 bypass 免疫的。注释原文：「bypass-immune — they must prompt even in bypassPermissions mode」。

**这就是 1d–1g 叫「免疫层」的原因**：它们排在 2a 之前，是 bypassPermissions 压不住的四类裁决。

## 6. 精读正文（三）：模式层 2a→2b→3

规则层与免疫层都没拦住，才轮到模式说话：

```ts
1299 │   // 2a. Check if mode allows the tool to run
1300 │   // IMPORTANT: Call getAppState() to get the latest value
1301 │   appState = context.getAppState()
1302 │   // Check if permissions should be bypassed:
1303 │   // - Direct bypassPermissions mode
1304 │   // - Plan mode when the user originally started with bypass mode (isBypassPermissionsModeAvailable)
1305 │   const shouldBypassPermissions =
1306 │     appState.toolPermissionContext.mode === 'bypassPermissions' ||
1307 │     (appState.toolPermissionContext.mode === 'plan' &&
1308 │       appState.toolPermissionContext.isBypassPermissionsModeAvailable)
1309 │   if (shouldBypassPermissions) {
1310 │     return {
1311 │       behavior: 'allow',
1312 │       updatedInput: getUpdatedInputOrFallback(toolPermissionResult, input),
1313 │       decisionReason: {
1314 │         type: 'mode',
1315 │         mode: appState.toolPermissionContext.mode,
1316 │       },
1317 │     }
1318 │   }
```

两个细节：① 1300 行特意**重新拉一次 appState**——走到这里可能已过了不少时间，模式可能被用户中途切换，判定必须用最新值；② 第 1319 行批注解释了 plan 分支：plan 模式只是暂时切到只读规划，不该顺手把用户「以 bypass 启动」的授意作废。

2b（1321–1335 行）查工具级 allow 规则，命中返回 allow，`decisionReason: { type: 'rule' }`——与 1a 完全对称，只是查的是 allow 表。

3（1338–1349 行）收尾：走到这没有早退，说明规则层没意见、模式没放行——把 1c 留下的 passthrough 转成 ask，弹框问用户。

**模式层与规则层的区别**到此清晰：

| | 规则层（1a/1b/1c/2b） | 模式层（2a，外层的 dontAsk/auto） |
| --- | --- | --- |
| 回答什么 | 「有没有一条**具体规则**管这件事」 | 「当前**会话档位**要不要整体放行/改判」 |
| 结果落在哪 | `decisionReason: { type: 'rule', rule }` | `decisionReason: { type: 'mode', mode }` |
| 优先级 | deny 规则压过一切模式（1a 在 2a 前） | 模式只能放行规则没拦的东西 |
| 免疫例外 | — | 1d–1g 在 2a 之前，bypass 压不住 |

## 7. 核心问题：为什么 deny 必须先判，顺序反了会出事

这是路线图 C 组的过关题（[00-零基础学习路线](../00-零基础学习路线.md) L4-C 表末尾）。三段论证：

**其一，代码证据**：1a 是主函数第一个判定分支（1205–1217 行），返回 deny；2a 的 bypassPermissions 放行在 1299 行之后。顺序就是优先级——排在前面的是先手，后面的一切只能在它「没拦住」的前提下发言。

**其二，作者的自白**：第 227 行批注（`getDenyRules` 下方）——deny 与 allow 分三张表存，「判定顺序完全由代码结构决定，不依赖数据里的字段」。第 303 行批注：deny「优先级最高，连 bypassPermissions 都不看它后面」。

**其三，反例推演**（顺序反了会出的事）：假设把 2a（模式放行）提到 1a 之前。用户处于 bypassPermissions 模式，同时设置里有一条 deny 规则 `Bash(rm -rf*)`——这是企业或用户明写的「这类命令永远不行」。顺序颠倒后，bypass 直接 return allow，**deny 规则被架空**：危险命令在 bypass 会话里畅通无阻。同理，若把 2b（allow 规则）提到 1a 前，任何一条 `Bash(*)` 级别的宽泛 allow 都会吞掉所有更具体的 deny。安全设计的铁律：**黑名单先于白名单、具体拒绝先于整体放行**。

补一刀佐证：外层包装（490–985 行）里，dontAsk 把 ask 降级为 deny 的转换被刻意放在**最外层最后**，第 986 行批注写明理由——内层 1a–2b 每步都可以 return，「任何一处漏掉就是策略被绕过」。**凡是安全语义的转换，要么排最前（deny），要么包最外（dontAsk），绝不夹在中间。**

## 8. 常见误读

**误读一：「1d–1g 是规则层的一部分」。**
第 57 行总览批注把它们单独归为「免疫层」：1a–1c 是规则层（问规则、问工具），1d–1g 是从 1c 的结果里**挑出四类不许被 bypass 压住的裁决**提前拦截。1e 甚至和规则无关（看的是工具的 `requiresUserInteraction()`）。注意主函数有 1e，而规则子集函数 `checkRuleBasedPermissions` **没有** 1e（1092–1191 行，注释明说「step 1e is not replicated」，调用方须自行预检）。

**误读二：「return null 就是放行」。**
规则子集函数结尾（1190 行）返回 null 表示「没有规则反对」——第 1192 行批注专门纠正：「null 只是说规则层没意见，模式层与分类器还没跑」。null ≠ allow，allow 是主函数 2a/2b 的产物。

**误读三：「1b 命中 ask 规则就一定弹框」。**
沙箱例外（1225–1242 行）：Bash + 沙箱 + autoAllowBashIfSandboxed + 确实进沙箱，四个条件齐了就**不**返回 ask，落给工具自己判命令级规则。只看 1b 的 if 不看 fall-through 会得出「ask 规则必弹框」的错误结论。

代码证据：1a 是主函数第一个判定分支（1205–1217 行），返回 deny，2a 的 bypass 放行在 1299 行之后；第 303 行批注明说 deny「连 bypassPermissions 都不看它后面」。事故场景：把 2a 提到 1a 前，bypassPermissions 会话里 `Bash(rm -rf*)` 的 deny 规则被整体放行架空，危险命令畅通——黑名单必须先于白名单与整体放行。</details>

<details><summary>4. 1f 的三重条件与对抗对象</summary>

`behavior === 'ask'` 且 `decisionReason.type === 'rule'` 且 `decisionReason.rule.ruleBehavior === 'ask'`（1282–1284 行）——精确圈出用户亲手写的内容级 ask 规则（如 `Bash(npm publish:*)`）产生的 ask。它排在 2a 之前，因此 bypassPermissions 模式压不住：用户说「publish 必须问我」，开了 bypass 也得弹框。</details>

<details><summary>5. 规则子集函数与主函数的差异</summary>

① 没有 1e（注释「step 1e is not replicated」，调用方须自行预检 `requiresUserInteraction()`）；② 收尾返回 null 而非继续跑 2a/2b/3——null 只表示「规则层没意见」，不等于 allow。它存在的意义（第 1146 行批注）：bypassPermissions 仍要尊重规则层，调用方需要在不触发模式副作用的前提下先问一句「有没有规则反对」。</details>

<details><summary>6. 2a 重新拉状态的原因</summary>

第 1300 行注释「IMPORTANT: Call getAppState() to get the latest value」：走到 2a 可能已耗时（1c 里工具的 checkPermissions 是 await 的），期间用户可能切换了模式（如从 default 切到 bypassPermissions，或反之），模式判定必须用最新状态，否则用的是过期档位。</details>
