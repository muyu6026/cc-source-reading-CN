## 11.1 问题是什么

> 📁 本节源码：[`src/services/compact/autoCompact.ts`](../source/src/services/compact/autoCompact.ts)

模型的**上下文窗口（context window）**是有限的（比如 200K token）。聊久了、读了一堆文件之后，消息会超过窗口，API 直接报错。

**compact（压缩）** 就是解决办法：把早期对话**浓缩成摘要**，腾出空间继续聊。

两种触发方式：

| 方式 | 触发 | 说明 |
|------|------|------|
| 手动 | 用户敲 `/compact` | `src/commands/compact/` |
| 自动 | 快满窗口时自动 | [`src/services/compact/autoCompact.ts`](../source/src/services/compact/autoCompact.ts) |

```ts
  const effectiveContextWindow = getEffectiveContextWindowSize(model)
  const autocompactThreshold = effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS

  const envPercent = process.env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE
  if (envPercent) { /* …把百分比换算成 token 阈值… */ }
  return autocompactThreshold
}
```

### 三个阈值概念
```
上下文窗口总量（如 200K）
├──────────────────────────────────────────┤
│                                          │
│          可用空间                          │
│                                          │
├──────────────────────────────────────────┤  ← 压缩阈值 = 窗口 - 13K
│      1.3 万 token 缓冲（留白）              │
├──────────────────────────────────────────┤
│                                          │
└──────────────────────────────────────────┘  ← 窗口顶部
```

- **压缩阈值**：`窗口 - 13,000`。到了这个数就自动压缩。
- **为什么要留 1.3 万缓冲？** 因为压缩动作本身也要消耗 token（要读旧对话、写摘要），而且模型还在生成。留缓冲防止"刚要压缩就已经超了"。

## 11.4 熔断：连失败 3 次就停手
```ts
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
```

注释里有个真实数据，非常值得看：

> 2026-03-10 的 BigQuery 统计显示，**1279 个会话出现过 50+ 次连续压缩失败**（最多 3272 次），白白浪费全球每天约 **25 万次 API 调用**。

### 为什么会出现"连续失败 50+ 次"
如果上下文已经**不可恢复地超过限制**（比如单条消息就超了窗口，压不动），那么每次尝试压缩都会失败，但主循环还在重试——于是变成"失败 → 重试 → 失败"的死循环，疯狂烧钱。

**熔断器（circuit breaker）**就是解法：连续失败 3 次，**主动停止尝试**，直接报错让用户处理。

> **学习要点**：这是个通用的工程模式——**任何"重试"都要配"熔断"**。否则遇到不可恢复的错误，重试逻辑会变成"烧钱机器"。

## 11.5 压缩到底做了什么：`compact/compact.ts`
不是说"把旧消息删掉"（那样 AI 就失忆了），而是：

```
旧对话（很长）
   ↓
fork 一个子 agent（runForkedAgent）
   ↓
子 agent 读旧对话，写一份摘要
   ↓
摘要放回 system 消息
   ↓
旧内容替换成一条 SystemCompactBoundaryMessage（压缩边界标记）
   ↓
后续对话基于"摘要 + 边界之后的新消息"继续
```

### 关键设计：`SystemCompactBoundaryMessage`
它是一条"**压缩边界标记**"，告诉系统"这之前的内容已经被压缩成摘要了"。这样：
- 需要完整历史时可以知道"这里断过"；
- UI 可以显示"以上内容已压缩"。

## 11.6 微压缩：`compact/microCompact.ts`
整段摘要比较重（要调一次模型）。所以还有一个轻量版：**microCompact（微压缩）**。

| 类型 | 压缩什么 | 开销 |
|------|----------|------|
| `compact` | 整段旧对话 → 摘要 | 高（要调模型） |
| `microCompact` | 只压局部（如超长的文件读取结果） | 低 |

> 类比：`compact` 是"把整本书缩写成摘要"，`microCompact` 是"把某几页折角贴上便签"。

## 11.8 和其他机制的关系
```
主循环 query.ts（06 篇）
   ├─ autoCompactTracking      ← 记录本轮有没有压缩过
   ├─ hasAttemptedReactiveCompact ← 记录有没有试过"被动压缩"
   └─ maxOutputTokensRecoveryCount ← 输出超限后重试次数
```

这三者一起，保证长任务**不崩**：
- 输入太长 → `autoCompact` 压缩；
- 输出超限 → `maxOutputTokensRecoveryCount` 重试；
- 压不动 → 熔断报错，别烧钱。

## 11.9 本篇小结
- 上下文有窗口上限，满了就报错；`compact` 把旧对话**摘要**腾空间。
- 自动压缩阈值 = `窗口 - 13,000`，留缓冲是因为压缩本身也耗 token。
- **熔断**：连失败 3 次就停，防止"压不动还疯狂重试"烧钱（有真实数据：每天浪费 25 万次调用）。
- 压缩不是删除，是"摘要 + 边界标记 `SystemCompactBoundaryMessage`"。
- `microCompact` 是轻量版，只压局部。
