## 2. 精读正文（一）：limits.ts——闸门

### 2.1 开头 14 行就是全部规格

```ts
1  │ /**
2  │  * Read tool output limits.  Two caps apply to text reads:
3  │  *
4  │  *   | limit         | default | checks                    | cost          | on overflow     |
5  │  *   |---------------|---------|---------------------------|---------------|-----------------|
6  │  *   | maxSizeBytes  | 256 KB  | TOTAL FILE SIZE (not out) | 1 stat        | throws pre-read |
7  │  *   | maxTokens     | 25000   | actual output tokens      | API roundtrip | throws post-read|
8  │  *
9  │  * Known mismatch: maxSizeBytes gates on total file size, not the slice.
10 │  * Tested truncating instead of throwing for explicit-limit reads that
11 │  * exceed the byte cap (#21841, Mar 2026).  Reverted: tool error rate
12 │  * dropped but mean tokens rose — the throw path yields a ~100-byte error
13 │  * tool-result while truncation yields ~25K tokens of content at the cap.
14 │  */
```

这张表值得逐列读：两个上限**管的东西不同**。`maxSizeBytes` 卡的是**整个文件**的大小（不是本次输出的切片），成本只有一次 `stat`，在**读之前**就抛错；`maxTokens` 卡的是**实际输出 token**，要读出来才能数，所以成本是一次 API 往返、在**读之后**才抛错。第 9–13 行是最珍贵的一段工程记录：字节闸卡「整个文件」而非「切片」是个已知不完美，团队试过改成「超限时截断而不是报错」，结果**报错率降了但平均 token 消耗涨了**——报错只吐约 100 字节的错误信息，截断却吐出 2.5 万 token 的正文，权衡后回滚。**一个「bug」改不改，要拿数字说话。**

### 2.2 默认值与环境变量覆盖

```ts
19 │ export const DEFAULT_MAX_OUTPUT_TOKENS = 25000
```

25,000 token，大约是上下文窗口的十分之一。一次 Read 最多吃掉十分之一窗口，剩下的留给别的事。注意它和 256KB **互相独立、没有换算关系**：一个压缩率极低的文件可能只有 300KB，字节没超、token 超了。

```ts
26 │ function getEnvMaxTokens(): number | undefined {
27 │   const override = process.env.CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS
28 │   if (override) {
29 │     const parsed = parseInt(override, 10)
30 │     if (!isNaN(parsed) && parsed > 0) {
31 │       return parsed
32 │     }
33 │   }
34 │   return undefined
35 │ }
```

四个细节：环境变量是**用户手动设的**，所以优先级压过实验平台（50–51 行注释明说）；返回 `undefined` 而不是 `null` 或 `0`，让调用方能干净地用 `??` 落到下一档；`parsed > 0` 挡住手滑写 `=0`——若 0 被当合法值，所有读取都会超限；`parseInt` 失败（`NaN`）也当「没设」。**解析用户输入的兜底原则：非法就当不存在，绝不猜。**

### 2.3 闸门的全貌：四个字段

```ts
38 │ export type FileReadingLimits = {
39 │   maxTokens: number
40 │   maxSizeBytes: number
41 │   includeMaxSizeInPrompt?: boolean
42 │   targetedRangeNudge?: boolean
43 │ }
```

前两个是**硬闸**（真的拦）；后两个是**软开关**（只改 prompt 里说什么），下一节会看到它们怎么接进说明书。

### 2.4 取值：三层优先级 + 逐字段兜底

```ts
57 │ export const getDefaultFileReadingLimits = memoize((): FileReadingLimits => {
58 │   const override =
59 │     getFeatureValue_CACHED_MAY_BE_STALE<Partial<FileReadingLimits> | null>(
60 │       'tengu_amber_wren',
61 │       {},
62 │     )
63 │
64 │   const maxSizeBytes =
65 │     typeof override?.maxSizeBytes === 'number' &&
66 │     Number.isFinite(override.maxSizeBytes) &&
67 │     override.maxSizeBytes > 0
68 │       ? override.maxSizeBytes
69 │       : MAX_OUTPUT_SIZE
```

第 71–78 行对 `maxTokens` 做同样的逐字段校验，只是优先级多一层：**环境变量（`getEnvMaxTokens()`，`??` 最前）> 实验平台 > 硬编码默认值**。实验平台下发的只是一个 `Partial<FileReadingLimits>`，每个字段单独判断「是不是有限正数」，非法就落回默认。

`memoize` 在这里**不是为了性能，是为了值稳定**（45–48 行注释点明）：实验值会在后台刷新，如果不冻结，同一个会话里 Read 的上限可能中途从 25,000 变成 30,000——而 prompt 里念给模型听的上限（`includeMaxSizeInPrompt`）和实际生效的就不一致了。**第一次调用就把值钉死。**

第 90–96 行的 return 把四个字段打包返回，布尔开关非法时返回 `undefined` 而不是 `false`——让调用方区分「实验明确关了」和「实验没下发」。注释最后一句是整段的目标：**`no route to cap=0`**，绝不允许任何路径把上限配成 0。

## 3. 精读正文（二）：prompt.ts——说明书

### 3.1 四个零散常量

```ts
 5 │ export const FILE_READ_TOOL_NAME = 'Read'
```

工具名单独放一个小常量文件（这里在 prompt.ts 顶部）导出，是因为别的文件只需要**一个词**就引用了整个工具本体，会造成循环依赖——L3-03 里 `FileEditTool/prompt.ts` 只 import 这一个字符串，注释原话：「Use a string constant for tool names to avoid circular dependencies」。

```ts
 7 │ export const FILE_UNCHANGED_STUB =
 8 │   'File unchanged since last read. The content from the earlier Read tool_result in this conversation is still current — refer to that instead of re-reading.'
```

去重命中时吐给模型的桩文案，三句话各答一个疑问：**发生了什么**（内容是上次读的）、**可信吗**（仍然最新）、**该怎么办**（引用上次结果，别重读）。少了第三句，模型往往会「保险起见」再读一遍，去重就白做了。

```ts
11 │ export const MAX_LINES_TO_READ = 2000
```

行数闸。注意现在有**三道独立的闸**：2,000 行（行数）、25,000 token（token）、256KB（字节）。一个 2,000 行的压缩 JS 可能远超 25,000 token，所以行数闸拦不住的 token 闸来拦。

```ts
14 │ export const DESCRIPTION = 'Read a file from the local filesystem.'
```

全文件最容易搞混的一对：这个一句话的 `DESCRIPTION` 给**人**看（工具列表、权限对话框）；下面 `renderPromptTemplate` 拼出来的长模板给**模型**看。Tool 契约里 `async description()` 返回前者、`async prompt()` 返回后者——后者最终塞进 API 请求的 `description` 字段，名字撞车纯属历史遗留。

### 3.2 offset 指令的两套文案

```ts
17 │ export const LINE_FORMAT_INSTRUCTION =
18 │   '- Results are returned using cat -n format, with line numbers starting at 1'
19 │
20 │ export const OFFSET_INSTRUCTION_DEFAULT =
21 │   "- You can optionally specify a line offset and limit (especially handy for long files), but it's recommended to read the whole file by not providing these parameters"
22 │
23 │ export const OFFSET_INSTRUCTION_TARGETED =
24 │   '- When you already know which part of the file you need, only read that part. This can be important for larger files.'
```

默认版劝模型「建议整读，别传 offset」；targeted 版反过来「已知要哪段就只读那段」。整读的好处是上下文完整，坏处是大文件白烧 token——哪个更好取决于用户在干什么，所以做成开关交给实验平台按数据切。**这是「用实验调 prompt」，不是拍脑袋写死。**

### 3.3 模板本体逐句拆

`renderPromptTemplate(lineFormat, maxSizeInstruction, offsetInstruction)`（31–35 行）留三个插值位，对应三段外部输入：行号格式、大小提示（可空）、offset 指令（二选一）。模板正文（37–53 行）按顺序是：

| 行 | 句子 | 在教模型什么 |
| --- | --- | --- |
| 37–38 | 「可以读机器上任何文件；用户给的路径当有效；读不存在的文件没关系，会返回错误」 | 打消模型「先确认文件存在」的多余动作 |
| 41 | `file_path` 必须是绝对路径 | 参数硬规矩 |
| 42 | 默认读前 `${MAX_LINES_TO_READ}` 行 | 行数闸念给模型听，让它知道会截断 |
| 43 | offset 指令（二选一插进来） | 上面 3.2 的开关 |
| 44 | `cat -n` 行号格式 | 让模型引用行号时别数错 |
| 45 | 能读图片（多模态直接看） | 能力声明 |
| 46–49 | PDF 段（**条件插入**） | 见下 |
| 50 | 能读 Jupyter notebook | 能力声明 |
| 51 | 只能读文件不能读目录，读目录用 Bash | 边界 + 替代方案 |
| 52 | 截图一律用本工具看 | 高频场景的特殊提醒 |
| 53 | 读到空文件会收到系统提醒 | 防止模型把「空」当成出错 |

第 46–49 行是一处**运行时条件**：`isPDFSupported()` 为假时，PDF 整段消失。**不支持的模型不该被告知有这个能力**，否则它会去试、然后拿到错误。说明书不仅要写「能做什么」，还要**不写**「不能做什么」。

还有一句没出现在模板里却最关键的规矩：`FileReadTool.ts` 的校验强制「必须先 Read 才能 Edit」。说明书（prompt.ts）立规矩，工具本体（FileEditTool 的校验）执行它——L3-03 讲的两层实现。

## 4. 两块骨头接在 Tool 契约的哪个孔上

L4-A2 学过 Tool 契约的字段，现在把两块骨头对号入座（以下摘自 `FileReadTool.ts`，行号为批注版实际行号）：

```ts
356 │   async prompt() {
357 │     const limits = getDefaultFileReadingLimits()
358 │     const maxSizeInstruction = limits.includeMaxSizeInPrompt
359 │       ? `. Files larger than ${formatFileSize(limits.maxSizeBytes)} will return an error; use offset and limit for larger files`
360 │       : ''
361 │     const offsetInstruction = limits.targetedRangeNudge
362 │       ? OFFSET_INSTRUCTION_TARGETED
363 │       : OFFSET_INSTRUCTION_DEFAULT
364 │     return renderPromptTemplate(
365 │       pickLineFormatInstruction(),
366 │       maxSizeInstruction,
367 │       offsetInstruction,
368 │     )
369 │   },
```

对应关系一张表：

| 零件 | 所在文件 | 接到哪个契约字段 | 谁消费 |
| --- | --- | --- | --- |
| `DESCRIPTION`（一句） | prompt.ts:14 | `description()` → FileReadTool.ts:353 | 权限对话框等 UI |
| `renderPromptTemplate` 产物 | prompt.ts:31 | `prompt()` → FileReadTool.ts:356 | 逐字塞进 API 请求 |
| `maxSizeBytes` / `maxTokens` | limits.ts | **不是契约字段**，在 `call()` 内部使用 | FileReadTool.ts:517–520 读出闸门值再拦截 |
| `includeMaxSizeInPrompt` / `targetedRangeNudge` | limits.ts | 通过 `prompt()`（357–363 行）**间接**接进说明书 | 实验开关 |

看清一个关键结构：**limits.ts 不是契约字段，它是 call() 的内部零件**——但它通过 357–363 行「渗」进了说明书：上限值会被念给模型听（`includeMaxSizeInPrompt` 打开时），offset 文案随 `targetedRangeNudge` 切换。闸门和说明书在 `prompt()` 这一个函数里交汇。这就是「一个最小工具」的真实形状：骨头不是两根孤立的杆，是一根**卡住行为**、一根**描述行为**，且描述必须和卡住的一致。

## 5. 核心问题：一个「最小可用」的工具最少要提供什么

数 FileReadTool 的零件清单：

1. **一个名字**：`FILE_READ_TOOL_NAME = 'Read'`（prompt.ts:5）。
2. **一句给人看的短描述**：`description()` → `DESCRIPTION`（FileReadTool.ts:353–355）。
3. **一份给模型看的长说明书**：`prompt()` → `renderPromptTemplate`（356–369）。
4. **一份参数契约**：`inputSchema`（zod，FileReadTool.ts:233），模型给的参数先过它。
5. **一个执行函数**：`call()`——闸门在这里生效（517–520 行取 limits，超限拦截、去重判断、真正读文件）。
6. **几个布尔旗标**：`isReadOnly`、`isConcurrencySafe`、`checkPermissions` 等——决定调度器和权限系统怎么对待它（Tool.ts 注释 62 行：它们必须自己实现）。

**最少要提供的就是这六样：名字、短描述、长说明书、参数契约、执行函数、布尔旗标。** FileReadTool 是这套最小集的标准样板：它没有任何花哨的机制（没有权限弹窗的特殊逻辑、没有流式进度），却完整跑通了「模型请求 → 校验 → 闸门 → 执行 → 结果」全链路。学新工具时，先拿它当模板比一比。

## 6. 常见误读

**误读一：「prompt.ts 是给用户看的文档」。**
不是。prompt.ts 的产物逐字进入 API 请求，唯一读者是**模型**。给人看的是 `DESCRIPTION` 那一句话（权限对话框）。两个「description」指的是完全不同的东西。

**误读二：「maxSizeBytes 卡的是本次读出来的内容大小」。**
卡的是**整个文件**的大小（limits.ts 第 6 行明写 `TOTAL FILE SIZE (not out)`）。所以「用 offset 只读一小段」**绕不开**字节闸——只要文件本体超 256KB，读切片也会抛错。第 9–13 行记录了团队试过放开这个限制，因 token 成本上升而回滚。

**误读三：「memoize 是性能优化」。**
这里冻结的是**实验平台的配置值**，动机是行为可复现：同一个会话内上限不能中途漂移，否则 prompt 里念的数和实际卡的数对不上。性能收益纯属顺带。

## 8. 合书自测

1. limits.ts 的两个上限分别卡什么？各在读取流程的哪个阶段生效？
<details><summary>答案</summary>maxSizeBytes（默认 256KB）卡整个文件大小，一次 stat、读之前抛错；maxTokens（默认 25,000）卡实际输出 token，一次 API 往返、读之后抛错。一个防「文件太大」，一个防「读出来塞不进上下文」。</details>

2. 为什么 `getEnvMaxTokens` 返回 `undefined` 而不是 0 或 `null`？
<details><summary>答案</summary>让调用方能用 <code>??</code> 干净地落到下一档优先级；若用 0 当「没设」的哨兵值，用户手滑设成 0 会让所有读取超限。解析失败或非正数一律当没设。</details>

3. `memoize` 包住 `getDefaultFileReadingLimits` 的真实动机是什么？
<details><summary>答案</summary>不是性能，是值稳定：实验平台的值会后台刷新，不冻结的话同一会话内上限会漂移，prompt 里念给模型的上限和实际生效的不一致、行为不可复现。第一次调用即钉死。</details>

4. `FILE_UNCHANGED_STUB` 三句话各回答模型什么疑问？少哪句最致命？
<details><summary>答案</summary>发生了什么（内容是上次读的）、可信吗（仍最新）、该怎么办（引用上次结果别重读）。少第三句最致命——模型会「保险起见」再读一遍，去重白做。</details>

5. `DESCRIPTION` 和 `renderPromptTemplate` 的产物分别给谁看？各自接到契约的哪个字段？
<details><summary>答案</summary>前者给人看（工具列表/权限对话框），接 <code>description()</code>；后者给模型看，逐字进 API 请求，接 <code>prompt()</code>。两者都像「description」但读者完全不同。</details>

6. 一个「最小可用」的工具最少要提供哪六样？
<details><summary>答案</summary>名字、给人看的短描述（description()）、给模型看的长说明书（prompt()）、参数契约（inputSchema）、执行函数（call()）、布尔旗标（isReadOnly / isConcurrencySafe / checkPermissions 等）。</details>
