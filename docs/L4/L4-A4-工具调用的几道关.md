## 3. 精读正文（二）：两个阈值，两种「慢」

```ts
151 │ // 【两个阈值，单位都是毫秒，但用途完全不同】
152 │ //
153 │ //      HOOK_TIMING_DISPLAY_THRESHOLD_MS = 500     超过就在界面上显示耗时
154 │ //      SLOW_PHASE_LOG_THRESHOLD_MS = 2000         超过就写一条调试警告
155 │ //
156 │ //  两个数都不是随手取的，注释给了依据：
157 │ //
158 │ //      500ms  →  低于这个看不到，显示了反而占地方
159 │ //      2000ms →  和 BashTool 的 PROGRESS_THRESHOLD_MS 对齐，因为
160 │ //                「折叠视图超过这个时长会让人以为卡死了」
161 │ //
162 │ //  注意后一条的理由是**用户体验**（felt stuck），不是技术指标。
163 │ //  这是很少见的写法：注释直接说「用户会觉得卡」，而不是「性能不佳」。
164 │ //
165 │ //  判据：阈值宁可抄同一套数字，也不要各自拍脑袋 —— 对齐才有可解释性。
166 │ /** Minimum total hook duration (ms) to show inline timing summary */
167 │ export const HOOK_TIMING_DISPLAY_THRESHOLD_MS = 500
168 │ /** Log a debug warning when hooks/permission-decision block for this long. Matches
169 │  * BashTool's PROGRESS_THRESHOLD_MS — the collapsed view feels stuck past this. */
170 │ const SLOW_PHASE_LOG_THRESHOLD_MS = 2000
```

500ms 是「界面上值不值得显示一条耗时」的门槛；2000ms 是「要不要写调试警告」的门槛，而它的依据是**和 BashTool 对齐**——用户对「多久算卡」的感知是全应用一致的，阈值各写各的就会自相矛盾。

记住 2000 这个数，第 5 节讲权限检查时会再遇到它。

## 4. 精读正文（三）：classifyToolError——压缩后还能诊断

```ts
205 │ export function classifyToolError(error: unknown): string {
206 │   if (
207 │     error instanceof TelemetrySafeError_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS
208 │   ) {
209 │     return error.telemetryMessage.slice(0, 200)
210 │   }
211 │   if (error instanceof Error) {
212 │     // Node.js filesystem errors have a `code` property (ENOENT, EACCES, etc.)
213 │     // These are safe to log and much more useful than the constructor name.
214 │     const errnoCode = getErrnoCode(error)
215 │     if (typeof errnoCode === 'string') {
216 │       return `Error:${errnoCode}`
217 │     }
218 │     // ShellError, ImageSizeError, etc. have stable `.name` properties
219 │     // that survive minification (they're set in the constructor).
220 │     if (error.name && error.name !== 'Error' && error.name.length > 3) {
221 │       return error.name.slice(0, 60)
222 │     }
223 │     return 'Error'
224 │   }
225 │   return 'UnknownError'
226 │ }
```

问题背景（172–193 行批注讲透了）：生产构建会压缩代码，`error.constructor.name` 变成 `nJT`、`Chq` 这样的三字母乱码——**开发环境里好使的诊断手段，上线后完全不可用**，这就是它一直没被发现的原因。

四级兜底，按可靠性排序：

1. `TelemetrySafeError`——专门设计的错误类，`telemetryMessage` 是审查过的、可安全上报的。
2. errno 的 `code`——`ENOENT`（没有这个文件）、`EACCES`（没权限），稳定且信息量大。
3. `error.name` 且长度 > 3——`ShellError` 是真类名（6 字符），乱码不超过 3 字符，**一个长度判断就过滤掉了压缩产物**。
4. 都不行就报 `'Error'`——比乱码强。

## 6. 核心问题：权限检查插在第几步、为什么在那一步

**答：第七步**（批注版 1081 行，`resolveHookPermissionDecision`），夹在「PreToolUse 钩子」（960 行）之后、「真正执行」（1367 行）之前；且 zod 形状校验（775 行）和业务校验（843 行）都排在它**前面**。为什么是这个位置，三个理由：

1. **形状不对的调用不配问权限。** 模型给的参数连 zod 都过不了、或业务上自相矛盾（比如 Edit 一个没读过的文件），这种请求无论允不允许都不该执行——先问用户「允不允许」只会浪费一次弹窗。所以校验双闸（关 4、关 5）必须排在权限前面。
2. **用户看到的必须是最终参数。** PreToolUse 钩子有权改写输入（`hookUpdatedInput`：批注版约 1003 行 `processedInput = result.updatedInput`）。如果先弹权限窗、后跑钩子，用户批准的是改写前的参数，钩子一改就「批准了个寂寞」。所以顺序必须是：钩子先改 → 改完再判权限。
3. **权限是执行前的最后一道闸。** 离执行越近，判定依据越接近「即将真实发生的事」（此时输入已经过校验、回填、钩子修正，不会再变）。太早判权限，后面任何一步改了输入，判定就作废了。

另外注意关 6 和关 7 的关系：钩子**有权直接裁决**（`hookPermissionResult`），`resolveHookPermissionDecision` 先消化钩子的裁决，没有才落到 `canUseTool`（规则匹配 → 弹窗）。所以严格说是「钩子裁决和用户权限合并成第七步」。

**本层过关题（路线图 A-4 卡片）：一个新工具要加哪几个文件、改哪几处注册？**

- **加文件**：新建 `annotated/src/tools/XxxTool/` 目录，最少三件——`XxxTool.ts`（实现 Tool 契约：L4-A3 那六样）、`prompt.ts`（说明书）、可选 `toolName.ts`（名字常量，防循环依赖，见 L4-A3 第 3.1 节）。
- **改注册**：`annotated/src/tools.ts` 两处——import（FileReadTool 在第 52 行）+ 加进 `getAllBaseTools()` 清单（317 行定义函数、FileReadTool 在 335 行）。`getAllBaseTools` 是**唯一真相来源**，45 个工具都在这一张清单上；加了它，调度、过滤、工具列表展示全部自动生效。

## 7. 常见误读

**误读一：「校验失败会抛异常，调用方接住再处理」。**
不会。关 2 和关 4 失败都是 **yield 一条内容为错误的 tool_result**（头注 17–18 行明说）。抛异常会留下悬空的 `tool_use`，下一次 API 请求直接 400。中止（关 3）同理——「取消」在协议层不是「什么都没发生」，而是一条「发生了取消」的消息。

**误读二：「权限检查在 zod 校验之前——安全的事应该最先做」。**
权限回答的是「允不允许做这件事」，校验回答的是「这件事本身成不成立」。参数形状都立不住的请求，问权限没有意义。而且钩子（关 6）要改写输入，权限必须等输入定稿后再判。

**误读三：「头注写的 345/615 行就是代码所在位置」。**
那是**原文**行号。批注版插入了约 160 行中文批注，同一逻辑位置变成 423/775。本文一律用批注版行号并已逐一 grep 核对；你自己去读时注意分清你在读哪个版本。

## 9. 合书自测

1. 一次工具调用依次过哪九道关？各自在批注版的哪一行？
<details><summary>答案</summary>①找工具（423，含 428–434 废弃别名回退）②找不到吐错误 tool_result（461 起）③中止检查（517）④zod 形状校验（775）⑤业务校验 validateInput（843）⑥PreToolUse 钩子（960，可改输入/直接裁决）⑦权限判定 resolveHookPermissionDecision（1081）⑧执行 tool.call（1367）⑨结果整形与收尾 processToolResultBlock（1575）/PostToolUse（1643）/失败钩子（1860）。</details>

2. 工具不存在时为什么不抛异常？
<details><summary>答案</summary>API 协议要求每个 tool_use 必须有配对的 tool_result，缺一个下次请求就 400。所以找不到工具、校验失败、用户中止都吐一条（内容为错误的）tool_result——「失败」也必须是合格的协议回复。</details>

3. 权限检查插在第几步？为什么不在最前面？
<details><summary>答案</summary>第七步（1081 行）。因为①形状/业务校验不过的调用不值得问权限；②PreToolUse 钩子可能改写输入，用户批准的必须是改写后的最终参数；③权限是执行前最后一道闸，判定依据最接近「即将真实发生的事」，早判了之后输入一变就作废。</details>

4. `classifyToolError` 为什么不直接用 `error.constructor.name`？四级兜底顺序是什么？
<details><summary>答案</summary>生产构建压缩后类名变成 nJT/Chq 等乱码，开发环境好使、上线不可用。顺序：TelemetrySafeError 的 telemetryMessage → errno 的 code（ENOENT/EACCES）→ error.name 且长度>3（长度判断过滤乱码）→ 'Error'。</details>

5. 两个毫秒阈值各管什么？为什么 2000 要和 BashTool 对齐？
<details><summary>答案</summary>500ms：超过就在界面显示耗时（低于看不见，显示占地方）；2000ms：超过写调试警告。对齐 BashTool 的 PROGRESS_THRESHOLD_MS 是因为「折叠视图超过这个时长会让人以为卡死」是全应用一致的用户感知，阈值各写各的会自相矛盾。</details>

6. 一个新工具要加哪几个文件、改哪几处注册？
<details><summary>答案</summary>新建 tools/XxxTool/ 目录（XxxTool.ts 实现 Tool 契约、prompt.ts 说明书、可选 toolName.ts）；注册改 src/tools.ts 两处：import + 加入 getAllBaseTools() 清单。getAllBaseTools 是唯一真相来源，加进它后调度、过滤、展示自动生效。</details>
