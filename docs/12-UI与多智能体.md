## 12.2 终端没有 DOM，React 照样能跑

React 本身不认浏览器，它认的是 **reconciler（调和器）**：一棵 Fiber 树 + 一套宿主环境接口（host config）。浏览器宿主叫 `react-dom`，这里换成了 `source/src/ink/reconciler.ts`。

```ts
// source/src/ink/reconciler.ts:224-...（节选，省略类型参数与无关钩子）
const reconciler = createReconciler<ElementNames, Props, DOMElement, ...>({
  createInstance: (type, props) => { /* createNode(type) 造 ink-box/ink-text */ },
  createTextInstance: (text) => createTextNode(text),
  appendChild: appendChildNode,
  supportsMutation: true,          // 就地改树，不做持久化重建
  resetAfterCommit(rootNode) {     // 每次提交后：先布局，再画帧
    rootNode.onComputeLayout()
    rootNode.onRender?.()
  },
})
```

宿主节点的类型是一套自定义枚举，只有终端语义（[`dom.ts:19`](../annotated/src/ink/dom.ts#L41)）：

```ts
export type ElementNames = 'ink-root' | 'ink-box' | 'ink-text' | 'ink-virtual-text' | 'ink-link' | ...
```

| React 概念 | 浏览器 | 这里 |
| --- | --- | --- |
| 宿主元素 | `div` / `span` | `ink-box` / `ink-text`（[`createNode`，`dom.ts:110`](../annotated/src/ink/dom.ts#L186)） |
| 插入/移动 | DOM API | `appendChildNode` / `insertBeforeNode`（`reconciler.ts:391-396`） |
| 更新属性 | `setAttribute` | `commitUpdate` 里 `diff(oldProps, newProps)`（`reconciler.ts:426`） |
| 布局 | CSS 引擎 | Yoga（`calculateLayout`） |
| 绘制 | 合成器 | 自写 screen buffer + ANSI |

```bash
grep -n "createReconciler<\|supportsMutation\|resetAfterCommit\|onRender?.()" source/src/ink/reconciler.ts
```

实际输出：

```
224:const reconciler = createReconciler<
247:  resetAfterCommit(rootNode) {
304:    rootNode.onRender?.()
405:  supportsMutation: true,
```

**关键理解**：React 在这里只做一件事——把组件树的变化翻译成对 `DOMElement` 节点树的增删改。它**从不碰 stdout**，写终端是下一节的第五步。

## 12.3 一帧的五个阶段

一次 setState 到屏幕变化，顺序固定（行号为 `source` 原文）：

| 阶段 | 位置 | 干了什么 |
| --- | --- | --- |
| ① 调和 + 提交 | `reconciler.ts:247` | React 算差异、改节点树；`resetAfterCommit` 收尾 |
| ② 布局 | `ink.tsx:249` | `yogaNode.calculateLayout(terminalColumns)`，宽度 = 终端列数 |
| ③ 画到屏幕缓冲 | `renderer.ts:31`、`:130` | `renderNodeToOutput` 把节点树刷成**单元格网格** |
| ④ 求差异 | `ink.tsx:586` | `log.render(prevFrame, frame)` 得到 `Patch[]`，只含变化的格子 |
| ⑤ 优化 + 写盘 | `ink.tsx:621`、`:736` | `optimize(diff)` 合并补丁，`writeDiffToTerminal` 拼成一个字符串 |

```bash
grep -n "log.render\|optimize(diff)\|writeDiffToTerminal\|calculateLayout" source/src/ink/ink.tsx
```

实际输出：

```
249:        this.rootNode.yogaNode.calculateLayout(this.terminalColumns);
586:    const diff = this.log.render(prevFrame, frame, this.altScreenActive,
621:    const optimized = optimize(diff);
736:    writeDiffToTerminal(this.terminal, optimized, this.altScreenActive && !SYNC_OUTPUT_SUPPORTED);
```

最后一跳在 [`terminal.ts:190`](../annotated/src/ink/terminal.ts#L302)：把几十个 patch 逐个翻译成 ANSI（光标移动、擦行、颜色），**拼进一个 buffer，只调用一次 `stdout.write`**（[`:247`](../annotated/src/ink/terminal.ts#L375)）。一次写的好处是不会出现「半帧」被终端画出来的撕裂。

两个容易忽略的点：

- **节流 16ms**：`scheduleRender` 是 lodash `throttle`，`FRAME_INTERVAL_MS = 16`（[`ink.tsx:213`](../annotated/src/ink/ink.tsx#L602)、[`constants.ts:2`](../source/src/ink/constants.ts#L2)）。流式输出一个 token 改一次 state，不会一 token 一帧。
- **不是「整屏字符串」**：首帧全屏，之后是差异补丁。常见简化说法是「序列化为一帧字符串写 stdout」，更准确的是「序列化为**一组补丁**再一次 write」。

## 12.4 三个物理约束，决定了 UI 代码为什么长这样

**约束一：字符宽度不等于字符数。** 汉字占 2 列，emoji 可能占 2 列，家庭 emoji 由多个码点组成但仍是一个字形。算错一列，右边框就歪。所以有一个专门函数 [`stringWidth`](../source/src/ink/stringWidth.ts#L220)：Bun 环境下直接用 `Bun.stringWidth`（按终端单元格算），否则回退到 `eastAsianWidth` + grapheme 分段。

**约束二：终端只能改「当前屏幕」，滚动出去的内容改不了。** 主屏模式必须维护 `frontFrame`（上一帧）和 `backFrame`，用差异补丁移动光标；alt-screen 模式每帧先把光标锚到 `(0,0)` 再 diff，防止 tmux 干扰让画面每帧上漂一行（`ink.tsx:563-580` 的注释写得很直白）。

**约束三：每个消息都是一棵 Fiber 树，内存会炸。** 对策写在 [`Messages.tsx:281-307`](../annotated/src/components/Messages.tsx#L411)：

```ts
// Ink mounts a full fiber tree per message (~250 KB RSS each) ...
// At ~2000 messages ... (observed: 59 GB RSS, 14k mmap/munmap/sec)
const MAX_MESSAGES_WITHOUT_VIRTUALIZATION = 200;
const MESSAGE_CAP_STEP = 50;
```

不用虚拟列表时，只渲染最近 200 条，按 50 条一档往前推；切点用 **UUID 锚点**而不是下标，因为压缩、折叠会改变数组长度，用下标会导致每回合整屏重置（`CC-941`/`CC-1154`/`CC-1174` 三段注释在 `:290-305`）。

## 12.6 权限弹窗：UI 反向卡住工具

普通 UI 是「数据变 → 界面变」。权限弹窗反过来：**界面等用户，工具调用挂起**。

1. 工具执行前调 `canUseTool`，返回一个 `Promise`（[`useCanUseTool.tsx:32`](../annotated/src/hooks/useCanUseTool.tsx#L38)）。
2. 需要询问时，把一条 `ToolUseConfirm` 推进 React 状态队列：`setToolUseConfirmQueue(queue => [...queue, item])`（[`PermissionContext.ts:364`](../source/src/hooks/toolPermission/PermissionContext.ts#L364)）；队列真身在 [`REPL.tsx:1101`](../source/src/screens/REPL.tsx#L1101)。
3. 队列非空时渲染 `PermissionRequest`，按工具对象**身份**选子组件：`case FileEditTool: return FileEditPermissionRequest`（[`:47-79`](../source/src/components/permissions/PermissionRequest.tsx#L47)，共 16 个 case）。
4. 用户点「允许/拒绝」→ `resolve` → Promise 结算 → 工具继续或中止。

```bash
grep -n "toolUseConfirmQueue, setToolUseConfirmQueue\] = useState" source/src/screens/REPL.tsx
grep -c "case .*Tool:" source/src/components/permissions/PermissionRequest.tsx
```

实际输出：`1101:  const [toolUseConfirmQueue, setToolUseConfirmQueue] = useState<ToolUseConfirm[]>([]);` 与 `16`。

这里的设计值得学：**弹窗不是「提示」，是控制流的一部分**。工具的执行线程真的停在这个 Promise 上，所以 UI 崩了或队列丢了，工具就永远挂着——这也是取消逻辑要单独写的原因（`useCancelRequest.ts:99` 直接清空整个队列）。

## 12.8 子代理的隔离边界：到底隔离了什么

「独立上下文」太粗。按 `runAgent.ts` 的实际代码，隔离项和共享项如下（[`:369-374`](../annotated/src/tools/AgentTool/runAgent.ts#L393)、[`:651-674`](../annotated/src/tools/AgentTool/runAgent.ts#L713)）：

| 维度 | 子代理 | 证据 |
| --- | --- | --- |
| 消息历史 | **新建** `initialMessages = [...contextMessages, ...promptMessages]`；普通子代理 `contextMessages` 为空 | `runAgent.ts:373` |
| 工具集 | **重新解析** `agentOptions.tools = allTools`，不是父级数组的引用 | `runAgent.ts:660-674` |
| 读文件缓存 | 新建或克隆 `readFileState` | `runAgent.ts:376-380` |
| abort 控制器 | 独立 `agentAbortController` | `runAgent.ts:706` |
| thinking | 普通子代理 `{ type: 'disabled' }`，省输出 token | `runAgent.ts:682-691` |
| AppState / 响应长度 | **同步**子代理与父级共享（`shareSetAppState: !isAsync`） | `runAgent.ts:709-712` |

两个反直觉点：

- **默认不带父级对话**。只有 `forkContextMessages` 存在（fork 路径）才把父级消息过滤后拼进去；普通 `Agent(prompt=...)` 拿到的是「任务描述 + 自己的系统提示」，不是父级全部历史。
- **工具是「解析出来的」，不是「继承的」**。`tools: ['*']` 展开成当前可用工具全集，再减 `disallowedTools`；权限规则还会再过滤一次（`filterDeniedAgents`，`AgentTool.tsx:219`）。

所以子代理贵不贵，取决于你给它多少工具和多少上下文，而不是「子代理天然便宜」。

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `inProcessRunner.ts` | 1,552 | 同进程 teammate 运行器：包 `runAgent()`，用 `AsyncLocalStorage` 隔离上下文，完成时通知 leader |
| `permissionSync.ts` | 928 | 跨代理权限同步：worker 把请求写进 leader 邮箱，leader 的 UI 审批后回信 |

| `spawnInProcess.ts` | 328 | 在同进程里拉起 teammate |

**开关是一票否决制**（[`agentSwarmsEnabled.ts:24-44`](../source/src/utils/agentSwarmsEnabled.ts#L24)）：ant 构建永远开；外部构建必须 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 或 `--agent-teams`，**并且** GrowthBook 的 `tengu_amber_flint` 没被关。少一个都返回 `false`，teammate 相关的工具、UI、提示词一起消失。

**权限怎么跨进程走**（`permissionSync.ts:1-18` 的文件头就是流程图）：

```
worker 遇到权限询问 → 写 permission_request 到 leader 邮箱
leader 轮询邮箱 → 弹出自己的 UI → 用户批准/拒绝
leader 写 permission_response 回 worker 邮箱 → worker 继续或中止
```

用的是**文件邮箱 + 锁**，不是共享内存：teammate 可能在另一个进程里，React 状态传不过去。同进程 teammate 走另一条捷径——`leaderPermissionBridge.ts` 把 REPL 的 `setToolUseConfirmQueue` 注册成模块级函数，非 React 代码也能把弹窗塞进主界面（[`REPL.tsx:1179`](../source/src/screens/REPL.tsx#L1179)）。

到这里，「多智能体」和「UI」其实是一件事：**队友的权限弹窗，最终画在 lead 的那一个 React 树里。**

2. 定义 worker 的**内部工具**：`INTERNAL_WORKER_TOOLS = {TeamCreate, TeamDelete, SendMessage, SyntheticOutput}`（`:29-34`）；给协调者描述「worker 能用什么」时，把这些从清单里滤掉（`:84-93`）。
3. `getCoordinatorSystemPrompt()`：一段「你是协调者，派 worker、验收、汇总」的提示词，明确要求读写任务分开并发、写任务按文件串行（`:111-232`）。

**更正**：旧版说 `coordinator/` 是「多智能体编排的核心，本质是 AgentTool 之上的一层封装」。实际读下来，它**只有模式开关 + 工具白名单 + 提示词**；真正的 worker 代理定义在 `coordinator/workerAgent.ts`，而这个文件在本快照里**不存在**：

```bash
grep -n "workerAgent" source/src/tools/AgentTool/builtInAgents.ts
ls source/src/coordinator/workerAgent.ts
```

实际输出：

```
38:      const { getCoordinatorAgents } =
39:        require('../../coordinator/workerAgent.js') as typeof import('../../coordinator/workerAgent.js')
ls: cannot access 'source/src/coordinator/workerAgent.ts': No such file or directory
```

这是 `feature('COORDINATOR_MODE')` 构建期做死代码消除（DCE）的结果：外部构建把整条分支删了，连被 require 的文件都不打包。判断方法同 [11.3](11-上下文压缩.md) 的坑：**看 `require` 外层有没有 `feature(...)`**。所以本快照只能读到「怎么指挥」，读不到「worker 长什么样」。

## 12.11 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 终端 UI 是「拼字符串打印」 | React 树 → 自有节点树 → Yoga 布局 → 单元格网格 → **差异补丁** → 一次 `stdout.write`（12.3） |
| `components/App.tsx` 管 stdin | 它只是三层 Provider（55 行）；stdin 在 `ink/components/App.tsx`（657 行） |
| 每帧重画整屏 | 只有首帧全屏；之后是 patch diff，还带 16ms 节流 |
| 多智能体的工具叫 `Task` | 线上名是 `Agent`，`Task` 是兼容旧权限规则/旧会话的别名；`TaskCreate` 是待办清单 |
| 子代理继承父级对话 | 默认从零开始，只有 fork 路径才拼父级消息；工具集也是重新解析的 |
| `coordinator/` 是多智能体核心 | 只有开关、工具白名单、提示词；`workerAgent.ts` 被 DCE 删了 |

## 12.12 本篇小结

- 终端能跑 React，靠的是自定义 reconciler：`createInstance` 造 `ink-box`/`ink-text`，`appendChild` 改树，`supportsMutation: true`。React 不碰 stdout。
- 一帧五阶段：commit → Yoga 布局 → 画进 screen buffer → diff 成 patch → 拼 ANSI 一次写；16ms 节流。
- 三个物理约束塑造了 UI 代码：字符宽度（CJK/emoji）、只能改当前屏、每消息一棵 Fiber（200 条上限、59GB RSS 的真实事故）。
- 多智能体只有入口工具 `Agent`（别名 `Task`）；隔离消息/工具/文件缓存/abort，共享 AppState。

<summary>参考答案（先自己写，再展开）</summary>

1. 最终是 `writeDiffToTerminal` 里的 `terminal.stdout.write(buffer)`（`terminal.ts:190/247`）。五阶段：① reconciler 提交（`reconciler.ts:247`）② Yoga 布局（`ink.tsx:249`）③ `renderNodeToOutput` 画进 screen buffer（`renderer.ts:130`）④ `LogUpdate.render` 求 diff（`ink.tsx:586`）⑤ `optimize` + 写屏（`ink.tsx:621/736`）。
