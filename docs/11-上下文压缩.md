## 11.1 不压缩会怎样：三个数字先摆出来

默认窗口是一个常量，不是「大概 200K」：

```ts
// source/src/utils/context.ts:9
export const MODEL_CONTEXT_WINDOW_DEFAULT = 200_000
```

但压缩判断用的不是 200,000，而是**有效窗口（effective context window）**——先扣掉「这次摘要请求自己要输出」的额度：

```ts
// source/src/services/compact/autoCompact.ts:28-48
const MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000   // p99.99 的摘要输出是 17,387 token
export function getEffectiveContextWindowSize(model: string): number {
  const reservedTokensForSummary = Math.min(
    getMaxOutputTokensForModel(model), MAX_OUTPUT_TOKENS_FOR_SUMMARY)
  ...
  return contextWindow - reservedTokensForSummary
}
```

再扣 13,000 缓冲，才是自动压缩阈值（`autoCompact.ts:72-91`）：

```ts
const autocompactThreshold = effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS
```

按 200K 窗口、输出上限 ≥20K 的模型代入（算术复现，`python -c` 实跑）：

```
sonnet-4-6: reserve=20000 effective=180000 autocompact=167000 warning=147000 blocking=177000 pct_at_threshold=92.8%
```

| 名字 | 公式 | 200K 模型上的值 | 出处 |
| --- | --- | --- | --- |
| 上下文窗口 | 常量/模型能力 | 200,000 | `utils/context.ts:9` |
| 有效窗口 | 窗口 − min(输出上限, 20K) | 180,000 | [`autoCompact.ts:33`](../annotated/src/services/compact/autoCompact.ts#L73) |
| 自动压缩阈值 | 有效窗口 − 13,000 | 167,000 | [`autoCompact.ts:62`](../annotated/src/services/compact/autoCompact.ts#L134) |
| 警告阈值 | 阈值 − 20,000 | 147,000 | [`autoCompact.ts:113`](../annotated/src/services/compact/autoCompact.ts#L231) |
| 阻塞上限 | 有效窗口 − 3,000 | 177,000 | [`autoCompact.ts:122-136`](../annotated/src/services/compact/autoCompact.ts#L259) |

注意两个细节：`WARNING_THRESHOLD_BUFFER_TOKENS` 与 `ERROR_THRESHOLD_BUFFER_TOKENS` 都是 20,000（`autoCompact.ts:63-64`），所以两个判断**今天永远同时为真**，UI 用后者决定红色/黄色（`TokenWarning.tsx:169`）；阻塞上限（177K）**高于**自动压缩阈值（167K），只有压缩被关掉或连续失败，才会走到「本地拦截」。

超了会怎样？两条路：

- **本地拦截**：请求发出前，若 `isAtBlockingLimit`，直接产出一条错误消息并结束本回合（[`query.ts:637-647`](../annotated/src/query.ts#L1338)），文案是 `Conversation too long. Press esc twice to go up a few messages and try again.`（`compact.ts:293-294`）。
- **服务端 413**：估算总有误差。真撞上 `prompt_too_long` 时，流式循环先把错误「扣住」不展示（[`query.ts:1065-1085`](../annotated/src/query.ts#L2150)），随后尝试恢复：先排空上下文折叠，再走反应式压缩（[`query.ts:1119`](../annotated/src/query.ts#L2262)）。

> 估算本身也值得知道：`tokenCountWithEstimation` 不是逐字数 token，而是「拿最后一条 API 响应的真实 `usage` + 对尾巴做粗估」（[`tokens.ts:226-261`](../source/src/utils/tokens.ts#L226)）；粗估就是**字符数 ÷ 4**（[`tokenEstimation.ts:203-207`](../annotated/src/services/tokenEstimation.ts#L213)）。

## 11.2 一个请求发出前，四道闸门的顺序

压缩不是「一个函数」，是主循环里四段串联。顺序在 `query.ts` 里写死（[`query.ts:400-467`](../annotated/src/query.ts#L857)）：

```
snip（裁剪，开关 HISTORY_SNIP）
  → microcompact（清旧工具结果，最便宜）
    → context collapse（折叠成视图，保留粒度）
      → autocompact（整段摘要，最贵）
        → 发请求
```

```bash
grep -n "deps.microcompact\|deps.autocompact\|buildPostCompactMessages" source/src/query.ts
```

实际输出：

```
13:import { buildPostCompactMessages } from './services/compact/compact.js'
414:    const microcompactResult = await deps.microcompact(
454:    const { compactionResult, consecutiveFailures } = await deps.autocompact(
528:      const postCompactMessages = buildPostCompactMessages(compactionResult)
```

顺序的理由，源码注释给了两条：

- 微压缩在自动压缩**之前**（`query.ts:412` 注释原话「Apply microcompact before autocompact」）：先做便宜的，可能就不用付摘要的钱。
- 折叠在自动压缩**之前**（`query.ts:428-431`）：折叠能压到阈值以下，自动压缩就变成 no-op，「保留细粒度上下文而不是一整段摘要」。反过来，自动压缩一旦开火，折叠攒下的细节就没了——所以 `shouldAutoCompact` 里检测到折叠开启会直接返回 `false`（[`autoCompact.ts:215-223`](../annotated/src/services/compact/autoCompact.ts#L379)），避免两者抢同一块空间。

压缩成功后，新的消息数组当回合就替换掉旧的（[`query.ts:528-535`](../annotated/src/query.ts#L1081)）。

## 11.3 入口不止三个：清点一遍

| 入口 | 触发 | 实现 | 是否调模型 |
| --- | --- | --- | --- |
| 手动 `/compact [指令]` | 用户敲命令 | `commands/compact/compact.ts:40` | 是（除非走会话记忆） |
| 自动压缩 | 超 167K 阈值，每回合检查 | `autoCompact.ts:241` | 是 |
| 微压缩 | 距上次回答超 60 分钟 / 缓存编辑策略 | `microCompact.ts:253` | **否** |
| 会话记忆压缩 | 开关开启且有记忆文件 | `sessionMemoryCompact.ts:514` | **否**（复用记忆文件） |
| 部分压缩 | 用户在消息上选「从这里/到这里压缩」 | `compact.ts:772` | 是 |
| 反应式压缩 | 撞 413 后补救 | `require('reactiveCompact.js')` | 是 |

命令入口只放元数据，实现懒加载（[`commands/compact/index.ts:4-13`](../source/src/commands/compact/index.ts#L4)）：

const compact = {
  type: 'local', name: 'compact',

三个关闭开关，粒度不同（[`autoCompact.ts:147-158`](../annotated/src/services/compact/autoCompact.ts#L277)）：`DISABLE_COMPACT` 全关；`DISABLE_AUTO_COMPACT` 只关自动、保留 `/compact`；设置项 `autoCompactEnabled` 默认 `true`（`utils/config.ts:594`）。

## 11.4 自动压缩：阈值怎么算，失败几次就停

阈值函数只有十几行，但留了两个后门（[`autoCompact.ts:72-91`](../annotated/src/services/compact/autoCompact.ts#L163)）：

```ts
export function getAutoCompactThreshold(model: string): number {
  const effectiveContextWindow = getEffectiveContextWindowSize(model)
  const autocompactThreshold = effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS
  const envPercent = process.env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE
  if (envPercent) { ... return Math.min(percentageThreshold, autocompactThreshold) }
  return autocompactThreshold
}
```

两个后门都**只能往下调**：`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 取 `Math.min`（`autoCompact.ts:40-46`），百分比覆盖也取 `Math.min`。设计意图是「方便测试提前触发」，不是「让你压得更晚」。

开火前还有四道递归护栏（[`autoCompact.ts:169-223`](../annotated/src/services/compact/autoCompact.ts#L323)）：`session_memory`、`compact` 这两个 fork 出来的 agent 自己压缩会死锁；`marble_origami`（上下文 agent）压缩会顺手清掉主线程的折叠日志；折叠模式开启时让位给折叠（[`autoCompact.ts:215-223`](../annotated/src/services/compact/autoCompact.ts#L406)）。

失败怎么办？熔断器（circuit breaker）（[`autoCompact.ts:257-265`](../annotated/src/services/compact/autoCompact.ts#L510)、`:334-350`）：

```ts
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
// BQ 2026-03-10: 1,279 sessions had 50+ consecutive failures (up to 3,272)
// in a single session, wasting ~250K API calls/day globally.
```

连续失败 3 次，本会话不再尝试自动压缩。触发条件是「上下文已经不可恢复地超限」（例如单条消息就超窗口），此时每回合重试都是白烧钱。成功一次就把计数清零（`autoCompact.ts:328-333`）。

> 通用工程结论：**任何重试都要配熔断**。重试解决的是「临时故障」，熔断解决的是「永久故障下的重试」。

## 11.5 主流水线：`compactConversation` 的八个动作

主函数 387 行起（[`compact.ts:387`](../annotated/src/services/compact/compact.ts#L800)），从头到尾一条主线：hooks → 拼提示词 → fork 子 agent 写摘要 → 摘要请求自己撞 413 就砍最老的组 → 清旧缓存 → 重建附件 → 造边界标记与摘要消息 → PostCompact hooks。

| 步 | 关键行 | 做了什么 |
| --- | --- | --- |
| ① | [`compact.ts:413`](../annotated/src/services/compact/compact.ts#L854) | `executePreCompactHooks({trigger: 'auto'|'manual'})`，钩子可改摘要指令 |
| ② | [`compact.ts:440`](../annotated/src/services/compact/compact.ts#L921) | `getCompactPrompt(customInstructions)`，包成一条 user 消息 |
| ③ | [`compact.ts:451`](../annotated/src/services/compact/compact.ts#L947) | `streamCompactSummary`，内部 `runForkedAgent({maxTurns: 1})`（`:1188-1200`） |
| ④ | [`compact.ts:460-490`](../annotated/src/services/compact/compact.ts#L970) | 摘要里出现 PTL 错误 → `truncateHeadForPTLRetry` |
| ⑤ | [`compact.ts:518-521`](../annotated/src/services/compact/compact.ts#L1079) | 先存 `readFileState` 快照，再清空 |
| ⑥ | [`compact.ts:532-585`](../annotated/src/services/compact/compact.ts#L1138) | 并行造文件/子 agent 附件，再补计划、技能、工具增量 |
| ⑦ | [`compact.ts:598-624`](../annotated/src/services/compact/compact.ts#L1277) | `createCompactBoundaryMessage` + 摘要消息 |
| ⑧ | [`compact.ts:723`](../annotated/src/services/compact/compact.ts#L1574) | PostCompact hooks；清理由调用方 `runPostCompactCleanup` 负责 |

几个容易被忽略的设计：

**③ 为什么用「fork 子 agent」而不是普通请求。** 摘要请求要读整段历史，如果另起一份 system prompt / tools，缓存前缀就变了，等于把整段历史按新单价重算一遍。fork 复用主线程的缓存键，`maxTurns: 1` 保证它只输出一段文字（`compact.ts:1181-1200`）。打开缓存共享后实测收益：缓存命中率直接进遥测（`compact.ts:1214-1227`）。

**④ 摘要请求自己也会超长。** 荒诞但真实：要压缩的对话太长，导致「压缩请求」本身 413。逃生舱在 `truncateHeadForPTLRetry`（[`compact.ts:243-291`](../annotated/src/services/compact/compact.ts#L459)）：按 API 轮次分组，从头丢组直到补上 token 缺口；缺口读不出来就丢 20%；最多 3 次（`MAX_PTL_RETRIES`，`compact.ts:227`）。注释自己承认「lossy but unblocks」（有损，但先让用户能动）。

**⑦ 边界标记不是装饰。** 它是 `system` 类型的 `compact_boundary` 消息，带 `trigger`/`preTokens`（[`utils/messages.ts:4530-4555`](../annotated/src/utils/messages.ts#L4599)）。后续所有「读历史」的代码都用它当起点：`getMessagesAfterCompactBoundary` 找**最后一个**边界并从它开始切（`messages.ts:4643-4647`）。所以边界必须留在数组里，不能当临时变量扔掉。

返回值 `CompactionResult` 是「怎么拼新数组」的完整配方（`compact.ts:299-310`），拼接顺序固定（[`compact.ts:330-338`](../annotated/src/services/compact/compact.ts#L679)）：

```ts
return [boundaryMarker, ...summaryMessages, ...(messagesToKeep ?? []), ...attachments, ...hookResults]
```

手动 `/compact` 替换历史的地方在命令处理层：返回 `type: 'compact'` 后，直接把消息数组换成 `buildPostCompactMessages(...)`，且 `shouldQuery: false`（不触发新请求）——[`processSlashCommand.tsx:679-702`](../source/src/utils/processUserInput/processSlashCommand.tsx#L679)。

## 11.6 摘要提示词：所谓「保留什么」，其实是 prompt 写的

摘要质量靠两段文本，不靠模型自觉。第一段是**禁止调工具**的开场（[`prompt.ts:19-26`](../annotated/src/services/compact/prompt.ts#L132)）：

```
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
- Tool calls will be REJECTED and will waste your only turn — you will fail the task.
```

原因写在 `prompt.ts:12-18`：fork 继承了父级的全部工具（为了缓存键一致），而 `maxTurns: 1` 下只要模型调一次工具，这一轮就废了，只能退回普通流式路径——Sonnet 4.6 上这个比例是 2.79%，4.5 上只有 0.01%。

第二段是固定的九节结构（[`prompt.ts:61-77`](../annotated/src/services/compact/prompt.ts#L236)）：1 用户请求与意图、2 关键技术概念、3 文件与代码段、4 错误与修复、5 问题解决、6 **All user messages（用户原话，防止意图被改写）**、7 待办、8 当前工作（断点）、9 下一步（要求原文引用最近对话）。

先让模型写 `<analysis>` 草稿再写 `<summary>`（`prompt.ts:31-44`），但草稿在进上下文前被剥掉（[`prompt.ts:311-335`](../annotated/src/services/compact/prompt.ts#L591)）：`<analysis>` 整段删除，`<summary>` 换成 `Summary:` 标题。**草稿只提升质量，不占上下文**。

最后包一层「会话续接」壳（[`prompt.ts:337-374`](../annotated/src/services/compact/prompt.ts#L635)），三件事：

```
This session is being continued from a previous conversation that ran out of context. ...
If you need specific details from before compaction ... read the full transcript at: <路径>
Continue the conversation from where it left off without asking the user any further questions.
```

第二行是**兜底通道**：摘要必然有损，但完整 transcript 还在磁盘上，模型需要精确代码时可以回去读。第三行只在 `suppressFollowUpQuestions=true`（自动压缩）时加，避免模型压缩完先来一句「好的，我们继续」。

## 11.7 压完留什么、丢什么

| 内容 | 全量压缩后 | 证据 |
| --- | --- | --- |
| 边界标记 `compact_boundary` | **留**（数组第 0 条） | `compact.ts:598`；拼接顺序 `:330` |
| 摘要消息（`isCompactSummary`） | **留**（数组第 1 条，对用户默认不显示） | `compact.ts:614-623` |
| 旧对话原文 | **丢**（全量压缩不设 `messagesToKeep`） | `CompactionResult.messagesToKeep?`，`compact.ts:304` |
| 最近读过的文件内容 | **留 5 个**，每个 ≤5K token，总预算 50K | `compact.ts:122-124`、`:1434-1463` |
| 计划文件 / 计划模式指令 | **留**（附件） | `compact.ts:545-555` |
| 用过的技能正文 | **留**，每个 ≤5K、总 25K | `compact.ts:129-130`、`:1494` |
| 工具/子 agent/MCP 指令增量 | **留**（按当前状态重新宣告） | `compact.ts:567-585` |
| SessionStart 钩子输出 | **留** | `compact.ts:592-594` |
| 图片 / 文档 | **丢**，替换成 `[image]` / `[document]` 文本 | `stripImagesFromMessages`，`compact.ts:145-199` |
| 技能发现/清单附件 | **丢**（压缩后本来就会重发） | `stripReinjectedAttachments`，`compact.ts:211-223` |
| thinking 块 | **不进摘要**（只进模型看到的原文，摘要里没有） | prompt 九节里无此项 |
| `tool_use` / `tool_result` 的**配对关系** | **必须留**，切点要退让 | 见下 |

「配对关系必须留」是硬约束，写在一个专门的函数里：`adjustIndexToPreserveAPIInvariants`（[`sessionMemoryCompact.ts:232-314`](../annotated/src/services/compact/sessionMemoryCompact.ts#L469)）。它做两件事：

1. 若保留区里有 `tool_result`，就往前找对应的 `tool_use`，把起点挪过去——否则切完就出现「孤立的 tool_result」，API 直接 400（文件头 204-219 行给了完整的坏例子）。
2. 若保留区里有某条 assistant 的 `message.id`，把它前面同 id 的兄弟消息也带上——流式输出会把一次响应拆成多条记录（thinking 一条、tool_use 一条），少带一条，thinking 块就在归一化时丢失（220-230 行）。

全量压缩不需要这个函数，因为它一条旧消息都不留；需要它的是「保留最近 N 条」的会话记忆压缩和部分压缩。

## 11.8 微压缩：只清工具结果，不写摘要

`microcompact` 常被误解成「小号 compact」。实际读下来，它**不调模型、不写摘要**，只把旧工具结果的内容换成一个墓碑字符串 `TIME_BASED_MC_CLEARED_MESSAGE = '[Old tool result content cleared]'`（[`microCompact.ts:36`](../annotated/src/services/compact/microCompact.ts#L133)）。

触发条件是「距最后一条 assistant 消息的间隔」超过阈值（[`microCompact.ts:446-467`](../annotated/src/services/compact/microCompact.ts#L1118)），默认配置三行（[`timeBasedMCConfig.ts:30-34`](../annotated/src/services/compact/timeBasedMCConfig.ts#L168)）：`enabled: false`（远程开关 `tengu_slate_heron`）、`gapThresholdMinutes: 60`、`keepRecent: 5`。

为什么是 60 分钟：服务端 prompt cache 的 TTL 是 1 小时，超时后整段前缀本来就要重写，不如先把旧结果清掉，让重写的内容更短（`timeBasedMCConfig.ts:3-13`）。这是**只在「反正要付钱」的时刻省钱**，不是随时乱删。

只清「可清工具」的结果（[`microCompact.ts:41-50`](../annotated/src/services/compact/microCompact.ts#L179)）：读文件、Shell、Grep、Glob、WebSearch、WebFetch、Edit、Write。改文件的结果留着，因为它是「我做过什么」的证据。

另一条路径是**缓存编辑（cache editing）**（[`microCompact.ts:305-399`](../annotated/src/services/compact/microCompact.ts#L788)）：本地消息一个字不改，只在 API 层附加 `cache_edits`，让服务端删掉指定 `tool_use` 的缓存条目。代价是只有主线程、特定模型、开关打开时可用（`:276-286`）。

关键一句在 `:288-292`：

```
// Legacy microcompact path removed — tengu_cache_plum_violet is always true.
// ... no compaction happens here; autocompact handles context pressure instead.
```

也就是说：**老的「无条件微压缩」已经被删了**。外部构建（没有 cached MC）走到 `microcompactMessages` 会原样返回。所以别指望微压缩兜住上下文——真正的兜底是自动压缩。

## 11.9 会话记忆压缩与部分压缩：两个「不全量」的变体

**会话记忆压缩**用一份持续维护的记忆文件代替「现场写摘要」，因此**不调模型**（`sessionMemoryCompact.ts:498-502` 注释：`SM-compact has no compact-API-call`）。它保留最近消息的**原文**，保留多少由三个数决定：`minTokens: 10_000`（至少 1 万 token）、`minTextBlockMessages: 5`（至少 5 条有文本的消息）、`maxTokens: 40_000`（硬顶）（[`sessionMemoryCompact.ts:57-61`](../annotated/src/services/compact/sessionMemoryCompact.ts#L149)）。

起点是「最后一条已被总结的消息」的下一条，然后**往前扩**直到满足两个下限，撞到上限或上一个边界就停（[`sessionMemoryCompact.ts:324-397`](../annotated/src/services/compact/sessionMemoryCompact.ts#L672)），最后交给 `adjustIndexToPreserveAPIInvariants` 修切点。注意它有两个前置条件：开关 `tengu_session_memory` **且** `tengu_sm_compact`（`:403-432`），否则返回 `null` 让调用方走全量压缩。

**部分压缩**是用户手选的：`direction: 'from'` 总结 pivot 之后、保留之前；`'up_to'` 总结之前、保留之后（[`compact.ts:772-800`](../annotated/src/services/compact/compact.ts#L1686)）。注释点出了缓存差异：`from` 保留的是前缀，prompt cache 还有效；`up_to` 摘要排在保留消息之前，缓存必然失效（`:766-771`）。同一段代码里还有一处细节——`up_to` 必须过滤掉旧的边界和旧摘要（`:790-799`），否则旧的 `boundary_A` 会让「找最后一个边界」的扫描提前停住，把新摘要 `summary_B` 丢掉。

- `runPostCompactCleanup` 有 7 个调用点（`grep -rn "runPostCompactCleanup(" source/src` 实测 8 行命中，其中 1 行是函数定义），手动、自动、`/clear` 都走它（`commands/clear/caches.ts:74`）。

## 11.11 压缩会丢信息，代码怎么把风险压下去

| 风险 | 机制 | 位置 |
| --- | --- | --- |
| 摘要漏掉关键细节 | 九节固定结构 + 第 6 节强制列「所有用户消息」 | `prompt.ts:66-77` |
| 摘要改写了用户意图 | 摘要后附完整 transcript 路径，模型可回读原文 | `prompt.ts:348-350` |
| 摘要请求自己超长 | 砍最老的组，最多 3 次；注释承认有损 | `compact.ts:460-490` |
| 压不动还无限重试 | 连续失败 3 次熔断 | `autoCompact.ts:257-265` |
| 切点破坏 tool 配对 | 起点前移，必要时补合成 user 消息 | `sessionMemoryCompact.ts:232-314`、`compact.ts:284-289` |
| 用户不知道刚发生过压缩 | 边界消息 + UI 提示 + 成功后抑制旧警告 | `messages.ts:4530`、`TokenWarning.tsx:169` |
| 压缩后模型「忘了」读过哪些文件 | 重注入最近 5 个文件，每文件截断到 5K | `compact.ts:122-124` |
| 压缩后缓存数字对不上 | `runPostCompactCleanup` 清十项缓存 | `postCompactCleanup.ts:41-76` |

最值得学的是「**有损操作要留退路**」这一条：PTL 重试会丢最老的对话，所以它丢之前先把完整 transcript 写盘；摘要会丢代码细节，所以摘要消息里带 transcript 路径。压缩不是「保证不丢」，而是「丢了还能找回来」。

## 11.12 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 压缩 = 删消息 | 删 + 写摘要 + 重建附件 + 造边界，四件事一起做；`buildPostCompactMessages` 决定新数组长什么样 |
| 微压缩是「小号 compact」 | 它不调模型、不写摘要，只把旧工具结果替换成墓碑字符串；老的通用微压缩已被删除（`microCompact.ts:288`） |
| 阈值就是「窗口 90%」 | 是 `窗口 − 输出预留 − 13K`，输出预留取 `min(模型上限, 20K)`；200K 模型上落在 167K（≈92.8%） |
| 压缩后保留「最近 N 轮」 | 全量压缩一条都不留；只有会话记忆压缩/部分压缩才保留原文 |
| 摘要提示词只是「总结一下」 | 九节结构 + 禁止调工具 + analysis 草稿剥离 + 续接壳，四层都是工程约束 |

## 11.13 本篇小结

- 200K 窗口先扣输出预留（≤20K）得有效窗口，再扣 13K 得自动压缩阈值；200K 模型上是 **167K**。
- 一个请求前四道闸门：snip → microcompact → collapse → autocompact；便宜的先做，能压下去就不付摘要钱。
- 压缩流水线八步，核心是「fork 子 agent 写九节摘要 → 砍 PTL → 清缓存 → 重建附件 → 造边界」。
- 全量压缩丢原文留摘要；会话记忆压缩留最近 1–4 万 token 原文；部分压缩按用户选的方向留一半。
- 微压缩只清工具结果（60 分钟缓存过期时最划算），不是压缩主力。
- 风险靠三样兜：熔断（3 次）、PTL 重试（3 次）、transcript 回读通道。

6. 连续失败 3 次就熔断，防的是什么场景？为什么不是「失败就重试到成功」？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. ①有效窗口 = 200,000 − min(模型输出上限, 20,000) = 180,000；②自动压缩阈值 = 180,000 − 13,000 = 167,000；③（可选）警告阈值再减 20,000 = 147,000。出处：`autoCompact.ts:33-48`、`:62`、`:72-91`。
2. snip → microcompact → context collapse → autocompact（`query.ts:400-467`）。微压缩最便宜（不调模型、只换字符串），先做可能直接把 token 降到阈值以下，省掉一次昂贵的摘要调用；折叠同理，能在保留细粒度上下文的前提下解决空间问题（`query.ts:428-431`）。
3. 第 0 条是 `system` / `subtype: 'compact_boundary'` 的边界标记（`createCompactBoundaryMessage`，`messages.ts:4530`）；第 1 条是 `user` 消息、`isCompactSummary: true` 的摘要（`compact.ts:614-623`）。顺序由 `buildPostCompactMessages` 固定（`compact.ts:330-338`）。
4. 因为摘要走 fork 子 agent、继承了父级全部工具，而 `maxTurns: 1` 下只要模型发起一次工具调用，这一轮就没有文本输出，整个摘要失败并退回普通流式路径（Sonnet 4.6 上 2.79%）。见 `prompt.ts:12-26`。
5. 因为 API 有两条硬约束：①每个 `tool_result` 必须有对应的 `tool_use`，否则 400；②同一次流式响应拆出的多条 assistant 记录共享 `message.id`，少带一条会把 thinking 块丢掉。`adjustIndexToPreserveAPIInvariants` 就是按这两条往前扩起点（`sessionMemoryCompact.ts:232-314`）。
6. 防「上下文不可恢复地超限」时的死循环：每次压缩都失败，主循环每回合还重试，真实数据是 1,279 个会话出现 50+ 次连续失败（最多 3,272 次），全球每天浪费约 25 万次 API 调用（`autoCompact.ts:67-70`）。重试只对临时故障有效；永久故障下重试是烧钱，所以用熔断止损。
