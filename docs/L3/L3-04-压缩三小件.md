## 1. 先画流水线：三个文件站在哪一格

压缩不是「一个函数」，是一条时间线：

```
   【压缩前】                【压缩中】                【压缩后】
   警告还显不显示            从哪儿下刀                清什么

   TokenWarning.tsx:107      compact.ts:257           commands/compact.ts:118
   读 compactWarningStore    groupMessagesByApiRound  runPostCompactCleanup
        ▲                         │                        │
        │ 订阅                    ▼                        ▼
   compactWarningHook.ts     Message[][] → slice()     下一轮请求
        ▲                    （不足 2 组则放弃）
   compactWarningState.ts ←── suppress／clear（microCompact.ts:259）
```

| 时刻 | 文件 | 它回答的问题 | 有效代码量 |
| --- | --- | --- | --- |
| 压缩前 | `compactWarningState.ts` | 那条「还剩多少上下文」的警告，现在该不该显示？ | 1 个 store + 2 个 setter |
| 压缩中 | `grouping.ts` | 要砍历史，刀口切在哪两条消息之间才安全？ | 1 个循环（20 行有效逻辑） |
| 压缩后 | `postCompactCleanup.ts` | 哪些缓存过期必须清？哪些故意不能清？ | 1 个判断 + 10 个清理动作 |

## 2. `grouping.ts`：站在「压缩中」的那一刀（快速带过）

唯一调用点在 PTL 逃生舱 `truncateHeadForPTLRetry`（`compact.ts:243` 起）：

```ts
251 │     messages[0]?.type === 'user' &&
252 │     messages[0].isMeta &&
253 │     messages[0].message.content === PTL_RETRY_MARKER
254 │       ? messages.slice(1)
255 │       : messages
257 │   const groups = groupMessagesByApiRound(input)
258 │   if (groups.length < 2) return null
```

三行定位它的角色：

1. **它不做压缩**。只把 `Message[]` 变成 `Message[][]`，一个 token 都没省。真正砍的是第 278 行 `groups.slice(dropCount).flat()`。
2. **它没有第二个调用方**。全仓库只有第 257 行这一处调用（`grep` 实测：其余命中只有第 115 行的 import、第 279 行的注释和 `grouping.ts:22` 的定义）。
3. **`groups.length < 2` 就放弃**。只剩一组没有刀口可下，返回 `null` 让上层走兜底——契约就是「至少两组才有意义」。L2-02 的三个条件这里只记结论：**刀口只能落在新的 assistant id 上**，同一轮响应的 `tool_use` 与 `tool_result` 必须同组。副作用是砍完要补：第 284–289 行判断 `sliced[0]` 是不是 assistant，是就补一条合成的 user 消息——因为分组让每组以 assistant 开头，砍掉第 0 组后**API 要求的第一条 user 就没了**。**分组让边界整齐，也让砍头必然破坏开头。**

## 3. `postCompactCleanup.ts`：压缩后的收尾（重点一）

### 3.1 签名：一个可选参数，一个最危险的默认值

```ts
31 │ export function runPostCompactCleanup(querySource?: QuerySource): void {
32 │   // Subagents (agent:*) run in the same process and share module-level
33 │   // state with the main thread. Only reset main-thread module-level state
34 │   // (context-collapse, memory file cache) for main-thread compacts.
35 │   // Same startsWith pattern as isMainThread (index.ts:188).
36 │   const isMainThreadCompact =
37 │     querySource === undefined ||
38 │     querySource.startsWith('repl_main_thread') ||
39 │     querySource === 'sdk'
```

`querySource?` 类型上允许不传，语义上不传 = **我是主线程** = **可以清全局状态**。JSDoc（第 12–30 行）明说：「undefined is only safe for callers that are genuinely main-thread-only (/compact, /clear)」。危险在于子 agent **不是独立进程**：它和主线程共享模块级变量，子 agent 压缩时若被当成主线程，就会把主线程的 `context-collapse` 存储、memory 缓存一起清掉。症状是「主线程莫名重读了一遍 CLAUDE.md」，触发点却是一次子 agent 压缩。

第 38 行用 `startsWith` 而不是 `===`，是踩过坑的：真实 source 长这样 `'repl_main_thread:outputStyle:custom'`。批注提到 `microCompact.ts` 曾写成 `===`，结果**所有改过 output style 的用户，微压缩从来没生效过**。

### 3.2 十个清理动作，一张表

| # | 行 | 调用 | 清的是什么（实测） | 作用域 |
| --- | --- | --- | --- | --- |
| 1 | 41 | `resetMicrocompactState()` | `cachedMCState` + `pendingCacheEdits`（`microCompact.ts:130-135`） | **无条件** |
| 2–4 | 47–60 | `resetContextCollapse()` / `getUserContext.cache.clear?.()` / `resetGetMemoryFilesCache('compact')` | 上下文折叠存储、**外层**记忆化缓存、memory 文件缓存 | 主线程（+开关） |
| 5–8 | 62–70 | `clearSystemPromptSections()` / `clearClassifierApprovals()` / `clearSpeculativeChecks()` / `clearBetaTracingState()` | 系统提示分段、分类器批准、Bash 推测性检查、beta 追踪 | 无条件 |
| 9 | 72–74 | `sweepFileContentCache()` | 文件内容缓存（`void`，不 await） | 开关 `COMMIT_ATTRIBUTION` |
| 10 | 76 | `clearSessionMessagesCache()` | `getSessionMessages.cache`（`sessionStorage.ts:3855`） | **无条件，最后** |

有条件的只有 2、3、4 三处，全是**进程级共享状态**；其余是**跟这次压缩走的状态**。判断依据不是「清的是什么」，而是「**这份状态是不是被多方共享**」：`microcompact` 是 per-compaction 的，子 agent 清自己的不伤主线程；memory 缓存是 per-process 的，必须判。第 10 项放最后，因为前面几个清理函数可能还在读会话消息缓存——**局部、只读的在前，破坏性的在后**。

### 3.3 两处「故意不清」

**① 不清 invoked skill 的内容**（第 17–20 行）：

```
 * Note: We intentionally do NOT clear invoked skill content here.
 * Skill content must survive across multiple compactions so that
 * createSkillAttachmentIfNeeded() can include the full skill text
 * in subsequent compaction attachments.
```

理由不是「我现在需不需要」，而是「**下一次压缩需不需要**」：下次要把技能全文放进附件，这次清掉就再也拿不回来——不可逆损失。**清理动作要向前看一步。**

**② 不清「已发送的技能清单」**（第 65–69 行）：

```ts
65 │   // Intentionally NOT calling resetSentSkillNames(): re-injecting the full
66 │   // skill_listing (~4K tokens) post-compact is pure cache_creation. The
67 │   // model still has SkillTool in schema, invoked_skills preserves used
68 │   // skills, and dynamic additions are handled by skillChangeDetector /
69 │   // cacheUtils resets. See compactConversation() for full rationale.
```

重发整份清单 ≈ 4K token，且是 `cache_creation` 单价（比普通 input 贵）。敢不清，因为三条保证各堵一个方向：能力还在（schema 里有 SkillTool）、历史还在（`invoked_skills`）、变化有别的通路（`skillChangeDetector`）。

这两条「不清」立刻长出一条依赖边——`/clear` 反过来要补清：

```ts
// commands/clear/caches.ts:74-80
  runPostCompactCleanup()
  // runPostCompactCleanup intentionally does NOT reset this (post-compact
  // re-injection costs ~4K tokens), but /clear wipes messages entirely so
  // the model needs the full listing again.
  resetSentSkillNames()
```

`/clear` 把消息全删了，模型手里什么都没有，必须重发——所以它**知道** cleanup 不清这一项，自己补上。这就是「故意不清」必须写注释的原因：不写，下一个人会以为是漏了，直接加进去，于是每次压缩白付 4K token。

### 3.4 一处「清内层不够，还要清外层」

```ts
52 │     // getUserContext is a memoized outer layer wrapping getClaudeMds() →
53 │     // getMemoryFiles(). If only the inner getMemoryFiles cache is cleared,
54 │     // the next turn hits the getUserContext cache and never reaches
55 │     // getMemoryFiles(), so the armed InstructionsLoaded hook never fires.
...
59 │     getUserContext.cache.clear?.()
60 │     resetGetMemoryFilesCache('compact')
```

调用链是**两层记忆化**：`getUserContext`（缓存①）→ `getClaudeMds()` → `getMemoryFiles`（缓存②）。只清 ②：下一轮 `getUserContext()` 命中 ①，直接返回旧值，**根本走不到** `getMemoryFiles()`；而「真的读了 memory 文件」才触发 `InstructionsLoaded` hook——于是「压缩后重载 CLAUDE.md」静默失效。**清缓存要清到最外层。** 第 60 行的 `'compact'` 也不是装饰：`resetGetMemoryFilesCache(reason)`（`claudemd.ts:1124-1130`）会设 `nextEagerLoadReason = reason`、`shouldFireHook = true`，让下次加载带着「因为压缩」这个原因触发 hook。

### 3.5 谁调用它：七个点，只有三个传 `querySource`

手动 `/compact`（`commands/compact/compact.ts:118`、`:201`、`:64`）与 `/clear`（`caches.ts:74`）都**不传**，因为它们是主线程专属入口；自动压缩（`autoCompact.ts:297`、`:326`）和部分压缩（`REPL.tsx:4972`）必须传。`/clear` 也调它——函数名带 `compact`，却被清空会话复用，说明它的本质是「**一批共享缓存的统一清理点**」。另一处细节：手动路径第 115–118 行是 `suppressCompactWarning()` → 清外层缓存 → `runPostCompactCleanup()`，第 202–204 行顺序相反；**顺序不一致说明这几步没有强依赖**（清两次也幂等）。

## 4. `compactWarningState.ts`：压缩前的可见性开关（重点二）

### 4.1 全文 18 行

```ts
1  │ import { createStore } from '../../state/store.js'
2  │
3  │ /**
4  │  * Tracks whether the "context left until autocompact" warning should be suppressed.
5  │  * We suppress immediately after successful compaction since we don't have accurate
6  │  * token counts until the next API response.
7  │  */
8  │ export const compactWarningStore = createStore<boolean>(false)
9  │
10 │ /** Suppress the compact warning. Call after successful compaction. */
11 │ export function suppressCompactWarning(): void {
12 │   compactWarningStore.setState(() => true)
13 │ }
14 │
15 │ /** Clear the compact warning suppression. Called at start of new compact attempt. */
16 │ export function clearCompactWarningSuppression(): void {
17 │   compactWarningStore.setState(() => false)
18 │ }
```

有效逻辑只有四处：一个 store、两个 setter、一个初始值。**为什么需要它**：压缩成功后本地的 token 数只是估算，真实值要等下一次 API 响应带回 `usage`。这段时间界面上的「还剩 15%」是错的——**显示错数字比不显示更糟**（用户以为还有余量，然后突然撞墙）。第 5 行的 `immediately` 是关键词：不能等 effect、不能等下一帧，否则用户会看到数字闪一下。

### 4.2 读写关系：谁写、谁读

| 方向 | 位置 | 动作 |
| --- | --- | --- |
| 写 `true` | `commands/compact/compact.ts:75`、`:115`、`:202`；`microCompact.ts:359`、`:511` | 压缩成功后抑制 |
| 写 `false` | `microCompact.ts:259` | 新一轮**开始时**解除抑制 |
| 读 | `compactWarningHook.ts:13-14` → `components/TokenWarning.tsx:107` | `useSyncExternalStore`；取到值后第 108 行据此 `return null` |

第 259 行注释把时序说全了：「Clear suppression flag at start of new microcompact attempt」。**成功才抑制，开始新尝试就解除**——万一这次失败，警告自然重新出现，不需要额外的失败分支。自愈设计。

### 4.3 一个布尔值，为什么要单独一个文件？

答案在隔壁 `compactWarningHook.ts` 的注释里：「Lives in its own file so that compactWarningState.ts stays React-free: microCompact.ts imports the pure state functions, and pulling React into that module graph would drag it into the print-mode startup path.」

拆开是**依赖方向**问题，不是代码整洁：`microCompact.ts`（服务层）要 import 两个 setter；若它们和 `useSyncExternalStore` 同住一个文件，服务层就被迫 import React；React 一旦进入这条模块图，就会被拖进 **print 模式的启动路径**——一个根本不渲染的地方。于是切成两半：`compactWarningState.ts` 只依赖 `state/store.js`（纯状态），`compactWarningHook.ts` 依赖 React，只有真正渲染的组件才 import 它。**方向：UI → hook → state；服务层 → state。服务层永远不向上碰 React。**

### 4.4 默认值：往安全的一侧偏

`createStore<boolean>(false)`——默认 `false` = **默认显示警告**。显示是安全的一侧：用户看到「快满了」会主动整理；默认抑制就会在用户不知情时压缩，中间那段信息就丢了。把它和 `postCompactCleanup` 并排看，恰好是一对反例：

| 文件 | 默认值 | 默认指向 | 后果 |
| --- | --- | --- | --- |
| `postCompactCleanup.ts` | `undefined` = 主线程 | **最危险**的一侧 | 忘了传参 → 多清全局状态 |
| `compactWarningState.ts` | `false` = 不抑制 | **最安全**的一侧 | 忘了设 → 多显示一个警告 |

同一个设计问题的两个答案。判据不是「哪个更常见」，而是「**两侧代价是否对称**」：多清一次主线程缓存可能让 CLAUDE.md 静默不重载；多显示一个警告只是让用户多看一眼。

## 5. 核心问题：三个小文件，各解决「大问题的一小块」

| 文件 | 大问题 | 它负责的那一小块 | 不负责什么 |
| --- | --- | --- | --- |
| `compactWarningState.ts` | 压缩会打断用户的心智模型 | **压缩前**：警告的可见性——何时藏、何时恢复 | 不算 token、不判阈值、不渲染 |
| `grouping.ts` | 压缩要砍历史，砍错就 400 | **压缩中**：刀口位置——按 API 轮次切 | 不估 token、不决定砍几组 |
| `postCompactCleanup.ts` | 压缩后缓存基于旧上下文，用下去就「数字对不上」 | **压缩后**：清哪些、留哪些、先清哪层 | 不压缩、不判断要不要压缩 |

三句话记住：**警告只在「成功之后」到「下次尝试之前」这个窗口里藏起来；分组只提供刀口、不提供刀；清理只清过期的东西，且清醒地留下两样不清。** 它们都小，不是因为简单，而是因为**各自只被允许管一个时刻的一件事**。判断一个文件的重要性，不看行数，看它在流水线上占的位置有没有别人替代。

## 6. 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| `grouping.ts` 是「压缩算法」 | 它一个 token 都不省，只切组。唯一的刀在 `compact.ts:278`，唯一调用方是 PTL 逃生舱 |
| 「清理当然越干净越好」 | 有两处**故意不清**：技能内容（下次压缩要用）、已发送技能清单（重发要 4K token）。`/clear` 反而要补清后者 |
| `compactWarningState.ts` 是「UI 组件状态」 | 它是纯 store，一格 React 都没有。React 在 `compactWarningHook.ts`——为了让服务层不把 React 拖进 print 启动路径 |
| `runPostCompactCleanup` 只在压缩后调用 | `/clear` 也调（`caches.ts:74`）。本质是「共享缓存的统一清理点」 |

2. 为什么 `runPostCompactCleanup` 的 `querySource` 是可选参数？不传会发生什么？
3. 哪两样东西「故意不清」？各自的理由是什么？
4. 只清 `getMemoryFiles` 的缓存、不清 `getUserContext` 的缓存，会导致什么静默故障？
5. `compactWarningState.ts` 与 `compactWarningHook.ts` 为什么拆开？合并后谁会受害？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. 压缩开始 → `clearCompactWarningSuppression()`（`microCompact.ts:259`，警告恢复）；压缩中 → `groupMessagesByApiRound()`（`compact.ts:257`，切组）；成功 → `suppressCompactWarning()`（警告隐藏）；随后 → `runPostCompactCleanup()`（清缓存）。
2. 主线程入口（`/compact`、`/clear`）不需要区分，传参冗余。不传 = 按主线程处理 = 会清 `context-collapse`、`getUserContext`、memory 缓存。危险在**子 agent 忘了传**：它与主线程同进程共享模块级状态，会把主线程的缓存清掉。
3. ① invoked skill 内容——下次压缩要放技能全文进附件，清了不可逆；② 已发送的技能清单——重发约 4K token 且是 `cache_creation` 单价，而能力、历史、变更通知三条都有别的通路。
4. 下一轮 `getUserContext()` 命中**外层**缓存直接返回旧值，永远走不到 `getMemoryFiles()`；「读了 memory 文件」这个动作不发生，`InstructionsLoaded` hook 不触发，「压缩后重载 CLAUDE.md」静默失效。没有报错，只有「改了 CLAUDE.md 却像没生效」。
5. 因为 `compactWarningState.ts` 必须 **React-free**：`microCompact.ts` 要 import 它的 setter，一旦这个文件 import React，就会把 React 拖进 print 模式启动路径。合并后受害的是**启动路径**——一个不渲染界面的模式被迫加载整个 React。

</details>
