## 3. 精读正文（行号为 source 原文行号）

### 3.0 统一接口：一个 context 进，一个四态结果出

23 个函数的签名一模一样：`(context: ValidationContext) => PermissionResult`。`ValidationContext`（103-116 行）装的是同一条命令的几种视图，差别只有一个字：**引号里的内容算不算数**——`unquotedContent` 保留双引号内容、剥掉单引号内容，`fullyUnquotedContent` 连双引号内容也剥，`unquotedKeepQuoteChars` 只留引号本身。同一个字符在引号里和引号外，bash 的解释完全不同，这是 3.2 节所有攻击的根源。返回值是四态（[`src/types/permissions.ts:251-266`](../../source/src/types/permissions.ts)），validator 只用三种。

### 3.1 主角一：`validateDangerousPatterns`——命令里还藏着第二条命令

```ts
// source/src/tools/BashTool/bashSecurity.ts:849-872（函数体）
  const { unquotedContent } = context

  // Special handling for backticks - check for UNESCAPED backticks only
  // Escaped backticks (e.g., \`) are safe and commonly used in SQL commands
  if (hasUnescapedChar(unquotedContent, '`')) {
    return {
      behavior: 'ask',
      message: 'Command contains backticks (`) for command substitution',
    }
  }

  // Other command substitution checks (include double-quoted content)
  for (const { pattern, message } of COMMAND_SUBSTITUTION_PATTERNS) {
    if (pattern.test(unquotedContent)) {
      logEvent('tengu_bash_security_check_triggered', {
        checkId:
          BASH_SECURITY_CHECK_IDS.DANGEROUS_PATTERNS_COMMAND_SUBSTITUTION,
        subId: 1,
      })
      return { behavior: 'ask', message: `Command contains ${message}` }
    }
  }

  return { behavior: 'passthrough', message: 'No dangerous patterns' }
```

**防什么**：命令替换。`echo hi` 只打印；`echo $(rm -rf ~)` 会在打印之前先执行另一条命令。这类写法（`$()`、反引号、`<()`、`>()`、`${}`）的共同特征是：**你以为是一个参数，其实是一个子进程**。

**怎么做**：反引号单独判——转义过的反引号合法（SQL 常见），只有没转义的才是替换。`hasUnescapedChar`（209-231）是手写扫描器，遇 `\` 跳两格（217-220 行：`i += 2 // Skip backslash and escaped character`）。其余 12 条模式在文件头 16-43 行，逐条列着已知的替换语法；其中第 4 条 `=cmd` 的注释写明理由：`=curl` 在 Zsh 里展开成 `/usr/bin/curl`，而规则引擎看到的基础命令是 `=curl`，`Bash(curl:*)` 的 deny 就被绕过了。**每条模式背后都有一个具体案例**，不是拍脑袋加的正则。

**输入输出**：输入 `unquotedContent`（双引号内容仍在，所以 `echo "$(id)"` 也抓得到），输出 `ask` 或 `passthrough`。**为什么是 `ask` 不是 `deny`**：`echo "$(date)"` 是完全正常的用法，这里的判断只到「**我拿不准**」——交给用户看一眼。这就是 fail-closed 的第一层含义：不确定就把决定权往上交，而不是自己拍板放行。

### 3.2 主角二：`validateCommentQuoteDesync`——我们和 bash 看的是同一行吗

```ts
// source/src/tools/BashTool/bashSecurity.ts:1975-1983（函数 JSDoc 里的攻击示例）
 * Example attack:
 *   echo "it's" # ' " <<'MARKER'\n
 *   rm -rf /\n
 *   MARKER
 * In bash: `#` starts a comment, `rm -rf /` executes on line 2.
 * In extractQuotedContent: the `'` at position 14 (after #) opens a single
 * quote, and the `'` before MARKER closes it. But the `'` after MARKER opens
 * ANOTHER single quote, swallowing the newline and `rm -rf /`, so
 * validateNewlines sees no unquoted newlines.
```

**这就是 parser differential（解析器差异）**：安全判断用我们自己的「引号追踪器」，真正执行的是 bash。两者对同一段文本的理解一旦分叉，后面所有检查都建立在错误前提上——`validateNewlines` 明明在跑，却「看不见」那个换行，因为追踪器以为自己在引号里。

有真正的语法树时，这个函数直接放行（1996-2000：`if (context.treeSitter) return { behavior: 'passthrough', … }`）——AST 里注释就是注释节点，这种 desync 根本不存在。只有退回正则路径才手工补偿：

```ts
// source/src/tools/BashTool/bashSecurity.ts:2049-2066
    // Unquoted `#` — in bash, this starts a comment. Check if the rest of
    // the line contains quote characters that would desync other trackers.
    if (char === '#') {
      const lineEnd = originalCommand.indexOf('\n', i)
      const commentText = originalCommand.slice(
        i + 1,
        lineEnd === -1 ? originalCommand.length : lineEnd,
      )
      if (/['"]/.test(commentText)) {
        logEvent('tengu_bash_security_check_triggered', {
          checkId: BASH_SECURITY_CHECK_IDS.COMMENT_QUOTE_DESYNC,
        })
        return {
          behavior: 'ask',
          message:
            'Command contains quote characters inside a # comment which can desync quote tracking',
        }
      }
```

**防什么**：不是某一种命令，而是「**解析前提被污染**」这件事本身。规则极简：看到未加引号的 `#`，且这一行后面还有引号字符 → 拦。

**为什么敢这么粗**：注释里带引号的命令合法但罕见；误伤代价是「多点一次 Yes」，漏放代价是「`rm -rf /` 直接执行」。原文 1985-1988 行写着：`Legitimate commands rarely have quote characters in their comments (and if they do, the user can approve manually).` **代价不对称，所以一律拦**——这是 fail-closed 的教科书式表述。

### 3.3 主角三：`validateZshDangerousCommands`——换个马甲还认得出来吗

```ts
// source/src/tools/BashTool/bashSecurity.ts:2194-2210（函数体前段）
  const ZSH_PRECOMMAND_MODIFIERS = new Set([
    'command',
    'builtin',
    'noglob',
    'nocorrect',
  ])
  const trimmed = originalCommand.trim()
  const tokens = trimmed.split(/\s+/)
  let baseCmd = ''
  for (const token of tokens) {
    // Skip env var assignments (VAR=value)
    if (/^[A-Za-z_]\w*=/.test(token)) continue
    // Skip Zsh precommand modifiers (they don't change what command runs)
    if (ZSH_PRECOMMAND_MODIFIERS.has(token)) continue
    baseCmd = token
    break
  }
```

拿到 `baseCmd` 之后就是一次集合查询（2212 行 `if (ZSH_DANGEROUS_COMMANDS.has(baseCmd))`），命中则返回 `ask`，文案是 `Command uses Zsh-specific '${baseCmd}' which can bypass security checks`。

**防什么**：Zsh 内建命令。清单在 45-75 行，共 **18** 个名字——`zmodload` 是总闸，后面跟着 `sysopen`/`syswrite`（裸文件 IO，绕过普通文件检查）、`ztcp`/`zsocket`（网络外传）、`zpty`（伪终端执行）、`zf_rm`/`zf_chmod`（内建版 `rm`/`chmod`，绕过「看的是哪个二进制」的判断）。

**怎么做**：这是全套里唯一真正的「**白名单遍历**」，但遍历前要先**归一化**：

| 你会怎么写 | 归一化后 | 若直接取第一个词 |
| --- | --- | --- |
| `FOO=bar zmodload zsh/system` | `zmodload` | `FOO=bar`（**漏**） |
| `command zmodload zsh/system` | `zmodload` | `command`（**漏**） |
| `builtin zmodload zsh/system` | `zmodload` | `builtin`（**漏**） |

环境变量赋值和 `command`/`builtin`/`noglob`/`nocorrect` 都不改变「最终执行的是谁」。**绕过防护最便宜的办法，从来不是写更复杂的攻击，而是在命令前面加一个词。**

函数末尾还有一条特判（2226 行）：`baseCmd === 'fc' && /\s-\S*e/.test(trimmed)`。`fc` 单独用只列历史（安全），带 `-e` 就是「用编辑器执行任意命令」（等于 `eval`）。**同一个命令，带不带某个 flag，安全性完全不同。**

### 3.4 三个 validator 怎么排队：调度器 2308-2407

调度器把 23 个 validator 分成两批。第一批「早期四件」（2308-2313：`validateEmpty`、`validateIncompleteCommands`、`validateSafeCommandSubstitution`、`validateGitCommit`）的结果一回来就立刻处理（2315-2332）：`allow` → 整条判 `passthrough`（只有空命令和 heredoc 白名单会走到这里）；`ask` → 加上 `isBashSecurityCheckForMisparsing` 标记后立即返回。

第二批是主战场（2348-2378），三个主角的位置：`validateCommentQuoteDesync` 在 **2355**，必须排在 `validateNewlines`（2364）**之前**——它修的是「换行看不见」这个前提，2353-2354 的注释写着 `Run comment-quote-desync BEFORE validateNewlines`；`validateDangerousPatterns` 在 **2367**（中段）；`validateZshDangerousCommands` 在 **2374**（靠后，紧挨最后的畸形 token 检查）。

更妙的是 2380-2407 的「延迟返回」。朴素写法是「谁先喊停就返回谁」，代码偏不：

```ts
// source/src/tools/BashTool/bashSecurity.ts:2392-2407
  let deferredNonMisparsingResult: PermissionResult | null = null
  for (const validator of validators) {
    const result = validator(context)
    if (result.behavior === 'ask') {
      if (nonMisparsingValidators.has(validator)) {
        if (deferredNonMisparsingResult === null) {
          deferredNonMisparsingResult = result
        }
        continue
      }
      return { ...result, isBashSecurityCheckForMisparsing: true as const }
    }
  }
  if (deferredNonMisparsingResult !== null) {
    return deferredNonMisparsingResult
  }
```

只有两个 validator 被登记为「非误解析」（2343-2346：`validateNewlines`、`validateRedirections`）。它们喊 `ask` 时**不返回，先记在小本子上继续跑**；若后面有「误解析类」也喊 `ask`，就用后者——因为后者带 `isBashSecurityCheckForMisparsing` 标记，会在更早的关口硬拦（2382-2387 给了个能穿过去的 payload：`cat safe.txt \; echo /etc/passwd > ./out`）。

**一句话**：**「我们可能看错了」比「命令里有可疑字符」更严重，所以前者的结论优先，哪怕它出现在列表更后面。**

### 3.5 parser differential 的兜底：分歧要记账

真有 tree-sitter 时，路径换到 `bashCommandIsSafeAsync_DEPRECATED`（2426）。它同时算两份结果——一份来自语法树，一份来自正则——**以语法树为准，但对不一致记账**：

```ts
// source/src/tools/BashTool/bashSecurity.ts:2503-2516
  if (!tsAnalysis.dangerousPatterns.hasHeredoc) {
    const hasDivergence =
      tsQuote.fullyUnquoted !== regexQuote.fullyUnquoted ||
      tsQuote.withDoubleQuotes !== regexQuote.withDoubleQuotes
    if (hasDivergence) {
      if (onDivergence) {
        onDivergence()
      } else {
        logEvent('tengu_tree_sitter_security_divergence', {
          quoteContextDivergence: true,
        })
      }
    }
  }
```

**这是 parser differential 的正确处理姿势**：两套解析器并行，分歧不静默吞掉，而是变成遥测事件。「两套都算、结果不同」本身就是最强的危险信号——今天它是日志，明天可能就是新的 `validate*`。

旁证（不展开）：真正的语法解析在 [`bashParser.ts`](../../annotated/src/utils/bash/bashParser.ts) 与 [`ParsedCommand.ts`](../../annotated/src/utils/bash/ParsedCommand.ts)。本文件里**没有**「管道解析器」这种东西，它管的是「拿不准就拦」。

## 4. 核心问题完整解答

对应 [学习路线](../00-零基础学习路线.md) L4-C 组卡片 C-3 的一问：「危险命令是怎么被识别的？」

**第一层：先归一化，再判断。** 命令进来先算几种视图（103-116），并剥掉「证明无害的 heredoc 体」（2293）。判断对象不是原始字符串，而是**去掉外壳后的骨架**。

**第二层：23 个 validator 各认一种绕过。** 本课读的三个各代表一类：`validateDangerousPatterns` 管「语法层面的第二条命令」；`validateCommentQuoteDesync` 管「解析前提被污染」；`validateZshDangerousCommands` 管「换名字绕过白名单」。

**第三层：只表态，不判决。** 45 处 `ask`、0 处 `deny`。产出是「我拿不准」，最终拦不拦由 C-2 的流水线和 C-4 的按钮决定。

**第四层：顺序即语义。** 早期四件的结论立刻生效（可提前放行，也可提前拦）；主列表里「误解析类」优先于「普通类」；普通类的 `ask` 延迟到列表末尾才兑现。

**为什么整体 fail-closed**：三处可验证——提前放行必须「PROVABLY safe」（292-294 行）；heredoc 剥离失败时「原始命令直接过全部 validator，这才是安全的方向」（2291-2292）；解析器分歧要记账（2503-2516）。**能证明安全才放行，不能证明就往上交。**

## 5. 常见误读

1. **「这个文件用 bash 解析器解析命令」**。主体是正则 + `shell-quote`，函数名自己都叫 `_DEPRECATED`（2254-2255 注释：`The primary gate is parseForSecurity (ast.ts)`）。tree-sitter 只在可用时增强（2467-2478），且**永远保留正则那份结果做对照**。
2. **「validator 会返回 deny」**。全文件 `behavior: 'deny'` 出现 **0** 次。把「被拦下来」等同于「被判 deny」，就解释不了 C-4 里用户为什么还能点 Yes。
3. **「注释里写的行号可以直接引用」**。2382 行注释说「非误解析的 ask 会在 `bashPermissions.ts:~1301-1303` 被丢弃」，实测该判断在 [`bashPermissions.ts:2094`](../../source/src/tools/BashTool/bashPermissions.ts)（同条件第二处在 2106）。**行号永远以 grep 为准。**

1. 用了三种：`allow`（早期放行）、`ask`、`passthrough`。没有 `deny`，因为 validator 只回答「这条命令我能不能看懂、要不要人看一眼」，判决权在权限流水线（规则 / hook / 工具自己的 `checkPermissions`）。
2. 前者剥单引号内容、**保留双引号内容**（所以 `echo "$(id)"` 仍能命中）；后者连双引号内容一起剥。选前者是因为双引号**不阻止**命令替换。
3. 防「注释里的引号把引号追踪器带跑」，让后面真正的命令被误认为「在引号里」而逃过换行检查。拦得粗是因为误判只多点一次 Yes——代价不对称，所以 fail-closed。
4. `validateZshDangerousCommands`：跳过 `FOO=bar` 与 `command`/`builtin`，拿到 `zmodload` 再查 `Set`。若只取第一个词，`baseCmd` 会是 `FOO=bar`，白名单查不到，**整条直接放行**。
5. 因为 `validateCarriageReturn` 属「误解析类」，`ask` 带 `isBashSecurityCheckForMisparsing`，能在更早关口硬拦；`validateNewlines` 被登记为「非误解析」（2343-2346），它的 `ask` 只是普通询问，必须让后面的强结论先跑完。
