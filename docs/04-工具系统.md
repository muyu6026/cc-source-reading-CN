## 4.1 工具到底是什么：发给模型的四样东西

先看请求是怎么拼的。构建 `tools[]` 的代码只有三段（[`utils/api.ts:160-181`](../annotated/src/utils/api.ts#L167)）：

```ts
// source/src/utils/api.ts:160-181（节选）
let input_schema = ('inputJSONSchema' in tool && tool.inputJSONSchema
  ? tool.inputJSONSchema
  : zodToJsonSchema(tool.inputSchema)) as Anthropic.Tool.InputSchema
if (!isAgentSwarmsEnabled()) input_schema = filterSwarmFieldsFromSchema(tool.name, input_schema)

base = {
  name: tool.name,
  description: await tool.prompt({ ... }),   // 注意：不是 tool.description()
  input_schema,
}
```

也就是说，模型眼里的一个工具**只有四个面**：名字、说明书（`prompt()` 的返回值）、参数表（Zod 转成的 JSON Schema）、以及上一轮 `tool_result` 的形状。TS 里的 `call()`、`isReadOnly()`、14 个渲染方法，模型一个都看不见——它们是给执行器和界面用的（[L4-A2 §3.3](L4/L4-A2-Tool契约字段.md)）。

拿两个真实工具对比，差异全在「说明书」上：

| 维度 | `BashTool` | `FileReadTool` |
| --- | --- | --- |
| 模型可见参数 | 5 个：`command`、`timeout`、`description`、`run_in_background`、`dangerouslyDisableSandbox` | 4 个：`file_path`、`offset`、`limit`、`pages` |
| 必填 | `command` | `file_path` |
| 描述写法 | 长文 + 正反例：`ls → "List files in current directory"`、`find ... -delete → "Find and delete..."`，还规定「不许用 complex/risk 这类词」 | 一句话 + 使用条件：`offset` 写「Only provide if the file is too large to read at once」 |
| 含运行时数字 | 有：`max ${getMaxTimeoutMs()}` → 600000 | 有：`Maximum ${PDF_MAX_PAGES_PER_READ} pages` |
| 内部参数 | `_simulatedSedEdit` 写进完整 schema 后**从模型可见版本剔除** | 无 |
| 结果形状 | 14 个字段的结构体（`stdout`/`stderr`/`interrupted`/`backgroundTaskId`…） | `type` 分支：`text` / `image` / `notebook` 等 |

两处值得停下来：

**① 参数描述就是产品文案。** `BashTool` 的 `description` 参数不是工具描述，而是「让模型给人类写一句命令说明」——schema 同时约束了模型的输出质量：*"Never use words like complex or risk in the description - just describe what it does."*（[`BashTool.tsx:231-241`](../annotated/src/tools/BashTool/BashTool.tsx#L350)）。这句话在 UI 上就是那行灰色小字，模型写歪了界面就难看。**schema 是给模型的说明书，也是给人看的界面的上游。**

**② schema 是安全边界。** 内部字段 `_simulatedSedEdit` 存在于完整 schema，却在面向模型的 `inputSchema` 里被 `.omit()` 掉，注释给了理由：暴露它就能「用一个无害命令配一次任意文件写」绕过权限与沙箱（[`BashTool.tsx:243-256`](../annotated/src/tools/BashTool/BashTool.tsx#L405)）。同理，`api.ts:173` 在 swarm 关闭时把相关字段滤掉；`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` 为真时 `run_in_background` 直接从 schema 消失（`BashTool.tsx:254-262`）——**工具还在，能力少一项。**

验证（真实输出）：

```bash
$ sed -n '228,250p' source/src/tools/BashTool/BashTool.tsx | grep -c "describe("
6
$ sed -n '227,243p' source/src/tools/FileReadTool/FileReadTool.ts | grep -c "describe("
4
```

Bash 的 6 个里有 1 个是内部字段 `_simulatedSedEdit`，模型实际看到 5 个；Read 的 4 个全部可见。`GrepTool` 还能再补一个角度——它的 `head_limit` 描述里直接写死了默认值和使用建议：「Defaults to 250… Pass 0 for unlimited (use sparingly — large result sets waste context)」（[`GrepTool.ts:80-83`](../annotated/src/tools/GrepTool/GrepTool.ts#L83)）。**默认值、上限、什么时候别用，全都写在 schema 里**，因为这是模型唯一会读的文档。

## 4.2 能力边界：清单之外，模型叫不动

「Agent 的能力边界 = 工具集边界」不是比喻，是执行层的硬检查。`StreamingToolExecutor.addTool` 拿到一个 `tool_use` 后第一件事是查表，查不到就直接回一条 `<tool_use_error>Error: No such tool available: ${block.name}</tool_use_error>`（[`StreamingToolExecutor.ts:77-100`](../annotated/src/services/tools/StreamingToolExecutor.ts#L143)）。

非流式路径还有第二道：`runToolUse` 先在当前工具池里找，找不到才去全量户口本里找，但**只有命中 `aliases`（旧名）才允许回退**——注释写得很清楚，这是给老 transcript 里的 `KillShell` 这类废弃名留的兼容（[`toolExecution.ts:346-355`](../annotated/src/services/tools/toolExecution.ts#L445)）。仍然找不到，就记一条 `No such tool available` 并返回错误块（`toolExecution.ts:369-375`）。

注意这里的分寸：**被开关藏起来的工具，用主名是叫不动的**，因为别名回退只认 `aliases` 数组。所以 4.4 那些条件加载不是「界面上藏起来」，是真的从能力集合里删掉。

工具池本身还要过三道加工才交给模型（[`assembleToolPool`](../annotated/src/tools.ts#L558)）：

```
getAllBaseTools()（54 个候选）
  → 去掉 specialTools（MCP 资源类，另路加入）
  → filterToolsByDenyRules（deny 规则整工具拒绝）
  → isEnabled() 逐个过滤
  → + MCP 工具，按名去重（内置优先）、分两段排序
```

最后那步排序是 prompt cache 契约：内置工具必须保持连续前缀，否则一个 MCP 工具插进中间，服务端缓存断点之后全部失效（[`tools.ts:354-366`](../annotated/src/tools.ts#L568)，[L4-A1 §2.6](L4/L4-A1-工具户口本.md) 有逐行）。

验证：

```bash
$ grep -rn "No such tool available" source/src/services/tools/ | wc -l
5
$ grep -n "fallbackTool.aliases?.includes" source/src/services/tools/toolExecution.ts
353:    if (fallbackTool && fallbackTool.aliases?.includes(toolName)) {
```

5 处命中里包含流式、非流式、合成错误三条路径——同一个语义在多处兜底，说明它是**协议级**约束，不是某一层的礼貌提示。

## 4.3 54 个工具的分类全景

先把数字钉死。`getAllBaseTools()` 数组里能数出 51 个名字，另有 `cronTools` 一次展开 3 个（增/删/查），合计 **54**：

```bash
$ sed -n '193,251p' source/src/tools.ts | grep -oE '[A-Za-z][A-Za-z0-9]*Tool\b' | sed 's/^get//' | sort -u | wc -l
51
$ grep -n "cronTools" source/src/tools.ts
29:const cronTools = feature('AGENT_TRIGGERS')
235:    ...cronTools,
```

按「这个工具对世界做了什么」分成 7 组（下表省略统一后缀 `Tool`，`†` = 快照里只有登记名、没有实现文件）：

| 组 | 数量 | 成员 | 判定依据（实读） |
| --- | --- | --- | --- |
| **只读检索** | 7 | FileRead、Glob、Grep、LSP、TaskOutput、ListMcpResources、ReadMcpResource | 七个都显式 `isReadOnly(){return true}`，且 `isConcurrencySafe(){return true}`（[`FileReadTool.ts:373-378`](../annotated/src/tools/FileReadTool/FileReadTool.ts#L386)） |
| **写入本地** | 4 | FileEdit、FileWrite、NotebookEdit、Config | 前三个**不写** `isReadOnly`，走默认 `false`；Config 按入参判：`value === undefined` 才是读（[`ConfigTool.ts:90-92`](../annotated/src/tools/ConfigTool/ConfigTool.ts#L92)） |
| **执行命令** | 3 | Bash、PowerShell、REPL | Bash 的 `isReadOnly(input)` 要解析 `command` 才答得出（[`BashTool.tsx:437`](../annotated/src/tools/BashTool/BashTool.tsx#L685)）——「是否只读」属于**某一次调用**，不属于工具 |
| **网络** | 4 | WebFetch、WebSearch、WebBrowser†、SubscribePR† | 都出网；WebFetch 结果受同一套落盘预算约束 |
| **编排/多智能体** | 16 | Agent、TaskStop、TaskCreate、TaskGet、TaskUpdate、TaskList、SendMessage、ListPeers†、TeamCreate、TeamDelete、Workflow†、CronCreate、CronDelete、CronList、RemoteTrigger、Monitor† | 都改「别的执行单元/时间线」，不改本地文件 |

| **元工具/环境** | 12 | ToolSearch、Snip†、CtxInspect†、TerminalCapture†、OverflowTest†、TestingPermission、Tungsten†、SuggestBackgroundPR†、VerifyPlanExecution†、EnterWorktree、ExitWorktree、Sleep | 改的是「工具怎么被找到」「上下文怎么被裁」「cwd/等待」这类运行环境 |

7 + 4 + 3 + 4 + 16 + 8 + 12 = **54**。

**① 54 个名字，磁盘上只找得到 40 个目录。** 剩下 14 个（就是上表带 `†` 的）是被 `feature('XXX')` 构建期开关做死代码消除（DCE）掉的：源码里引用了，但这个快照的构建没把它们打进包，文件也不在仓库里。逐个核对：

## 4.4 三种条件加载（外加一种「半加载」）

一个工具从「写在源码里」到「模型能用」要过四道不同的门，机制完全不同，混淆它们会得出相反结论。

### 机制一：`feature('XXX')`——构建期，关掉就不进包

`tools.ts` 里出现 17 次 `feature('`。它不是运行时 if：Bun 打包时把 `feature(...)` 折叠成常量，关闭分支整段代码不进入 bundle。最直接的证据就是上面那个「目录里只剩 prompt.ts」的 `SleepTool`。

```bash
$ grep -c "feature('" source/src/tools.ts
17
$ ls source/src/tools/SleepTool/
prompt.ts
```

### 机制二：`isEnabled()`——运行期，每次组池都问一遍

`getTools` 在最后一行统一过滤（[`tools.ts:325-326`](../annotated/src/tools.ts#L526)）：

```ts
const isEnabled = allowedTools.map(_ => _.isEnabled())
return allowedTools.filter((_, i) => isEnabled[i])
```

为什么先 `map` 再按位过滤，而不是 `filter(t => t.isEnabled())`？保证每个实现只调一次——有些 `isEnabled` 要读环境、查连接状态。真实条件五花八门：

| 工具 | 条件 | 出处 |
| --- | --- | --- |
| LSP | `isLspConnected()`，没连上语言服务器就不给 | [`LSPTool.ts:137-140`](../annotated/src/tools/LSPTool/LSPTool.ts#L141) |
| TeamCreate | `isAgentSwarmsEnabled()` | [`TeamCreateTool.ts:88-90`](../annotated/src/tools/TeamCreateTool/TeamCreateTool.ts#L93) |
| TodoWrite | `!isTodoV2Enabled()`——v2 一开，老工具**整个消失**，任务交给 Task* 四件套 | [`TodoWriteTool.ts:52-56`](../annotated/src/tools/TodoWriteTool/TodoWriteTool.ts#L56) |
| TaskCreate | `isTodoV2Enabled()`，与上一条严格互斥 | [`TaskCreateTool.ts:68-70`](../annotated/src/tools/TaskCreateTool/TaskCreateTool.ts#L75) |

这解释了一个常见困惑：「源码里明明有 TodoWrite，为什么我的会话里没有？」——不是 bug，是开关。全仓共 24 处 `isEnabled` 声明。

### 机制三：权限/模式过滤——池子里根本没有

`filterToolsByDenyRules` 在模型看到工具之前就按 deny 规则整条剔除，注释强调它用的是**和运行时权限检查同一个匹配器**，所以 `mcp__server` 这种前缀规则会在模型看见之前就把整台服务器的工具拿掉（[`tools.ts:253-269`](../annotated/src/tools.ts#L426)）。

模式层面还有一个更狠的：coordinator mode 下只剩 4 个工具（Agent、TaskStop、SendMessage、SyntheticOutput）加 PR 订阅类（[`constants/tools.ts:107-112`](../source/src/constants/tools.ts#L107)、[`toolPool.ts:36-42`](../source/src/utils/toolPool.ts#L36)）。

**但这里有一处必须如实说**：`mergeAndFilterTools` 的签名收了 `mode: ToolPermissionContext['mode']`，函数体里却**一次都没用**（[`toolPool.ts:55-77`](../source/src/utils/toolPool.ts#L55)）：

```bash
$ grep -n "mode" source/src/utils/toolPool.ts
28: * Filters a tool array to the set allowed in coordinator mode.
44: * Pure function that merges tool pools and applies coordinator mode filtering.
52: * @param mode - The permission context mode.
58:  mode: ToolPermissionContext['mode'],
```

三行注释 + 一行形参，正文零引用。也就是说：**「权限模式改变工具清单」这个钩子已经预留，但当前快照里没接线**；真正生效的是 deny 规则和 coordinator 过滤。读源码时看到参数就假定它有用，是最容易犯的错。

还有一种「半加载」：工具在池子里，参数表被裁（`BashTool` 的 `run_in_background`、swarm 字段），**能力被削了一角，但「有没有这个工具」的答案仍是有**（见 4.1 ②）。

## 4.5 结果整形：谁在截断，截到多少

工具返回的不是字符串，是 `ToolResult<T>`（[`Tool.ts:321-336`](../annotated/src/Tool.ts#L859)）：

```ts
export type ToolResult<T> = {
  data: T
  newMessages?: (UserMessage | AssistantMessage | AttachmentMessage | SystemMessage)[]
  contextModifier?: (context: ToolUseContext) => ToolUseContext  // 仅非并发安全工具生效
  mcpMeta?: { _meta?: ...; structuredContent?: ... }
}
```

`data` 是工具自己的 `Output` 类型，形状由工具定（Bash 是 14 个字段的结构体）。要进上下文，还得过 `mapToolResultToToolResultBlockParam` 映射成 API 的 `tool_result` 块——**这是「结果整形」的第一层，也是唯一由工具作者负责的一层**。

第 0 层是工具自己的责任，之后四层由框架统一处理，顺序与数字如下：

| 层 | 谁做 | 阈值/动作 | 出处 |
| --- | --- | --- | --- |
| 0 工具内自截 | 各工具自己 | Grep 默认 `head_limit=250`，`0` 才无限 | [`GrepTool.ts:108-127`](../annotated/src/tools/GrepTool/GrepTool.ts#L114) |
| 1 空结果补齐 | `maybePersistLargeToolResult` | 内容为空 → 换成 `(ToolName completed with no output)` | [`toolResultStorage.ts:281-292`](../annotated/src/utils/toolResultStorage.ts#L293) |
| 2 单结果落盘 | 同上 | `min(声明值, 50_000)` 字符，写文件 + 2,000 字符预览 | [`toolResultStorage.ts:55-77`](../annotated/src/utils/toolResultStorage.ts#L84)、`PREVIEW_SIZE_BYTES=2000`（`:109`） |
| 3 单条消息预算 | `enforceToolResultBudget` | 一条 user 消息里所有 `tool_result` 合计 > 200,000 字符 → 从最大的开始落盘 | [`toolLimits.ts:49`](../source/src/constants/toolLimits.ts#L49)、[`toolResultStorage.ts:769`](../annotated/src/utils/toolResultStorage.ts#L812) |
| 4 历史层清理 | microcompact | 60 分钟前的旧结果换成墓碑字符串 | 见 [11 上下文压缩 §11.8](11-上下文压缩.md) |

第 2 层有个反直觉的设计：**落盘不是截断**。超限内容原样写进 `tool-results/<tool_use_id>.txt`，模型收到的是「太大（多大）+ 文件路径 + 前 2,000 字符预览」（[`toolResultStorage.ts:193-199`](../annotated/src/utils/toolResultStorage.ts#L211)）。模型需要细节就再 Read 一次——**信息没丢，只是从上下文挪到了磁盘**。

阈值是「声明值」和「全局值」取小，所以清单里写 `100_000` 的工具实际只有 50,000 额度：

```bash
$ grep -h "maxResultSizeChars" source/src/tools/*/*.ts* | sed 's/^ *//' | sort | uniq -c | sort -rn
     36 maxResultSizeChars: 100_000,
      2 maxResultSizeChars: 30_000,
      1 maxResultSizeChars: Infinity,
      1 maxResultSizeChars: 20_000,
      1 maxResultSizeChars: 10_000,
```

41 个声明（其余工具走默认）。三个例外值得记：

- **Bash / PowerShell 是 30,000**，Grep 是 20,000——命令输出最容易炸上下文，主动收紧。
- **Read 是 `Infinity`，故意永不落盘**。理由写在批注版：Read 的输出本来就有 `maxTokens` 兜底，再落盘让模型 Read 回来是循环（[`FileReadTool.ts:350-351`](../annotated/src/tools/FileReadTool/FileReadTool.ts#L351)）。所以 `Infinity` 在 `getPersistenceThreshold` 里是**优先级最高的退出开关**，连远程配置都覆盖不了（`toolResultStorage.ts:60-66`）。
- **单条消息预算会把「每个都不超」的工具一起收拾**：10 个并发工具各返回 40K，单看都合规，合起来 400K，就得落盘几个（`toolLimits.ts:39-49` 的注释就是这么写的）。

为什么必须截断，三条理由都能在代码里找到：

1. **窗口**：200K 上下文里塞两个大结果，历史就没地方了（阈值体系见 [11 章 §11.1](11-上下文压缩.md)）。
2. **缓存**：落盘决策一旦做出就**冻结**——`enforceToolResultBudget` 用 `seenIds` 记住哪些结果被替换过，之后每轮只重放同一个预览字符串，绝不改主意，否则前缀一变整个 prompt cache 失效（[`toolResultStorage.ts:743-756`](../annotated/src/utils/toolResultStorage.ts#L812)）。连「同一个工具这轮没超、下轮超了」也不许翻案。
3. **模型行为**：空 `tool_result` 会让某些模型把结尾当成轮次边界、直接停止输出，所以宁可塞一句 `(X completed with no output)` 也不能留空（`toolResultStorage.ts:281-289` 的注释给了完整来龙去脉）。

> **深入**：`FileReadTool/limits.ts` 那三道闸（行数/字节/token）与 `prompt.ts` 怎么把上限念给模型听，见 [L4-A3](L4/L4-A3-最小工具的两块骨头.md)。

## 4.6 加一个新工具：六步清单

以做一个 `MyTool` 为例，每一步都落到真实文件。

**① 建目录，照现成的最小结构抄。** 工具目录没有脚手架，就是手写：

```bash
$ ls source/src/tools/GlobTool/ source/src/tools/FileReadTool/
source/src/tools/GlobTool/:
GlobTool.ts  UI.tsx  prompt.ts
source/src/tools/FileReadTool/:
FileReadTool.ts  UI.tsx  imageProcessor.ts  limits.ts  prompt.ts
```

最小三件套：`MyTool.ts`（工具对象）、`prompt.ts`（说明书常量）、`UI.tsx`（渲染函数）。需要阈值就加 `limits.ts`（学 `FileReadTool`），需要被别处引用的常量就加 `constants.ts`（`TodoWriteTool/constants.ts` 就被系统提示词引用），工具名单独放 `toolName.ts`（`BashTool/toolName.ts`）。

**② 实现契约，最少 8 个成员。** `buildTool({...})` 会补 7 个默认方法，剩下必须自己写：`name`、`description`、`prompt`、`inputSchema`、`call`、`maxResultSizeChars`、`mapToolResultToToolResultBlockParam`、`renderToolUseMessage`（[`Tool.ts:757-792`](../annotated/src/Tool.ts#L1923)，逐字段见 [L4-A2 §3.4](L4/L4-A2-Tool契约字段.md)）。

**③ `checkPermissions` 千万别省。** 默认实现是 `return { behavior: 'allow' }`（`Tool.ts:757-769`），而权限流水线会把这个 `allow` 当「工具实现已批准」直接采纳——只有 `passthrough` 才会被转成 `ask`（[`permissions.ts:1301-1312`](../annotated/src/utils/permissions/permissions.ts#L1340)）。换句话说：**不写 = 默认放行**。要收紧就自己返回 `deny`/`ask`，照 `ConfigTool` 的写法（读配置放行、写配置走确认）。

**④ 注册。** 在 `tools.ts` 加 `import`，然后在 `getAllBaseTools()` 的数组里加一行；有开关就包成 `...(cond ? [MyTool] : [])`。位置有讲究：清单顺序进系统提示词，进 prompt cache，改完要同步服务端的 Statsig 配置（[`tools.ts:190-192`](../annotated/src/tools.ts#L307)）。

**⑤ 权限规则不用中心注册。** 规则对象的 `toolName` 只是 `string`（[`types/permissions.ts:68`](../source/src/types/permissions.ts#L68)），匹配按名字走，新增工具自动可被 `allow`/`deny` 规则命中。需要「`MyTool(npm publish:*)` 这种细粒度」才在 `checkPermissions` 里用 `preparePermissionMatcher` 自己做。

**⑥ 加 prompt——两处，不是一处。** 一处是 `tool.prompt()`（工具自己的说明书，进 `tools[].description`）；另一处是**系统提示词里的工具偏好**：`providedToolSubitems` 明确写着「读文件用 Read 而不是 cat」「搜索用 Glob 而不是 find」（[`constants/prompts.ts:290-301`](../annotated/src/constants/prompts.ts#L682)）。新工具如果和 Bash 有功能重叠而不在这里登记，模型就永远不会优先用它——**工具存在 ≠ 工具会被用**（反面教材见 4.3 的 `SleepTool`：说明书在，能力不在）。

## 4.7 失败模式：抛异常、超时、中断、并发

**工具抛异常怎么办？** `tool.call()` 包在 `try/catch` 里，catch 分支不重抛，而是造一条 `is_error: true` 的 `tool_result` 返回给模型（[`toolExecution.ts:1589-1726`](../annotated/src/services/tools/toolExecution.ts#L1882)）。

这是整个工具系统最重要的一条设计：**异常被降级成「结果」，回合继续**。模型看到错误文本，可以改参数重试、换个工具、或者向用户解释。`AbortError` 特殊：不写错误日志、不进 `tengu_tool_use_error` 统计（`toolExecution.ts:1631`），因为用户按 ESC 不是故障。

错误分类也专门写了函数（[`toolExecution.ts:150-172`](../annotated/src/services/tools/toolExecution.ts#L205)）。原因很实在：压缩后的构建里 `error.constructor.name` 会变成 `nJT` 这种三字符乱码，所以优先取 `TelemetrySafeError` 的白名单消息、其次取 fs 错误码（`ENOENT`/`EACCES`）、再次取稳定的 `error.name`，最后才退回 `"Error"`。

**超时。** 超时不是框架统一管的，是**工具自己的参数**。Bash 的 `timeout` 写在 schema 里，默认 2 分钟、上限 10 分钟，且保证「上限 ≥ 默认」：

```bash
$ grep -n "DEFAULT_TIMEOUT_MS\|MAX_TIMEOUT_MS" source/src/utils/timeouts.ts
2:const DEFAULT_TIMEOUT_MS = 120_000 // 2 minutes
3:const MAX_TIMEOUT_MS = 600_000 // 10 minutes
```

BashTool 里 `const timeoutMs = timeout || getDefaultTimeoutMs()`（[`BashTool.tsx:860`](../annotated/src/tools/BashTool/BashTool.tsx#L1358)）——**永远会传一个值下去**，所以 `Shell.ts:44` 那个 `DEFAULT_TIMEOUT = 30 * 60 * 1000`（30 分钟）在 Bash 路径上永远轮不到（[`Shell.ts:203`](../annotated/src/utils/Shell.ts#L203) 的 `timeout || DEFAULT_TIMEOUT` 只是给别的调用方兜底）。读常量时看到两个默认值，先确认调用方有没有传参，否则会把 30 分钟当成真实默认。

**中断。** 用户在工具跑一半时发新消息，行为由 `interruptBehavior()` 决定：`'cancel'` 丢弃结果、`'block'` 让新消息等（默认 `block`，[`StreamingToolExecutor.ts:216-236`](../annotated/src/services/tools/StreamingToolExecutor.ts#L329)）。取消时不是静默丢弃，而是补一条合成结果 `User rejected tool use`，保证每个 `tool_use` 都有配对的 `tool_result`——否则下一次请求直接 400。

**并发。** 两条规则（[`StreamingToolExecutor.ts:196-215`](../annotated/src/services/tools/StreamingToolExecutor.ts#L196)）：

```ts
private canExecuteTool(isConcurrencySafe: boolean): boolean {
  const executingTools = this.tools.filter(t => t.status === 'executing')
  return executingTools.length === 0 ||
    (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))
}
```

- 并发安全工具之间可以并行；一旦有非并发安全工具在跑，别人都得等；
- 队列按**收到顺序**推进，遇到第一个非并发安全工具就 `break`——后面的不能插队，否则结果顺序会乱（结果本身按收到顺序缓冲输出）。

上限 10，可用 `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` 覆盖（[`toolOrchestration.ts:8-13`](../annotated/src/services/tools/toolOrchestration.ts#L31)）。最细的一条：**只有 Bash 报错会取消同批兄弟**，注释理由是命令之间常有隐式依赖（`mkdir` 失败后面全无意义），而 Read/WebFetch 互相独立，一个失败不该连坐（[`StreamingToolExecutor.ts:475-482`](../annotated/src/services/tools/StreamingToolExecutor.ts#L475)）。被取消的兄弟收到的是 `Cancelled: parallel tool call Bash(...) errored`，不是自己的错误。

> **深入**：`runToolUse` 的九道关（校验、hook、权限、执行、映射）与两个「慢」阈值，见 [L4-A4](L4/L4-A4-工具调用的几道关.md)。

## 4.8 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 「工具描述」就是源码里那个 `description` 字段 | 模型读的是 `prompt()` 的返回值；`description(input)` 是**这一次调用**的一句话，给人和权限 UI 看 |
| schema 只是类型校验 | 它同时是说明书（写默认值/使用建议）、安全边界（内部字段被 omit）、环境开关（按 flag 删参数） |
| 54 个工具都能在 `tools/` 下读到 | 只有 40 个目录，其中 `SleepTool` 仅剩 `prompt.ts`；14 个被构建期 DCE |
| 大输出会被截断，信息就丢了 | 是**落盘 + 预览**：全文进 `tool-results/<id>.txt`，模型可以再 Read 回来 |
| 权限模式会改变工具清单 | `mergeAndFilterTools` 收了 `mode` 参数但**函数体没用**；实际起作用的是 deny 规则与 coordinator 过滤 |

## 4.9 一篇小结

- 模型看到的工具只有四样：名字、`prompt()` 说明书、`input_schema`、`tool_result` 形状。其余 40 多个成员都是给执行器和界面的。
- 能力边界是硬边界：查不到工具名就回 `No such tool available`，别名回退只认 `aliases`。
- 54 个工具分 7 组（7/4/3/4/16/8/12）；磁盘上 40 个目录，14 个被 `feature()` 消掉。
- 四道加载门：构建期 `feature`、运行期 `isEnabled`、权限规则过滤、schema 裁剪。`mode` 参数是预留未接线。
- 结果整形：工具内自截（Grep 250）+ 框架四层（空结果补齐 → 单结果 `min(声明, 50K)` 落盘 → 单条消息 200K 预算 → 历史层 microcompact）。落盘决策一旦做出就冻结，为了 prompt cache。
- 失败被降级成结果：异常 → `is_error` 结果块；中断 → 合成 `User rejected tool use`；Bash 报错连坐同批。
- 加工具六步：目录、契约（含 `checkPermissions`，不写=放行）、注册、规则、两处 prompt、缓存排序。

## 4.10 合书自测

1. 模型眼里的工具只有哪四样？`description()` 和 `prompt()` 分别给谁看？
2. 54 个工具按行为分 7 组，写出组名和数量；为什么磁盘上只找到 40 个目录？
3. 一个工具「被隐藏」有哪几种方式？`mergeAndFilterTools` 的 `mode` 参数说明了什么？
4. Grep 默认返回多少条？单结果落盘的阈值是多少、为什么 Read 是例外？落盘后模型怎么拿回全文？
5. 新增工具时如果完全不写 `checkPermissions`，会发生什么？为什么？
6. 同批并行调用里，Read 失败和 Bash 失败对兄弟工具的影响有何不同？为什么？

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. `name`、`description`（由 `tool.prompt()` 填入 `tools[].description`）、`input_schema`（Zod 经 `zodToJsonSchema` 转换）、以及上一轮 `tool_result` 的形状（`utils/api.ts:160-181`）。`description(input, options)` 描述这一次调用，给人和权限 UI；`prompt(options)` 是工具说明书，给模型，每会话算一次进缓存。
2. 只读检索 7、写入本地 4、执行命令 3、网络 4、编排/多智能体 16、交互/模式 8、元工具/环境 12（合计 54）。14 个由 `feature('XXX')` 控制，构建期被死代码消除，文件不在快照里；另外 `SleepTool/` 只剩 `prompt.ts`（`tools.ts:25-28` 用 `feature('PROACTIVE') || feature('KAIROS')` 包着 `require`）。
3. 四种：构建期 `feature()` 不进包；运行期 `isEnabled()` 过滤（LSP 连接、Team 开关、Todo v1/v2 互斥）；权限 deny 规则整条剔除、coordinator 只留 4 个；以及 schema 层 `.omit()` 掉参数。`mode` 出现在签名和注释里、函数体零引用（`toolPool.ts:55-77`），说明「按模式裁剪」只是预留钩子。
4. 默认 250（`DEFAULT_HEAD_LIMIT`，传 0 才无限）。单结果阈值 `min(工具声明值, 50_000)`；Read 声明 `Infinity` 是主动退出落盘，因为它自己用 `maxTokens` 兜底，落盘再 Read 会形成循环。落盘后模型拿到「大小 + 文件路径 + 前 2,000 字符预览」，需要细节自己 Read 文件。
5. 会被默认放行。`TOOL_DEFAULTS.checkPermissions` 返回 `{behavior:'allow'}`，而权限流水线只把 `passthrough` 转成 `ask`（`permissions.ts:1301-1312`），`allow` 被当作工具实现已批准直接采纳。所以新工具必须自己实现 `checkPermissions`，或至少配一条 ask 规则。
6. Read 失败只影响自己；Bash 失败会把 `siblingAbortController` 一起 abort，同批其他工具收到 `Cancelled: parallel tool call ... errored`（`StreamingToolExecutor.ts:475-482`）。理由是 shell 命令之间常有隐式依赖，而读类工具互相独立。
