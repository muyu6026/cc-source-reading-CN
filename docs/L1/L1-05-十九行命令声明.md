## 1. 精读正文

全文件 19 行，逐字摘录：

```ts
1  │ /**
2  │  * Clear command - minimal metadata only.
3  │  * Implementation is lazy-loaded from clear.ts to reduce startup time.
4  │  * Utility functions:
5  │  * - clearSessionCaches: import from './clear/caches.js'
6  │  * - clearConversation: import from './clear/conversation.js'
7  │  */
8  │ import type { Command } from '../../commands.js'
9  │
10 │ const clear = {
11 │   type: 'local',
12 │   name: 'clear',
13 │   description: 'Clear conversation history and free up context',
14 │   aliases: ['reset', 'new'],
15 │   supportsNonInteractive: false, // Should just create a new session
16 │   load: () => import('./clear.js'),
17 │ } satisfies Command
18 │
19 │ export default clear
```

### 1.1 第 1–7 行：JSDoc 块注释，一份「目录导读」

```ts
1  │ /**
2  │  * Clear command - minimal metadata only.
3  │  * Implementation is lazy-loaded from clear.ts to reduce startup time.
```

`/**` 开头的块注释（L0 讲义 §1.2）：「clear 命令——**只放最精简的元信息**。实现从 clear.ts **惰性加载**，目的是缩短启动时间。」第 4–6 行还列了两个工具函数的出处（`clearSessionCaches`、`clearConversation`）。**注释先告诉你：真正干活的不在这个文件里。**

### 1.2 第 8 行：唯一的一行 import，而且是 type-only

```ts
8  │ import type { Command } from '../../commands.js'
```

**中文念法**：「从上上级的 `commands.js` 里，只拿 `Command` 这个**类型**。」`import type` 编译后**整行消失**（L0-02 的主题）——为了一个类型标签，不会把 754 行的 `commands.ts` 拖进运行时。这行 import 不产生任何真实依赖。

### 1.3 第 10–17 行：命令对象本体，6 个字段逐个讲

```ts
10 │ const clear = {
```

一个对象字面量，最后用 `satisfies Command` 验收（L0-04 的主题：**按 `Command` 的规矩检查我，但别把类型改宽**——写错字段名编译期立刻报错）。`Command` 类型定义在 `source/src/types/command.ts` 第 205 行（实测）：`Command = CommandBase & (PromptCommand | LocalCommand | LocalJSXCommand)`——斜杠命令分三类，本命令是 `local`（本地执行、返回文本）那类。

**字段 1（第 11 行）`type: 'local'`** —— 决定「谁来执行它」。`'local'` = 本地函数执行、返回文本（不走模型）。对应下一课 `clear.ts` 里那个 `call` 函数。

**字段 2（第 12 行）`name: 'clear'`** —— 命令名。用户敲 `/clear` 里的 `clear` 就是它。

**字段 3（第 13 行）`description`** —— 一句英文说明「清空对话历史，释放上下文空间」。这行文字就是你在输入框敲 `/` 时补全列表里跟在 `/clear` 后面的那句说明，**直接展示给用户**。

**字段 4（第 14 行）`aliases: ['reset', 'new']`** —— 别名数组。所以 `/reset`、`/new`、`/clear` 是同一个命令的三个名字。`'new'` 这个名字透露了设计意图：`/clear` 的语义其实是「**开一个新会话**」，而不是「删除已有的东西」。

**字段 5（第 15 行）`supportsNonInteractive: false`** —— 「不支持非交互模式」。行尾注释 `// Should just create a new session`：「应该（由外部）新建一个会话」。非交互模式（`-p` / headless）是一次性执行、没有「会话」概念，清空上下文无从谈起。实测 `source/src/main.tsx` 第 2622 行的过滤逻辑：只有 `command.type === 'local' && command.supportsNonInteractive` 的命令才进入非交互命令列表——`false` 意味着 `-p` 模式下 `/clear` **根本不在列表里**。

**字段 6（第 16 行）`load: () => import('./clear.js')`** —— 本文件最讲究的一行。值是一个**箭头函数**（收零个参数），函数体是**动态导入** `import('./clear.js')`——讲义 §4.2：`import()` 是**函数调用**，不是文件加载时执行的 import 语句。启动时这个字段只是一个**没被调用的函数对象**，7+251 行的实现一字节都没加载；只有谁调了 `load()`，谁才触发加载。

### 1.4 第 19 行：默认导出，注册进命令总表

```ts
19 │ export default clear
```

**中文念法**：「把 `clear` 对象作为本文件的主输出交出去。」实测 `source/src/commands.ts` 第 9 行：

```ts
9 │ import clear from './commands/clear/index.js'
```

启动时命令系统把全仓几十个这样的「门牌」对象收集进一张总表（`commands.ts`，754 行，实测行数），你敲 `/` 时弹出的补全列表就是查这张表。

## 2. 核心问题（路线卡片原题的完整解答）

### 2.1 这个文件干的唯一一件事是什么？

> **声明 `/clear` 这个命令「存在」，并且把它的实现「延迟」到真正被使用时才加载。**

拆开说：它不清理任何东西，不做任何实际动作；它只是把 6 个字段打包成一个对象交给命令总表。总表靠它知道「有 `/clear` 这个命令、叫什么、干什么、能不能在 headless 用、**去哪里加载实现**」。全部实际工作都发生在 `load` 字段指向的 `clear.js` 里——那是下一课的内容。

### 2.2 不看文件，默写这 6 个字段（自测原题）

| 字段 | 值 | 作用 |
| --- | --- | --- |
| `type` | `'local'` | 本地执行、返回文本（不走模型） |
| `name` | `'clear'` | 命令名，用户敲 `/clear` |
| `description` | `'Clear conversation history and free up context'` | 补全列表里的说明文字 |
| `aliases` | `['reset', 'new']` | 两个别名，同一条命令 |
| `supportsNonInteractive` | `false` | `-p` 模式下不可用 |
| `load` | `() => import('./clear.js')` | 惰性加载真正的实现 |

### 2.3 `load` 惰性加载的收益是什么？

启动要登记**几十个**斜杠命令（敲 `/` 要能补全它们）。如果每个命令的**实现**都在启动时顶层 `import`，光启动就要解析几十个命令的全部依赖——而绝大多数命令这一次会话里根本不会被用到。拆成两层后：

- **启动时**只加载每个命令几十字节的元信息（本文件 19 行 + 唯一类型 import 编译后消失）；
- **用到时**（用户敲了 `/clear`）才通过 `load()` 加载那 7+251 行的实现。

实测调用现场在 `source/src/utils/processUserInput/processSlashCommand.tsx` 第 668 行：

```ts
668 │             const mod = await command.load();
```

用户敲 `/clear` 之后走到这一行，`await` 等动态导入完成，接着第 669 行 `await mod.call(args, context)` 才真正执行命令。**「可能用不上」的代价，被推迟到了确认要用那一刻**——这是本仓库从命令系统到 `cli.tsx` 反复出现的同一思路。

## 3. 常见误读

**误读 1：以为 `import type { Command }` 会把 754 行的 `commands.ts` 加载进来。**
`import type` 编译后整行消失，运行时不存在任何依赖。它只是给编译器看的「验收标准」。写成不带 `type` 的普通 import 才会产生真实加载。

**误读 2：以为 `load` 字段的值是「clear.js 模块」。**
它是一个**函数**。函数没被调用时，`import('./clear.js')` 一个字都没执行。把 `load` 从「函数」错当成「模块」，就无法理解「为什么启动时加载它没负担」。

**误读 3：以为 `supportsNonInteractive: false` 只是「提示一下」。**
它是硬门禁：`main.tsx:2622` 按这个字段过滤非交互命令列表，`false` 的命令在 `-p` 模式下**完全不存在**，敲了也匹配不到。命令的每项「能力」都是被外部逐个门禁的，不是自己声明的权限。

## 5. 合书自测

**1. 一句话说清这个文件「做了什么、没做什么」。**

<details>
<summary>参考答案</summary>

做了：声明 `/clear` 命令存在（6 个字段）并注册进命令总表，实现挂在惰性加载函数后面。没做：任何实际的清理动作——那些都在 `clear.ts` 和它依赖的文件里。

</details>

**2. 默写 6 个字段的名字和各自的值。**

<details>
<summary>参考答案</summary>

`type: 'local'`、`name: 'clear'`、`description: 'Clear conversation history and free up context'`、`aliases: ['reset', 'new']`、`supportsNonInteractive: false`、`load: () => import('./clear.js')`。

</details>

**3. 为什么 19 行的文件启动时「没负担」，实现却重达几百行？**

<details>
<summary>参考答案</summary>

本文件没有静态 import 任何实现代码（唯一的 `import type` 编译后消失）；实现通过 `load: () => import('./clear.js')` 挂在箭头函数里，启动时只是一个未被调用的函数对象，敲 `/clear` 走到 `processSlashCommand.tsx:668` 的 `await command.load()` 时才真正加载。

</details>

**4. `/reset` 和 `/new` 敲下去之后发生的事和 `/clear` 有区别吗？**

<details>
<summary>参考答案</summary>

没有。它们只是同一个命令对象 `aliases` 数组里的两个别名，最终指向同一个 `call`。`new` 这个名字体现设计语义：/clear 是「开新会话」。

</details>

**5. `satisfies Command` 换成 `: Command` 会损失什么？**

<details>
<summary>参考答案</summary>

`: Command` 会把对象类型拓宽成 `Command` 联合类型，`clear.type` 不再精确为 `'local'`、`clear.name` 不再精确为 `'clear'`；`satisfies` 只校验形状、保留字面量窄类型，写错字段名照样编译期报错。

</details>
