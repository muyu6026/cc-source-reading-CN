## 1. 精读正文

全文件只有 2 行，先一字不差地摆出来：

```ts
1 │ // Here to break circular dependency from prompt.ts
2 │ export const BASH_TOOL_NAME = 'Bash'
```

### 1.1 第 1 行：一句注释，说明「我为什么存在」

```ts
1 │ // Here to break circular dependency from prompt.ts
```

- **`//`** —— 行注释，读作「以下到行尾是给人看的，机器不管」。
- **`Here to break circular dependency`** —— 「我在这里是为了打断循环依赖」。
- **`from prompt.ts`** —— 「这个循环的来源是 `prompt.ts` 这个文件」。

**中文念法**：

> 「这个文件存在，是为了替 `prompt.ts` 打断一个循环依赖。」

这句话不是随手写的。在 50 万行的仓库里，第一行注释就是「存在理由声明」的小文件有一批：`FileEditTool/constants.ts` 第 1 行写的是 `// In its own file to avoid circular dependencies`（为了避免循环依赖而单独成文件），`NotebookEditTool/constants.ts` 也是同一句话。**遇到「小得莫名其妙」的文件，先读它的第一行注释，十有八九是这类解耦路标。**

### 1.2 第 2 行：一个具名导出的常量

```ts
2 │ export const BASH_TOOL_NAME = 'Bash'
```

逐个词拆：

- **`export`** —— 交出去，允许别的文件导入。
- **`const`** —— 常量声明，之后不允许再对 `BASH_TOOL_NAME` 重新赋值。
- **`BASH_TOOL_NAME`** —— 名字。具名导出的名字是「契约」：导入方必须一字不差写它（想改名必须显式写 `as`，见 L0-03）。
- **`= 'Bash'`** —— 值是字符串 `'Bash'`。这是 Bash 工具在界面、权限规则、提示词里统一使用的名字。

**中文念法**：

> 「导出一个常量 `BASH_TOOL_NAME`，值是 `'Bash'`；谁要用，就按这个名字来取。」

全文件没有 `import`——它是依赖图最底端的「叶子」：谁都可以引用它，它谁都不引用。这个形状正是它能「打断循环」的前提，下面细讲。

## 2. 核心问题：一个字符串常量为什么要单独成一个文件？

这是路线图卡片里的原问题。答案分三步：先看死结怎么形成，再看拆开怎么活，最后看证据。

### 2.1 循环依赖的死结是怎么形成的

先假设不拆：把 `BASH_TOOL_NAME = 'Bash'` 直接写在 Bash 工具的主文件 `BashTool.tsx` 里。这时有两个已存在的事实：

- `BashTool.tsx` 需要 `prompt.ts`——它第 45 行有 `import { getDefaultTimeoutMs, getMaxTimeoutMs, getSimplePrompt } from './prompt.js'`（实测）。
- `prompt.ts` 需要 `BASH_TOOL_NAME`——它拼提示词时要写工具名，于是得从某处导入这个常量。

常量若住在 `BashTool.tsx`，`prompt.ts` 就只能去导入 `BashTool.tsx`。于是依赖关系变成：

```
BashTool.tsx ──import──▶ prompt.ts
      ▲                     │
      └──────import─────────┘        ← 死结
```

**这就是循环依赖（circular dependency）**：A 要 B 的东西，B 又要 A 的东西。在文件层面它长这样——两个文件各自的 `import` 区里都能找到对方的路径。

死结在哪？模块系统加载文件要按依赖顺序：先用到的先加载。可现在「谁先」没有答案——加载 `BashTool.tsx` 要先加载 `prompt.ts`，加载 `prompt.ts` 又要先加载 `BashTool.tsx`，转一圈回到原点。轻则某个导入拿到 `undefined`（对方还没执行完，常量还没赋值），重则启动直接报错。而且这种错**不一定每次都出现**，跟加载顺序有关，是典型的「幽灵 bug」。

### 2.2 破法：把共用的东西提到第三个文件 C

标准解法是引入一个双方都依赖、自己谁也不依赖的第三方文件：

```
BashTool.tsx ──▶ toolName.ts ◀── prompt.ts
                      ▲
              常量住在这里（叶子：自己不 import 任何人）
```

- `toolName.ts` 里**没有一个 `import`**（全 2 行，第 1 行还是注释）。
- `prompt.ts` 导入它：`import { BASH_TOOL_NAME } from './toolName.js'`（`source/src/tools/BashTool/prompt.ts` 第 25 行，实测）。
- `BashTool.tsx` 也能导入它，且**不需要经过 prompt.ts**。

两条依赖边都是单向的，加载顺序永远确定：先加载 `toolName.ts`，再加载任何需要它的文件。死结消失。

**代价与收益**：代价是一个只有 2 行的文件，看起来「浪费」；收益是加载顺序不再有歧义，而且这个字符串可以被任意多的文件安全共享——下面看它到底被共享得多广。

### 2.3 证据：一个 2 行文件撑起了多少引用

动手验证一节会跑这个命令，这里先给结论：`BASH_TOOL_NAME` 在 `source/src` 里出现 **100 次**，分布在 **36 个文件**里。一个工具名字符串被 36 个文件共享——权限判断要用它、提示词要用它、日志要用它。如果它挂在任何一个「会反向依赖别人」的大文件上，这 36 个文件就全都可能参与成环。**越是被广泛共享的东西，越要住在依赖图的最底层。**

## 3. 常见误读

**误读 1：「2 行的文件是设计失误，迟早该合并回 BashTool.tsx。」**
正好相反。合并回去，循环依赖立刻复活。这个小文件是**结构性修复的产物**，第 1 行注释就是它的「病历」：曾经真的成过环，拆出来才好。同目录 `FileEditTool/constants.ts`（11 行）、`NotebookEditTool/constants.ts` 的第一行注释是同一句话，说明这是全仓的固定套路。

**误读 2：「循环依赖很罕见，我大概遇不到。」**
恰恰因为常见，仓库才形成了一整套应对模式。本课教材之外，`REPLTool/constants.ts` 第 4 行还导入了 `FILE_EDIT_TOOL_NAME`（实测 `import { FILE_EDIT_TOOL_NAME } from '../FileEditTool/constants.js'`）——连「常量文件」之间也在互相共享工具名，说明这套常量网络是全仓级的基础设施。

**误读 3：「`import type` 也算循环依赖，因为类型也能互相引用。」**
类型层面的循环引用（A 的类型里用到 B 的类型、B 里又用到 A）编译后会被**整行删掉**（L0-02 讲过 `import type` 编译即消失），不会产生运行时死结。会死锁的是**值的导入**——运行时真的要执行代码的那种。区分「类型的环」和「值的环」是读依赖图的基本功。

## 4. 动手验证

数一数这个常量被引用多少次（路线卡片上的验证命令）：

```bash
grep -rn "BASH_TOOL_NAME" source/src | wc -l
grep -rln "BASH_TOOL_NAME" source/src | wc -l
```

**我实际跑出来的输出**：

```
100
36
```

第一行：100 次出现（含 1 次定义，其余是导入和使用）；第二行：分布在 36 个文件里。

再确认它是「叶子」——文件里没有一个 `import`：

```bash
grep -c "import" source/src/tools/BashTool/toolName.ts
```

**实际输出**：

```
0
```

最后看看 prompt.ts 那条边确实存在：

```bash
grep -n "toolName" source/src/tools/BashTool/prompt.ts
```

**实际输出**：

```
25:import { BASH_TOOL_NAME } from './toolName.js'
```

三个数字连起来读：**0 个 import、2 行、36 个文件在用**——这就是「叶子文件」的标准形状。

## 5. 合书自测

**1. 「循环依赖」在文件层面长什么样？**

<details>
<summary>参考答案</summary>

两个文件互相出现在对方的 `import` 区：A 导入 B，B 又导入 A。后果是模块加载器无法决定先加载谁，轻则某个导入值是 `undefined`（对方还没执行完），重则启动报错。

</details>

**2. 把共用常量提到第三个文件 C，为什么就能解开死结？**

<details>
<summary>参考答案</summary>

因为 C 自己不导入任何东西（是叶子），A→C 和 B→C 都是单向边。加载顺序必然是先 C 后 A/B，不再存在「谁先」的问题。死结的根源是「环」，拆掉环就解开。

</details>

**3. 本仓库判断「这个小文件是不是解耦产物」的第一步是什么？**

<details>
<summary>参考答案</summary>

读它的第一行注释。`toolName.ts` 写着 `Here to break circular dependency`，`FileEditTool/constants.ts` 写着 `In its own file to avoid circular dependencies`——同一套路的两句话。

</details>

**4. `BASH_TOOL_NAME` 被多少处引用？这个数字和文件只有 2 行之间有什么关系？**

<details>
<summary>参考答案</summary>

100 次出现、36 个文件。引用者越多，越不能让它挂在任何一个「会反向依赖别人」的大文件上，否则所有引用者都可能与那个大文件成环。共享越广，越要沉到依赖图底层。

</details>

**5. 类型层面的循环引用会不会死锁？为什么？**

<details>
<summary>参考答案</summary>

不会。`import type` 编译后整行消失，类型引用不产生任何运行时代码；会死锁的是值的导入。判断时看是「类型的环」还是「值的环」。

</details>
