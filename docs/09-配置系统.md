# 09 · 配置系统：你的设置到底存在哪

> 本篇目标：搞清楚"主题、默认模型、允许的命令、企业策略"这些设置分别存在哪个文件、谁优先。
> 对应源码：[`src/utils/config.ts`](../source/src/utils/config.ts)、`src/utils/settings/`、`src/services/remoteManagedSettings/`

---

## 9.1 三层配置（优先级从低到高）
| 层级 | 文件位置 | 中文 | 例子 |
|------|----------|------|------|
| 全局 | `~/.claude.json`（由 `getGlobalClaudeFile()` 定位） | 用户级配置 | 主题、默认模型 |
| 项目 | `.claude/settings.json` | 项目级配置 | 该项目允许哪些命令 |
| 企业托管 | managed settings | 公司下发的强制配置 | 禁用某些工具 |

**优先级规则**：越靠近"组织"的层级，优先级越高（企业 > 项目 > 全局）。这样公司能强制统一策略，个人设置不能覆盖。

## 9.2 [`src/utils/config.ts`](../source/src/utils/config.ts) 的一个细节：重入保护

> 📁 本节源码：[`src/utils/config.ts`](../source/src/utils/config.ts)

开头就有一段防递归注释，很典型：

```ts
// Re-entrancy guard: prevents getConfig → logEvent → getGlobalConfig → getConfig
// infinite recursion when the config file is corrupted.
// 重入保护：防止配置文件损坏时 getConfig → logEvent → getGlobalConfig → getConfig 无限递归。
let insideGetConfig = false
```

### 这段在解决什么真实问题
正常情况：

```
getConfig() → 读文件 → 成功返回
```

但如果配置文件**损坏**（比如 JSON 语法错）：

```
getConfig()
  → 解析失败
  → 想打日志 logEvent()
  → logEvent 需要读配置 getGlobalConfig()
  → 又调 getConfig()
  → 又解析失败
  → 又打日志 …
  → 💥 栈溢出
```

`insideGetConfig` 这个布尔开关就是"**我已经在里面的，别再进来**"——第二次调用直接返回兜底默认值，切断递归链。

> **学习要点**：任何"读配置 + 打日志"的系统都有这个递归风险。记住这个模式：`if (inside) return default; inside = true; try { ... } finally { inside = false }`。

## 9.4 一个设置从写下到生效的流程
```
① 用户 / 管理员写下设置
   ├─ 全局:   ~/.claude.json
   ├─ 项目:   .claude/settings.json
   └─ 企业:   managed settings（也可能从远程拉取）
        ↓
② 读取时按优先级合并
   src/utils/settings/settings.ts
   getSettingsForSource() / getInitialSettings()
        ↓
③ 校验
   src/utils/settings/validation.ts → ValidationError
        ↓
④ 变更时应用
   src/utils/settings/applySettingsChange.ts
        ↓
⑤ 各模块按需读取
   例：getTools() 读 allow/deny 规则过滤工具
       例：getSystemPrompt() 读 language / outputStyle
```

## 9.5 企业托管配置的特殊之处
`src/services/remoteManagedSettings/` 有 5 个文件，专门处理"公司下发的配置"：

| 文件 | 作用 |
|------|------|
| `index.ts` | 入口 |
| `securityCheck.tsx` | **安全检查**——托管的配置也要验，防止被中间人篡改 |
| `syncCache.ts` / `syncCacheState.ts` | 同步缓存（离线也能用上次的配置） |
| `types.ts` | 类型定义 |

> 注意 `securityCheck.tsx` 这个设计：**连"管理员下发的配置"都要做安全检查**。这是"零信任"的思路——不因为来源是"公司"就无条件信任。

## 9.6 本篇小结
- 三层配置：全局 `~/.claude.json` < 项目 `.claude/settings.json` < 企业托管。
- `config.ts` 的 `insideGetConfig` 重入保护，防止"配置损坏 → 打日志 → 读配置 → 再损坏"的无限递归。
- 设置流程：写下 → 合并 → 校验 → 应用 → 各模块读取。
- 企业托管配置也要过 `securityCheck`——零信任。
