### 2.2 529 白名单：重试不是免费的（110–174 行）

```ts

// 重试会被放大 3-10 倍（注释原话：3-10× gateway amplification）。

  'repl_main_thread',
  'repl_main_thread:outputStyle:custom',
  // ...（还有 5 项，见原文 137–148 行）
  'sdk',
  'agent:custom',
  'agent:default',
  'agent:builtin',
  'compact',
```

白名单里全是「用户真的在等结果」的路径：主线程、子 agent、压缩。摘要、标题、建议这类后台调用撞 529 **直接放弃**——用户根本看不到它们失败，而每次重试都在给过载的网关添堵。

`shouldRetry529`（169–174 行）里有个反直觉的默认值：`querySource === undefined || FOREGROUND_529_RETRY_SOURCES.has(querySource)`——来源缺失时**选重试**。批注 162–168 行解释：白名单未命中是「已知的后台调用」→ 明确不重试；来源未知是「无法判断用户在不在等」→ 保守选重试。已知路径和未知路径给不同默认值。

### 2.6 退避计算：指数 + 正抖动（909–957 行）

```ts
export function getRetryDelay(
  attempt: number,
  retryAfterHeader?: string | null,
  maxDelayMs = 32000,
): number {
  if (retryAfterHeader) {
    const seconds = parseInt(retryAfterHeader, 10)
    if (!isNaN(seconds)) {
      return seconds * 1000
    }
  }

  const baseDelay = Math.min(
    BASE_DELAY_MS * Math.pow(2, attempt - 1),
    maxDelayMs,
  )
  const jitter = Math.random() * 0.25 * baseDelay
  return baseDelay + jitter
}
```

三件事：
1. **服务端的 `retry-after` 头优先于一切本地计算，且不受 32 秒上限约束**（直接 `return seconds * 1000`，没有 Math.min）。批注 914–921 行：服务端的指令应当被尊重；persistent 模式在外面另套 6 小时封顶，防病态 header。
2. **指数退避**：500ms × 2^(n-1)，封顶 32 秒。曲线：0.5s → 1s → 2s → 4s → 8s → 16s → 32s（第 7 次起封顶）。10 次重试全耗完约 5 分钟。
3. **正抖动**：只往上加 0–25% 噪声，不往下减。批注 945–954 行对比了业界常见的 full jitter：full jitter 打散效果好但「可能莫名等很短」；正抖动保证不低于理论退避值。目的相同——让同时失败的 N 个客户端不要同一毫秒一起重试（thundering herd）。

**为什么必须退避？** 立刻重试等于把故障放大：服务端过载时每个客户端都在原频率上再打一遍；指数退避让重试流量随时间指数衰减，给服务端留出恢复窗口。

### 2.7 shouldRetry：从特殊到一般的决策树（1205–1358 行）

批注 1190–1204 行给出完整优先级：1 测试假错误永不重试 → 2 persistent+429/529 一律重试 → 3 CCR 远程 401/403 重试 → 4 message 含 overloaded 重试 → 5 可修的溢出 400 重试 → 6/7 服务端 `x-should-retry` 显式指令 → 8 连接错误重试 → 9 具体状态码 → 10 其余不重试。核心几段逐字看：

```ts
  // Check for overloaded errors first by examining the message content
  // The SDK sometimes fails to properly pass the 529 status code during streaming,
  // so we need to check the error message directly
  if (error.message?.includes('"type":"overloaded_error"')) {
    return true
  }
```

529 的判定看消息文本而不是状态码（`is529Error`，1065–1076 行，两个判据并存）——因为**流式路径上状态码会丢**。

```ts
  if (error instanceof APIConnectionError) {
    return true
  }
  if (!error.status) return false

  // Retry on rate limits, but not for ClaudeAI Subscription users
  // Enterprise users can retry because they typically use PAYG instead of rate limits
  if (error.status === 429) {
    return !isClaudeAISubscriber() || isEnterpriseSubscriber()
  }
  // Clear API key cache on 401 and allow retry.
  if (error.status === 401) {
    clearApiKeyHelperCache()
    return true
  }
  // Retry internal errors.
  if (error.status && error.status >= 500) return true

  return false
```

三处最容易被误读的地方，批注都点了名：`APIConnectionError` 通常**没有 status**，必须排在 `if (!error.status) return false` 之前（1304–1306 行），否则所有网络错误都被判成不可重试；429 对订阅用户不重试——他们的限流是「几小时后」的配额窗口，企业用户是 PAYG 瞬时速率（408/409 见决策表）；5xx 一律重试——服务端自己的错，值得再试。

| 错误 | 判断处（行号） | 处理方式 |
| --- | --- | --- |
| 测试假 429（mock） | shouldRetry 1209 | **永不重试**（否则测试停不下来） |
| 529 / `overloaded_error` | 586–592、618–653 | 前台白名单 → 退避重试；后台调用 → 直接放弃；连续 3 次 → 抛 `FallbackTriggeredError` 换模型 |
| 429 限流 | shouldRetry 1328–1330 | 订阅用户不重试（配额窗口）；企业/PAYG 重试 |
| `x-should-retry` 头 | shouldRetry 1280–1302 | 服务端显式指令优先于状态码猜测；唯一例外：ant 内部 + 5xx 可无视 false |

| 401 认证失败 | shouldRetry 1341–1344 + 主循环 453–479 | 重试，但要**清凭证缓存 + 刷 token + 重建 client**（不清缓存 = 拿同一个过期 token 白试 10 次） |
| 403 token 被吊销 | shouldRetry 1347–1349 | 重试 + 刷 OAuth token |
| 5xx 服务端错误 | shouldRetry 1355 | 一律重试 |
| 400 上下文溢出（可解析出数字） | 702–750 | 改小 `max_tokens` 立刻重试；**其余 400 不重试** |
| ECONNRESET / EPIPE | 222–228 | 重试 + `disableKeepAlive()`（死连接在池子里，只重试不换池子还会撞上） |
| 其他连接错误（无 status） | shouldRetry 1307–1309 | 重试 |
| 无 status 且不是连接错误 | shouldRetry 1313 | **不重试**（不是 HTTP 层错误，保守放弃） |
| 重试次数用尽 | 669–671 | 抛 `CannotRetryError`（携带 retryContext 供上层报告） |

**一句话总结「为什么不可重试的错误重试也是浪费」**：4xx（除 408/409/401/可修溢出）意味着**请求本身错了**——参数错、格式错、没权限。服务器每次都会以同样的方式拒绝同样的请求，重试只是把自己犯的错重复发给对方，还消耗配额。只有「服务端忙」（429/529/5xx）和「路不通」（连接错误）才值得等一等再试。

## 5. 常见误读

**误读一：「401 不可重试，4xx 都不能重试。」** 401 恰恰要重试，但要带副作用：清 apiKeyHelper 缓存（1342 行）、刷新 OAuth token、重建 client（453–479 行）。只重试不清缓存才是真的浪费——同一个过期 token 试 10 次。教训是「重试前必须让状态变好」。

**误读二：「400 一律不可重试。」** 有一个例外：上下文溢出的 400 可以通过缩小 `max_tokens` 修复（702–750 行），判据是正则能否从文案里解析出三个数字。其余 400（参数错、格式错）确实重试一万次也一样。

**误读三：「retry-after 也要受 32 秒上限约束。」** 不受。`getRetryDelay` 里服务端的 retry-after 直接 `return seconds * 1000`（928 行），没有 Math.min——服务端的显式指令优先于本地策略。32 秒封顶只管本地算出来的指数退避。

<details><summary>2. 529 时为什么不是所有调用都重试？白名单里收的是哪几类？</summary>

因为重试不免费：容量雪崩时每个客户端的重试会被网关放大 3–10 倍。白名单只收「用户真的在等结果」的路径（主线程、子 agent、compact、安全分类器）；摘要/标题/建议等后台调用直接放弃，用户根本看不到它们失败。注意是**白名单**：新增 querySource 默认不重试。
</details>

<details><summary>3. 写出默认退避曲线，并说明抖动方向。</summary>

0.5s → 1s → 2s → 4s → 8s → 16s → 32s（第 7 次起封顶），每次叠加 0–25% 的**正**抖动（只加不减）。10 次重试全耗完约 5 分钟。服务端 retry-after 头优先且不受 32s 封顶约束。</details>

<details><summary>4. 为什么 4xx 大多不可重试？有哪几个例外？各自凭什么例外？</summary>

因为 4xx 表示请求本身错，同样的请求重发只会得到同样的拒绝。例外四个：401（清缓存/刷 token/重建 client 后状态变好）、403 token 被吊销（同上）、408/409（超时与锁冲突，「等一下真的会好」）、上下文溢出的 400（改小 max_tokens 后请求能装下）。</details>

<details><summary>5. 连续 3 次 529 之后发生什么？抛的是哪种「错误」？</summary>

抛 `FallbackTriggeredError`（630 行）——它不是错误而是**控制流信号**：文案是「Model fallback triggered: X -> Y」，claude.ts 必须原样 rethrow，query.ts 接住后换 fallbackModel 重跑。没有 fallbackModel 时，外部用户直接拿到明确的「服务过载」错误而不是看 5 分钟转圈。</details>

<details><summary>6. ECONNRESET/EPIPE 为什么「只重试不关连接池」是错的？</summary>

这两个错误码几乎总是**复用了一条已被服务端关闭的 keep-alive 死连接**（215–221 行批注）。不 `disableKeepAlive()` 的话，下一次重试还从同一个池子拿同一条死连接，继续撞。正确做法：重试 + 关池子重建。
</details>
