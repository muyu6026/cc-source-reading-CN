## 3.1 先给结论：三棒其实是五站

[01 篇](01-项目总览与架构.md) 用「三棒接力」建立骨架，本篇把它放大成五站——多出来的两站都不是小事：

| 站 | 文件 | 干什么 | 证据 |
|:--:|------|--------|------|
| 1 | `entrypoints/cli.tsx` | 看参数，能零依赖办完就立刻退出；否则加载 main | [`cli.tsx`](../annotated/src/entrypoints/cli.tsx#L92) |
| 2 | `main.tsx` **模块顶层** | 在 `main()` 跑起来之前就抢跑 3 个子进程/打点 | [`main.tsx`](../source/src/main.tsx#L1) |
| 3 | `entrypoints/init.ts` | commander 的 `preAction` 钩子：开配置、铺网络、接遥测 | [`init.ts`](../source/src/entrypoints/init.ts#L57) |
| 4 | `setup.ts` | 定目录、抓 hook 快照、建 worktree、预热、埋点、安全闸 | [`setup.ts`](../annotated/src/setup.ts#L314) |

## 3.2 第 1 站 `cli.tsx`：唯一目标是「别加载 main」

这个文件只有 **1 条静态 import**（第 25 行的 `feature`），其余全是 `await import(...)`。这不是风格问题，是性能契约：静态 import 会在模块求值那一刻加载全部依赖树，`claude --version` 就会为整包买单。

快速路径清单（行号均为批注版）：

| 分支 | 干什么 | 注意 |
|------|--------|------|
| `--version` / `-v` / `-V` [L100](../annotated/src/entrypoints/cli.tsx#L100) | 打印版本后 `return` | 前提是 `args.length === 1`，`--version --foo` 不走这里 |
| `--dump-system-prompt` [L127](../annotated/src/entrypoints/cli.tsx#L127) | 打印渲染好的系统提示词 | 内部评测用，外层 `feature('DUMP_SYSTEM_PROMPT')` 从外部构建删掉 |

| `ps` / `logs` / `attach` / `kill` / `--bg` [L300](../annotated/src/entrypoints/cli.tsx#L300) | 后台会话管理 | 注册表在 `~/.claude/sessions/` |

还有两个「改写参数但继续走」的分支容易看漏：`--update` / `--upgrade` 被改写成 `update` 子命令（[L419](../annotated/src/entrypoints/cli.tsx#L419)）；`--bare` 先把 `CLAUDE_CODE_SIMPLE=1` 设上（[L429](../annotated/src/entrypoints/cli.tsx#L429)）——必须这么早，因为后面很多判断在模块求值阶段就要读它。

> **这一站教什么**：快速路径的判据不是「参数长什么样」，而是**「能不能零依赖办完」**。全文件 15 个 `profileCheckpoint`、29 处 `await import`，都是为了把「不必加载的东西」推迟到确定需要的那一刻。

## 3.3 第 2 站 `main.tsx`：模块顶层先抢跑三个动作

`main.tsx` 的第 1–20 行是**故意的顶层副作用**，注释写得很直白（[`main.tsx:1`](../source/src/main.tsx#L1)）：

1. `profileCheckpoint('main_tsx_entry')`——在重模块求值之前先打点；
2. `startMdmRawRead()`——把 MDM 子进程（`plutil` / `reg query`）先发射出去，跟下面「约 135ms 的 import」并行；
3. `startKeychainPrefetch()`——macOS 钥匙串的两次读取提前并发，否则会在 `applySafeConfigEnvironmentVariables()` 里串行同步 spawn，注释自述每次启动约 65ms。

（135ms / 65ms 都是**注释里的作者测量值**，不是本篇实测。）

`main()` 真正的开头只有五件事（[`main.tsx:585`](../source/src/main.tsx#L585)）：

```ts
process.env.NoDefaultCurrentDirectoryInExePath = '1';  // Windows 防 PATH 劫持
initializeWarningHandler();                            // 先接住警告
process.on('exit',  () => { resetCursor() });           // 退出时还原光标
process.on('SIGINT', () => {
  if (process.argv.includes('-p') || process.argv.includes('--print')) return; // 让 print.ts 自己处理
  process.exit(0);
});
profileCheckpoint('main_warning_handler_initialized');
```

两个设计点：`NoDefaultCurrentDirectoryInExePath` 必须**早于任何命令执行**（注释原文：prevent PATH hijacking）；`SIGINT` 在打印模式下直接 `return`，因为 `print.ts` 会注册自己的中断处理器，这里抢先生效会让「优雅收尾」变成硬退出。

## 3.4 第 3 站 `init.ts`：commander 的 `preAction` 钩子

`main()` 用 commander 建命令树，但把初始化挂在 `preAction` 上（[`main.tsx:907`](../source/src/main.tsx#L907)）——好处是 `claude --help` 只打印帮助，**不会**触发初始化。

钩子里的顺序（每一步都有原因）：

| 顺序 | 动作 | 为什么在这 |
|:--:|------|-----------|
| 1 | `await Promise.all([ensureMdmSettingsLoaded(), ensureKeychainPrefetchCompleted()])` | 回收 3.3 提前发射的两个子进程；必须早于第一次读设置 |
| 2 | `await init()` | 配置、网络、遥测的总开关 |
| 3 | `process.title = 'claude'` | 放在 init 之后，好让 `settings.json` 也能关掉它 |
| 4 | `initSinks()` | 子命令不跑 `setup()`，这里不接 sink 就会静默丢事件 |
| 5 | `runMigrations()` | 老版本配置迁移 |

`init` 本身是 `memoize` 包住的（[`init.ts:57`](../source/src/entrypoints/init.ts#L57)），重复调用只跑一次。它做的事按性质分三类：

- **配置**：`enableConfigs()` → `applySafeConfigEnvironmentVariables()`（[L65](../source/src/entrypoints/init.ts#L65)、[L74](../source/src/entrypoints/init.ts#L74)）。注意是「**safe**」，因为此刻**信任对话框还没弹**，来自项目的危险环境变量（`LD_PRELOAD`、`PATH`）还不能应用。
- **收尾与网络**：`setupGracefulShutdown()`（[L87](../source/src/entrypoints/init.ts#L87)）、`configureGlobalMTLS()`、`configureGlobalAgents()`、`preconnectAnthropicApi()`（提前做 TCP+TLS 握手）。
- **发射后不管**：第一方事件日志、OAuth 账户信息、JetBrains 探测、GitHub 仓库探测——一律 `void import(...)`，不阻塞启动。

**与 `setup()` 的分工一句话记**：`init()` 管「配置 / 网络 / 遥测」，`setup()` 管「会话 / 目录 / 工作树」。

> 顺带回答一个常见疑问：`entrypoints/mcp.ts`（196 行）**不在这条链上**。它是 `claude mcp serve` 的入口，`startMCPServer()` 用 stdio 把 CC 的工具对外暴露（[`mcp.ts:35`](../source/src/entrypoints/mcp.ts#L35)），走的是子命令分支，与 REPL 启动无关。

## 3.5 第 4 站 `setup()`：调用方先把它「并行出去」

读 `setup()` 之前必须先看**谁在调它**，否则会误以为它是串行的一环（[`main.tsx:1919`](../source/src/main.tsx#L1919)）：

```ts
if (process.env.CLAUDE_CODE_ENTRYPOINT !== 'local-agent') {
  initBuiltinPlugins();
  initBundledSkills();                       // ① 纯内存 push，<1ms
}
const setupPromise = setup(preSetupCwd, permissionMode, ...);   // ② 不 await
const commandsPromise = worktreeEnabled ? null : getCommands(preSetupCwd);          // ③
const agentDefsPromise = worktreeEnabled ? null : getAgentDefinitionsWithOverrides(preSetupCwd);
commandsPromise?.catch(() => {});            // ④ 抑制瞬时 unhandledRejection
agentDefsPromise?.catch(() => {});
await setupPromise;                          // ⑤ 只等 setup
```

四个可读出来的事实：

1. **① 的位置是被 bug 逼出来的**。内置技能原来在 `setup()` 里注册，但 `setup()` 前面有约 20ms 的 `await`（socket bind），并行的 `getCommands()` 会先跑完并 **memoize 一份没有内置技能的命令表**。修法不是加锁，而是把注册挪到并行启动**之前**——注释原话：pure in-memory array pushes（<1ms, zero I/O）。
2. **③ 在 `--worktree` 时必须放弃并行**。因为 `setup()` 会 `process.chdir()`，而命令表必须从 chdir **之后**的目录读。
3. **④ 的 `.catch(() => {})` 不是偷懒**，是防「setup 那 28ms 窗口里 promise 瞬时 reject」把进程打崩。
4. **`setup()` 自述约 28ms，其中约 20ms 是 `startUdsMessaging` 的 socket bind**（[`main.tsx:1913`](../source/src/main.tsx#L1913) 注释）——不是磁盘 IO，所以敢和 `getCommands` 抢。

`getCommands` 为什么这么怕被抢先？因为它的重活在 `loadAllCommands = memoize(async (cwd) => ...)`（[`commands.ts:449`](../source/src/commands.ts#L449)）——**谁先算，谁定终身**。

## 3.7 worktree 段：唯一有实质分支的地方

`if (worktreeEnabled)` 从 [L570](../annotated/src/setup.ts#L570) 一直到 L795，值得单独看，因为它把「错误分级」演示了一遍：

| 阶段 | 判断 | 失败处理 |
|------|------|----------|
| 能不能建 | `hasWorktreeCreateHook() || await getIsGit()` | **两者都没有 → `exit(1)`**，并提示可以在 `settings.json` 配 `WorktreeCreate` hook（给 SVN/P4 用户留的路） |
| 工作树叫什么 | PR 号 → `pr-1234`；否则 `--worktree <name>`；否则 `getPlanSlug()` | 三条优先级，同一个 slug 同时用于分支名和 tmux 名 |
| 主仓库在哪 | `findCanonicalGitRoot(getCwd())` | 找不到 → `exit(1)`（说明 `.git` 损坏或权限异常） |
| 建树 | `createWorktreeForSession(...)` | 抛错 → `exit(1)`：隔离环境不存在，继续跑就会在错目录改代码 |
| 开 tmux | `createTmuxSessionForWorktree(...)` | 失败只**警告**，继续——tmux 只是便利功能 |

建完之后连着七个落位动作，语义各不相同（[L753](../annotated/src/setup.ts#L753)）：

```ts
process.chdir(worktreeSession.worktreePath);  // 真的搬进程目录（子进程、相对路径全变）
setCwd(worktreeSession.worktreePath);         // 同步内部状态（UI 显示、getCwd）
setOriginalCwd(getCwd());                     // 记录「原本的起点」
setProjectRoot(getCwd());                     // 本次会话的项目根 = 工作树
saveWorktreeState(worktreeSession);           // 持久化，供 /resume 找回
clearMemoryFileCaches();                      // CLAUDE.md 按路径缓存，目录变了必须清
updateHooksConfigSnapshot();                  // 换目录后重新抓 hook 快照
```

最后那句 `updateHooksConfigSnapshot()` 是**同一个快照抓两次**：第 8 步抓的那份是给「建树」用的（`WorktreeCreate` hook 本身要先读快照），建完目录变了，就得为重抓一次覆盖。这是循环依赖的实用解法——先抓一份够用的，再抓一份正确的。

## 3.8 「顺序即正确性」：四条被注释钉死的依赖

| 依赖 | 证据（注释原文关键词） | 破坏了会怎样 |
|------|----------------------|-------------|
| `setCwd()` → `captureHooksConfigSnapshot()` | Must be called AFTER setCwd() | 读到上一个目录的 hook 配置，且**不报错**，表现成「hook 有时生效有时不生效」 |
| worktree 处理 → `getCommands()` | otherwise `/eject` won't be available | 命令表是 memoize 的，少一条 `/eject` 之后不会自己补回来 |
| `await startUdsMessaging()` → `SessionStart` hook | before any hook ... can spawn and snapshot process.env | hook 子进程读到的 `$CLAUDE_CODE_MESSAGING_SOCKET` 是空的 |
| `initBuiltinSkills()` → `getCommands()` | getCommands() memoized an empty list | 内置技能整批不出现（真实发生过的竞态，见 3.5） |

四条里三条都是「**memoize + 顺序**」的产物。所以读这套代码时，看到 `memoize` 就该顺手问一句：它第一次被调用是什么时候？

## 3.9 两个门槛：`before first query` 与 `before render`

`setup()` 里反复出现两个判定词，它们不是同义词：

- **before first query（更硬）**：缺了模型就答错。例：命令表、hook 快照、`initSessionMemory()`。
- **before render（可松）**：缺了只是第一帧闪一下、慢一点。例：logo 的更新日志与最近活动（[L1064](../annotated/src/setup.ts#L1064)）、`loadPluginHooks()`。

由此得到一条取舍原则：**阻塞不是错，无条件的阻塞才是错**。全文只有两处真阻塞的 `await`（终端设置恢复、logo 数据），两处都被 `!isBareMode()` 或 `!getIsNonInteractiveSession()` 严格挡住——脚本模式一毫秒都不花。

---

## 3.10 埋点：`initSinks()` 才是开关时刻

`logEvent()` 在 sink 接上之前**不会丢，只会排队**（[`sinks.ts:5`](../source/src/utils/sinks.ts#L5) 的注释原文：draining any events queued before attachment）。所以 [L1006](../annotated/src/setup.ts#L1006) 那一行 `initSinks()` 是整套埋点系统的分界线：之前入队，之后直送。

紧接着 [L1037](../annotated/src/setup.ts#L1037) 就是 `logEvent('tengu_started', {})`，注释里写了一段事故复盘，值得当成「监控设计」教材：

- `tengu_started` 是**会话成功率的分母**；它发得越晚，崩在它之前的会话就越不计入分母，成功率反而**假性偏高**。
- 事故（inc-3694，P0 级 CHANGELOG 崩溃）：它原来放在 `checkForReleaseNotes` 之后，而那个函数在某一版抛了异常，于是这个 beacon 自己也没发出去，后面的事件全死。
- 修法：把它前移到「第一个可能抛错的 IO」**之前**，紧跟 sink 接好。原则一句话——**监控点要放在故障点上游**。

---

## 3.11 一个常见误解：信任对话框不在 `setup()` 里

很多二手资料（包括 [01 篇](01-项目总览与架构.md) 的初始化清单）会把「工作区信任检查」算进 `setup()`。核对源码后要修正：

- `setup()` 里**唯一**的信任判断在 [L1042](../annotated/src/setup.ts#L1042) 的 `prefetchApiKeyFromApiKeyHelperIfSafe()`；它内部的检查是「key 来自项目/本地设置 **且** 信任未确认 → 直接返回」（[`auth.ts:591`](../source/src/utils/auth.ts#L591)）。也就是说 —— **不弹窗，只是不干活**。
- 真正弹信任对话框的是 [main.tsx:2241](../source/src/main.tsx#L2241) 的 `showSetupScreens()`，位置比 `setup()` **晚**；遥测也要等它之后才初始化（[`main.tsx:2597`](../source/src/main.tsx#L2597)）。

这个顺序解释了一个设计约束：`setup()` 跑的时候，当前目录**可能还没被信任**。所以它开头只能用 `applySafeConfigEnvironmentVariables()` 的成果，只有明确「信任已确认」的动作（执行 `apiKeyHelper` 外部命令）才被允许。**先假设不可信，再逐项解锁**——这是整条启动链的安全基调。

## 3.13 合书自测（不翻书写出答案才算过）

1. `claude --version` 走完这条路径一共加载了几个静态 import？为什么 `--version --foo` 不算快速路径？
2. 为什么 `main()` 里 `setup()` 与 `getCommands()` 能并行，而 `--worktree` 时不能？
3. `setCwd()` 与 `process.chdir()` 有什么区别？`setup()` 里为什么有时候两个都要调？
4. 内置技能注册为什么从 `setup()` 挪到了 `main.tsx`？「把注册提前」比「加锁」好在哪？
5. `initSinks()` 之前调用的 `logEvent()` 会丢吗？`tengu_started` 为什么必须紧跟它？
6. `setup()` 中哪一段不被任何模式跳过？这样做是为了防什么？

<details><summary>参考答案（点开）</summary>

1. **1 个**（`feature`，第 25 行）；`--version` 的输出靠构建期内联的 `MACRO.VERSION`，连配置都不读。`args.length === 1` 才走快速路径，多一个参数就落到完整流程——因为「多参数」意味着用户可能在组合别的开关。
2. 因为 `setup()` 自述约 28ms，其中约 20ms 是 UDS 的 socket bind（不是磁盘 IO），不会和 `getCommands` 的读文件抢资源；而 `--worktree` 会让 `setup()` 真的 `process.chdir()`，命令表必须从 chdir **之后**的目录读，所以 `commandsPromise` 直接置 `null`。
3. `setCwd()` 只改项目自己的 cwd 状态（UI 显示、`getCwd()` 返回值）；`process.chdir()` 改真实进程目录（子进程继承、相对路径生效）。worktree 落位时两个都要调——因为接下来要执行 git 命令、要开 tmux，子进程必须看到新目录。
4. 因为 `setup()` 前面有约 20ms 的 `await`，并行的 `getCommands()` 会先跑完并把「没有内置技能的命令表」memoize 下来。注册只是纯内存数组 push（<1ms、零 IO），挪到并行启动点之前就**必然**先于 `getCommands`——用顺序解决问题，比引入锁更简单，也没有死锁风险。
5. 不会丢，会入队；`initSinks()` 接上 sink 后把队列排空。`tengu_started` 是会话成功率的分母，必须前移到「第一个可能抛错的 IO」之前，否则一次崩溃会让它和它后面的事件集体消失，成功率反而变好看（inc-3694）。
6. **bypass 权限的安全闸**（[L1085](../annotated/src/setup.ts#L1085)）：不在 bare 分支里，也不是 early-return，所以任何模式都跑。防的是「用某个开关把安全检查整段跳过」——尤其是 root 且不在沙箱、或沙箱里还能上网时，`--dangerously-skip-permissions` 必须被拒绝。

</details>
