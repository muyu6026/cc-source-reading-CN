## 1. 为什么这个循环适合「盯变量」

上一课我们顺着调用链倒着读；这一课的代码没有调用链可追——一个函数、一个循环、两个变量。这种代码**顺着读一遍是记不住的**，因为它难的不是语法，是**状态随时间的变化**。

读循环的正确姿势：

1. 先把**变量的初始值**抄在纸上；
2. 再把**循环体的判断条件**抄下来；
3. 然后拿一组具体数据，一条一条「喂」进循环，每喂一条就更新纸上两个变量的值；
4. 循环喂完，再看循环**结束后**还有什么代码会执行。

先看两个变量长什么样（原文第 22–32 行）：

```ts
export function groupMessagesByApiRound(messages: Message[]): Message[][] {
  const groups: Message[][] = []
  let current: Message[] = []
  // ...（中间 25–31 行是注释，讲 id 判据的由来）
  let lastAssistantId: string | undefined
```

| 变量 | 初始值 | 类型含义 | 它记的是什么 |
| --- | --- | --- | --- |
| `current`（第 24 行） | `[]` | 一条消息都没装 | **当前这一组**：还没被切出去的消息 |
| `lastAssistantId`（第 32 行） | `undefined` | `string \| undefined`：还没见过 assistant | **最近一次见到的 assistant 消息 id**——同一个 id = 同一次 API 响应 |
| `groups`（第 23 行） | `[]` | 数组的数组 | 最终成品：每一项是一组 |

为什么要按 `message.id` 切？第 25–31 行的注释给了背景：一次 API 响应会被拆成多条消息，但**它们共享同一个 id**；中途的工具结果还会被实时插进来。所以「id 变了」才是真正的新一轮，才是安全的刀口——刀口切错会把 `tool_use` 和它的 `tool_result` 切开，发 API 直接 400。

## 2. 精读正文：循环本体（原文第 43–57 行）

```ts
  for (const msg of messages) {
    if (
      msg.type === 'assistant' &&
      msg.message.id !== lastAssistantId &&
      current.length > 0
    ) {
      groups.push(current)
      current = [msg]
    } else {
      current.push(msg)
    }
    if (msg.type === 'assistant') {
      lastAssistantId = msg.message.id
    }
  }
```

**逐段念**：

| 行 | 念法 |
| --- | --- |
| 第 44–48 行（三个条件） | 「是 assistant 消息」**且**「id 和上次见的不一样」**且**「当前组不是空的」——三条全中才算一个刀口 |
| 第 49 行 `groups.push(current)` | 把攒到现在的整组**收进成品** |
| 第 50 行 `current = [msg]` | 新组的第一条就是触发刀口的这条 assistant 消息本身（注意是**替换**，不是清空） |
| 第 51–52 行 `else` 分支 | 三条没全中：这条消息**属于当前组**，直接装进去 |
| 第 54–55 行 | 只要这条是 assistant（不管走哪个分支），都更新「最近见过的 id」 |

还有一个变量行为要看清：`lastAssistantId` 声明时是 `string | undefined`（[L0-06](../L0/L0-06-联合类型三值状态机.md) 的联合类型）——`undefined` 就是「还没见过任何 assistant 消息」的状态标记，和任何真实的 id 都不相等，所以第一条 assistant 消息天然能通过第 46 行的比较。

### 循环结束后的收尾（原文第 59–63 行）

```ts
  if (current.length > 0) {
    groups.push(current)
  }
  return groups
```

为什么循环都结束了还要 push 一次？——纸上演示完你就会看到：**最后一组没有人替它触发刀口**。刀口只在「下一条 assistant 到来」时切，但最后那组后面可能根本没有下一条。这是所有「按边界切分」循环的固定套路，漏掉就会丢最后一组。

## 3. 纸上模拟：6 条消息怎么被切进 2 组

数据（一次真实的压缩前会话片段，`type` 和 `message.id` 都标注好）：

| # | 消息 | 说明 |
| --- | --- | --- |
| ① | assistant, id=X | 同一次响应的第 1 块（tool_use：搜索） |
| ② | user | 对应的工具结果 |
| ③ | assistant, id=X | **同一次**响应的第 2 块（tool_use：读文件）——注意 id 还是 X |
| ④ | user | 对应的工具结果 |
| ⑤ | assistant, id=Y | **新一轮**响应（总结文本） |
| ⑥ | user | 人类的新发言 |

现在逐条喂进循环。**你先别往下看，自己走一遍**；走完再对照这张表（每行是「这一条处理完之后」两个变量的值）：

| # | 三条件判定 | 动作 | 处理后的 `current` | 处理后的 `lastAssistantId` | `groups` |
| --- | --- | --- | --- | --- | --- |
| ① | assistant，X ≠ undefined，但 `current.length > 0` **不成立**（是空的） | else：装进当前组 | `[①]` | `X` | `[]` |
| ② | 不是 assistant，前两条直接短路 | else：装进当前组 | `[①②]` | `X`（不变） | `[]` |
| ③ | assistant，但 id X **等于** lastAssistantId | else：装进当前组 | `[①②③]` | `X` | `[]` |
| ④ | 不是 assistant | else：装进当前组 | `[①②③④]` | `X` | `[]` |
| ⑤ | assistant，Y ≠ X，组非空 → **三条件全中，切！** | push 旧组；`current = [⑤]` | `[⑤]` | `Y` | `[[①②③④]]` |
| ⑥ | 不是 assistant | else：装进当前组 | `[⑤⑥]` | `Y`（不变） | `[[①②③④]]` |

循环结束，执行第 59–61 行：`current` 是 `[⑤⑥]`，非空 → push。最终 `groups`：

- 第 1 组：`[①②③④]`——一次 API 响应的块和它们的工具结果，**完整地在一起**；
- 第 2 组：`[⑤⑥]`——新一轮响应和人类的发言。

两个观察点：

1. **③ 是关键**：它也是 assistant，但 id 和 ① 相同，所以不切。如果只判「是不是 assistant」（去掉第二个条件），①②③④ 会被切成四组，`tool_use` 和 `tool_result` 分家。
2. **第 2 组是收尾 push 生成的**：⑥ 不是 assistant，永远不会触发刀口；⑤ 之后也没有新的 assistant 来切它。没有第 59–61 行，这组就丢了。

## 4. 核心问题（路线图 L2-2 卡片）

### 问题 1：三个条件缺一个会怎样？`current.length > 0` 为什么不能省？

**去掉第 45 行 `msg.type === 'assistant'`**：user 消息也参与 id 比较。user 消息的 id 不会等于 assistant 的 id，于是每条 user 消息都可能成为刀口，组被碎成渣——「每条消息一组」和「不分组」一样没用。

**去掉第 46 行 `msg.message.id !== lastAssistantId`**：只要是 assistant 就切。一次响应拆出的多块共享 id（`[tu_A(id=X), result_A, tu_B(id=X)]`），会被切成三组——`tool_use` 和它的 `tool_result` 分家，发 API 时 400。这正是第 25–31 行注释用一大段解释的事。

**去掉第 47 行 `current.length > 0`**：设想第一条消息就是 assistant（resume 恢复的会话经常这样开头）。此时 `current` 还是 `[]`，三条件少这一条的话会命中 → `groups.push([])`——**成品里多出一个空组**。空组在下游「按组砍头」时会造成 off-by-one：你以为砍掉了一组，实际砍掉的是空气，该砍的没砍。这条条件用一次比较就守住了下游的计数正确性。

### 问题 2：循环结束后为什么还要 push 一次（第 59–61 行）？

因为**最后一组没有「下一条消息」来触发它**。刀口的触发条件是「下一个 assistant 到来」，而循环结束意味着没有下一条了——第 3 节表格里的第 2 组 `[⑤⑥]` 就是这样被第 59–61 行手动收走的。

可以反证：把这三行删掉，喂 3 条消息 `[assistant(X), user, user]`，函数返回 `[]`——三条消息全在 `current` 里，但 `current` 永远没被收进 `groups`，**整个输入凭空消失**。这种 bug 不报错、只在特定输入下丢数据，定位成本极高。记住这个固定套路：**按边界切分的循环，结束后必须 flush 尾巴**。

### 问题 3：第 18–20 行说拆这个文件是为了「打断循环依赖」——和 L1-1 是同一个模式吗？

原文第 18–20 行：

```ts
 * Extracted to its own file to break the compact.ts ↔ compactMessages.ts
 * cycle (CC-1180) — the cycle shifted module-init order enough to surface
 * a latent ws CJS/ESM resolution race in CI shard-2.
```

**是同一个模式**：L1-1（`toolName.ts`，2 行）是把共用的字符串常量提出来，让 A、B 都只引用它而不是互相引用；这里是把共用的 20 行函数提出来，让 `compact.ts` 和 `compactMessages.ts` 都引用 `grouping.ts`。手法一致：**把双方都需要的代码提到第三个文件，A↔B 的环就断成了 A→C、B→C**。

但规模和后果不同，值得对比：

- L1-1 是**预防**：2 行常量，拆的时候没什么症状，纯粹是不让环有机会形成；
- 这里是**事后拆环 + 记录事故**：注释里写着事故编号 CC-1180——循环依赖改变了**模块初始化顺序**，暴露了一个潜伏的 `ws` 库 CJS/ESM 解析竞态，而且只在 CI 的 shard-2 上崩。症状（ws 解析失败）和病因（两个业务模块互相 import）毫无语义关联，定位成本极高。

两课合起来记一句话：循环依赖的代价不是「代码不好看」，是**初始化顺序变成隐式状态**。

## 5. 常见误读

| ❌ 0 基础最可能这样读 | ✅ 实际是什么 |
| --- | --- |
| 刀口在 user 消息处（「人类说完话就是新一轮」） | 刀口在**新的 assistant id** 出现处；老版本的「按人类轮次分组」正是因为太粗被换掉的（见第 13–16 行注释） |
| `current = [msg]` 会把 msg 之前的消息弄丢 | 旧消息在第 49 行已经整体 push 进 `groups` 了，一条不少；`current` 是**换新**不是清空 |
| `lastAssistantId` 在循环开头更新 | 在循环体**末尾**（第 54–55 行），且只对 assistant 更新——顺序错了整个判定就反了 |
| 第 59–61 行和第 49 行是重复代码，可以删一个 | 不可删：第 49 行切的是「被新刀口顶出去的组」，59–61 行收的是「没人触发刀口的尾巴」 |

## 7. 合书自测

1. 5 条消息全是 assistant，id 依次是 X、Y、X、Y、X。会被切成几组？每组是什么？
2. 第 47 行 `current.length > 0` 删掉后，输入 `[assistant(id=A), ...]`（第一条就是 assistant）会产出什么坏数据？
3. 为什么同一次 API 响应的多个消息块**必须**留在同一组？切开会发生什么？
4. `lastAssistantId` 的类型是 `string | undefined`。`undefined` 在这里扮演什么角色？如果初始值改成空字符串 `''` 会有问题吗？
5. 循环结束后那三行删掉，什么样的输入会「丢消息」？
6. 本文件和 L1-1 的 `toolName.ts` 是同一个模式吗？一句话说出两处的共同手法。

<details>
<summary>参考答案（先自己写，再展开）</summary>

1. **5 组**。每条的 id 都和前一条不同（X≠undefined、Y≠X、X≠Y、Y≠X、X≠Y），每次都触发刀口，最后再 flush——每条消息自成一组。这个例子说明：id 判据只在「同一次响应共享 id」时才合并，id 乱换的输入会被切到最碎。
2. `groups` 里多出一个**空组 `[]`**：第一条 assistant 满足另外两个条件（是 assistant、id ≠ undefined），但 `current` 还是空的就被 push 了。空组传到下游按组砍头处会造成 off-by-one。
3. 因为它们属于**同一次 API 响应**，其中的 `tool_use` 必须和它的 `tool_result` 一起发；切开就配对失败，API 返回 400。注释（第 30–31 行）举的例子 `[tu_A(id=X), result_A, tu_B(id=X)]` 必须整体在一组。
4. `undefined` 是「**还没见过任何 assistant 消息**」的状态标记。因为任何真实 id 都 ≠ undefined，第一条 assistant 天然能通过比较。改成 `''` 也碰巧能工作（真实 id 不会是空串），但 `undefined` 才是「不存在」的准确表达，`''` 是一个「值为空字符串的 id」，语义上是说谎。
5. 任何**最后一组后面没有新 assistant** 的输入——也就是几乎所有输入。最后攒在 `current` 里的那组永远收不进 `groups`，静默丢失。
6. 是。共同手法：**把双方都需要的代码提到第三个文件，让 A↔B 的循环依赖断成 A→C、B→C**。区别只在规模（2 行常量 vs 20 行函数）和时机（预防 vs 带着事故编号 CC-1180 的事后拆环）。

</details>
